## 1. APIアーキテクチャ

### 1.1 システム構成

```
┌─────────────┐     ┌──────────────────┐     ┌──────────────────┐
│   Client    │────>│  API Gateway     │────>│  Backend Service │
│  (Frontend) │     │ (Spring Cloud)   │     │  (Spring Boot)   │
└─────────────┘     └──────────────────┘     └──────────────────┘
                           │                        │
                           │                    ┌──────────────────┐
                           │                    │   Database       │
                           │                    │ (PostgreSQL等)   │
                           │                    └──────────────────┘
                           │
                    ┌──────────────────┐
                    │ Service Registry │
                    │    (Eureka)      │
                    └──────────────────┘
```

### 1.2 コンポーネント役割

| コンポーネント   | 役割                                                                 |
|------------------|----------------------------------------------------------------------|
| API Gateway      | 単一エントリポイント、ルーティング、認証・認可、レートリミッティング |
| Backend Service  | ビジネスロジックの実装、データベースアクセス                         |
| Service Registry | サービスの登録・発見、ロードバランシング                             |
| Database         | データ永続化                                                         |

### 1.3 通信プロトコル

- **外部通信**: HTTPS (TLS 1.2以上)
- **内部通信**: HTTP (サービス間通信はAPI Gateway経由)
- **データ形式**: JSON (application/json)

## 2. API Gateway設計

### 2.1 Spring Cloud Gatewayの役割

- **単一エントリポイント**: すべての外部リクエストはAPI Gatewayを経由
- **ルーティング**: パスベースのルーティングでバックエンドサービスにリクエストを転送
- **サービスディスカバリー**: Eurekaによる動的なサービス発見とロードバランシング
- **クロスカット関心事**: 認証・認可、ログ、レートリミッティングをGatewayで一元管理

### 2.2 ルーティング設定

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: as-association-service
          uri: lb://as-association-service
          predicates:
            - Path=/api/as/**
          filters:
            - StripPrefix=0
```

### 2.3 ルーティング規則

| 項目       | 説明                                          |
|------------|-----------------------------------------------|
| id         | ルートの一意の識別子                          |
| uri        | 転送先URI（`lb://` でロードバランシング有効） |
| predicates | ルーティング条件（Path、Method、Headerなど）  |
| filters    | リクエスト/レスポンスの変換フィルタ           |

### 2.4 フィルタ設計

| フィルタ種別       | 説明                                                           |
|--------------------|----------------------------------------------------------------|
| グローバルフィルタ | 全ルートに適用される共通フィルタ（ログ、セキュリティヘッダー） |
| ルートフィルタ     | 特定のルートにのみ適用されるフィルタ                           |

#### 使用フィルタ一覧

| フィルタ名         | 説明                     |
|--------------------|--------------------------|
| AddRequestHeader   | リクエストヘッダーの追加 |
| StripPrefix        | パスプレフィックスの削除 |
| RewritePath        | パスの書き換え           |
| RequestRateLimiter | レートリミッティング     |

## 3. セキュリティ設計

### 3.1 認証・認可

| 項目         | 設計                                                                          |
|--------------|-------------------------------------------------------------------------------|
| 認証方式     | JWT（JSON Web Token）またはOAuth 2.0                                          |
| トークン管理 | 認証トークンはHTTPS経由で安全に伝送                                           |
| 認可方式     | RBAC（Role-Based Access Control） - ASモジュールはAZ認可モジュールと連携     |

### 3.2 API Gatewayでのセキュリティ

| 項目                 | 設計                                                                     |
|----------------------|--------------------------------------------------------------------------|
| CORS設定             | 許可されたオリジンからのリクエストのみを許可                             |
| セキュリティヘッダー | `X-Content-Type-Options`, `X-Frame-Options`, `Strict-Transport-Security` |
| レートリミッティング | DDoS対策としてリクエスト制限を適用                                       |
| IPフィルタリング     | 必要に応じてIPアドレスベースのアクセス制御                               |

### 3.3 権限管理

AS関連付けは、組織・従業員情報の参照・登録・更新・削除を行うため、以下の権限管理を適用します。

| 操作     | 必要な権限         | 説明                           |
|----------|-------------------|--------------------------------|
| 参照     | AS:READ           | 組織・従業員情報の参照         |
| 登録     | AS:WRITE          | 組織・従業員情報の登録         |
| 更新     | AS:WRITE          | 組織・従業員情報の更新         |
| 削除     | AS:DELETE         | 組織・従業員情報の削除         |

### 3.4 セキュリティベストプラクティス

- **HTTPSの強制**: すべて通信をHTTPSで暗号化
- **入力サニタイズ**: SQLインジェクション、XSS対策として入力を検証・サニタイズ
- **機密情報の保護**: パスワードやトークンはレスポンスに含まれないようにする
- **ログのセキュリティ**: 機密情報をログに記録しない

## 4. APIバージョン管理

### 4.1 バージョン管理戦略

- **URLベースのバージョン管理**: `/api/as/v1/`、`/api/as/v2/` の形式でバージョンを明示
- **後方互換性の維持**: 既存のAPIを変更する場合は、新しいバージョンを追加し、旧バージョンは廃止スケジュールを明示
- **デプロケーション通知**: APIの廃止予定は `Deprecation` ヘッダーで通知

### 4.2 バージョン命名規則

| バージョン | 説明                       |
|------------|----------------------------|
| v1         | 初期リリース               |
| v2         | 後方互換性のある変更       |
| v3         | 破壊的変更を含むバージョン |

## 5. リソース命名規則

| 要素             | 規則                                 | 例                                              |
|------------------|--------------------------------------|-------------------------------------------------|
| リソース名       | 名詞の複数形、小文字、ハイフン区切り | `/api/as/v1/parties`, `/api/as/v1/employees`    |
| サブリソース     | スラッシュで階層を表現               | `/api/as/v1/parties/{partyId}/roles`            |
| クエリパラメータ | camelCase                            | `?pageSize=10&pageNumber=0`                     |
| パスパラメータ   | リソースのID                         | `/api/as/v1/parties/{partyId}`                  |

### 5.1 APIパスプレフィックス

AS関連付けのAPIは、以下のプレフィックスを使用します。

| 事業領域 | プレフィックス       | 例                                      |
|----------|---------------------|-----------------------------------------|
| AS       | `/api/as/v1/`       | `/api/as/v1/parties`                    |

## 6. ページネーション・ソート設計

### 6.1 ページネーション

| 項目                 | 設計                                       |
|----------------------|--------------------------------------------|
| リクエストパラメータ | `pageSize`, `pageNumber` を使用            |
| レスポンスメタデータ | 総件数、総ページ数、現在のページ情報を返す |
| デフォルト値         | `pageSize` のデフォルト値を設定（例: 20）  |
| 最大値制限           | `pageSize` の最大値を制限（例: 100）       |

#### ページネーションレスポンス例

```json
{
  "data": [...],
  "metadata": {
    "pageSize": 10,
    "pageNumber": 0,
    "totalElements": 100,
    "totalPages": 10
  }
}
```

### 6.2 ソート

| 項目                 | 設計                                              |
|----------------------|---------------------------------------------------|
| リクエストパラメータ | `sort` パラメータでソート条件を指定               |
| ソート形式           | `sort=fieldName,ASC` または `sort=fieldName,DESC` |
| 複数ソート           | カンマ区切りで複数ソート条件を指定                |

## 8. エラーレスポンス共通仕様

### 8.1 エラーレスポンス形式

すべてのAPIエンドポイントで共通して使用するエラーレスポンス形式を定義します。

```json
{
  "error": {
    "status": 400,
    "code": "ERROR_CODE",
    "message": "エラーメッセージ",
    "details": [
      {
        "field": "fieldName",
        "message": "フィールドエラーメッセージ"
      }
    ],
    "timestamp": "2024-01-01T00:00:00Z"
  }
}
```

### 8.2 エラーコード一覧

| エラーコード              | HTTPステータス | 説明                                 |
|---------------------------|----------------|--------------------------------------|
| PARTY_NOT_FOUND           | 404            | 指定されたPartyが見つからない        |
| EMPLOYEE_NOT_FOUND        | 404            | 指定された従業員が見つからない       |
| ORGANIZATION_NOT_FOUND    | 404            | 指定された組織が見つからない         |
| COMPANY_NOT_FOUND         | 404            | 指定された会社が見つからない         |
| STORE_NOT_FOUND           | 404            | 指定された店舗が見つからない         |
| ROLE_NOT_FOUND            | 404            | 指定されたロールが見つからない       |
| PARTY_ALREADY_EXISTS      | 409            | 指定されたPartyは既に存在する        |
| EMPLOYEE_ALREADY_EXISTS   | 409            | 指定された従業員は既に存在する       |
| INVALID_AFFILIATION       | 400            | 無効な所属情報                       |
| INVALID_VALIDITY_PERIOD   | 400            | 無効な有効期間                       |
| INVALID_PARAMETER         | 400            | 無効なパラメータ                     |
| INTERNAL_SERVER_ERROR     | 500            | サーバー内部エラー                   |

### 8.3 HTTPステータスコード一覧

| ステータスコード          | 説明                     |
|---------------------------|--------------------------|
| 200 OK                    | 成功                     |
| 201 Created               | 作成成功                 |
| 204 No Content            | 内容なし（削除成功など） |
| 400 Bad Request           | クライアントエラー       |
| 401 Unauthorized          | 認証失敗                 |
| 403 Forbidden             | 認可失敗                 |
| 404 Not Found             | リソースが見つからない   |
| 409 Conflict              | 競合エラー               |
| 500 Internal Server Error | サーバー内部エラー       |

## 11. REST API設計原則

### 11.1 HTTPメソッドの適切な使用

| HTTPメソッド | 操作     | 幂等性 |
|--------------|----------|--------|
| GET          | 取得     | 幂等   |
| POST         | 作成     | 非幂等 |
| PUT          | 全体更新 | 幂等   |
| PATCH        | 部分更新 | 非幂等 |
| DELETE       | 削除     | 幂等   |

### 11.2 幂等性

- GET、PUT、DELETEは幂等（Idempotent）に設計する
- 同じリクエストを複数回送信しても、結果は同じになる

### 11.3 HATEOAS

- 必要に応じてレスポンスに関連リソースへのリンクを含める

## 12. AS関連付け固有の設計

### 12.1 Party Roleパターン

AS関連付けはParty Roleパターンを採用しています。API設計では、以下の点を考慮します。

| 項目             | 設計                                                                 |
|------------------|----------------------------------------------------------------------|
| PartyとRoleの分離 | Party（実体）とRole（役割）を分離して管理                            |
| ロール有効期間   | ロールの有効期間（開始日・終了日）を管理                             |
| 履歴管理         | ロール変更履歴を保持                                                 |

### 12.2 外部システム連携

AS関連付けは、以下の外部システムと連携します。

| 外部システム   | 連携内容                           |
|---------------|-----------------------------------|
| JBジョブ管理   | 会社・店舗・従業員情報の参照       |
| AGアジルーム   | プロジェクトメンバー情報の参照     |
| AZ認可         | ユーザー権限情報の参照             |

### 12.3 データ一貫性

AS関連付けは、組織・従業員情報の一元管理を行うため、以下の点を考慮します。

| 項目             | 設計                                                                 |
|------------------|----------------------------------------------------------------------|
| トランザクション | 関連する複数のリソースの変更はトランザクションで保護                 |
| 楽観ロック       | 競合更新を防ぐために楽観ロックを適用                                 |
| 変更履歴         | 組織・従業員の変更履歴を保持                                         |
