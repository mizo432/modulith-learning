# 非機能要件一覧

## 概要

本ドキュメントは、Agiloomシステムで扱う非機能要件を中分類毎に定義します。

---

## A. 可用性

### A-01. 稼働時間

> **✅ 対応する**: [ADR-0006](../14%20ADR/ADR-0006_A-01_稼働時間_対応する.md) を参照

システムは、以下の稼働時間を確保すること。

| 項目     | 要件                                     |
|----------|------------------------------------------|
| 稼働率   | 99.9% 以上（年間停止時間 8.76 時間以内） |
| 稼働時間 | 24時間 / 365日                           |
| 対象環境 | 本番環境                                 |

**補足**

- 開発・テスト環境は、本番環境と同じ稼働率を必須としない
- 計画停止時間は稼働率の計算から除外する

### A-02. 計画停止

> **✅ 対応する**: [ADR-0007](../14%20ADR/ADR-0007_A-02_計画停止_対応する.md) を参照

計画的なシステム停止は、以下の要件を満たすこと。

| 項目                 | 要件                                        |
|----------------------|---------------------------------------------|
| 事前通知             | 停止の 3 営業日前までにユーザーに通知       |
| 停止時間帯           | 可能な限り深夜帯（02:00 - 06:00 JST）に実施 |
| 年間回数             | 5 回以内を目標                              |
| 1 回あたりの停止時間 | 2 時間以内を目標                            |

**補足**

- 緊急のセキュリティパッチ適用の場合は、事前通知の期間を短縮できる
- 計画停止のスケジュールは、システム管理画面上で確認可能にする

### A-03. 障害許容度・冗長化

> **✅ 対応する**: [ADR-0008](../14%20ADR/ADR-0008_A-03_障害許容度冗長化_対応する.md) を参照

システムは、以下の障害許容度と冗長化を確保すること。

| 項目                 | 要件                                         |
|----------------------|----------------------------------------------|
| 冗長化構成           | アクティブ・スタンバイ構成またはマルチAZ構成 |
| 単一障害点           | 許容しない                                   |
| 自動フェイルオーバー | 対応（検知から切り替えまで 5 分以内）        |
| データベース冗長化   | マスター・スレーブレプリケーション           |

**補足**

- クラウド環境（AWS/GCP/Azure）を利用する場合、マルチAZ構成を推奨
- スタンバイ系への自動フェイルオーバー機能を実装する

### A-04. 災害対策・免災

> **⚠️ 現時点で対応しない**: [ADR-0001](../14%20ADR/ADR-0001_A-04_災害対策免災_対応しない.md) を参照

システムは、以下の災害対策を講じるものとする。

| 項目             | 要件                             |
|------------------|----------------------------------|
| リージョン冗長化 | 複数リージョンへの展開を考慮     |
| バックアップ     | 別リージョンへのバックアップ保存 |
| 免災計画         | 年 1 回以上の免災訓練の実施      |

**補足**

- 初期段階では単一リージョンでの運用を開始し、規模に応じてマルチリージョン化を検討する
- 免災計画は定期的にレビューし、変更を反映する

### A-05. 目標復旧時間・復旧時点（RTO / RPO）

> **✅ 対応する**: [ADR-0009](../14%20ADR/ADR-0009_A-05_目標復旧時間復旧時点_対応する.md) を参照

システムは、以下の RTO / RPO を目標とする。

| 項目                | 要件                                           |
|---------------------|------------------------------------------------|
| RTO（復旧目標時間） | 4 時間以内                                     |
| RPO（復旧目標時点） | 1 時間以内                                     |
| 対象障害            | 大規模障害（システム全体が利用不能となる場合） |

**補足**

- RTO / RPO は定期的な検証により達成可能であることを確認する
- バックアップの頻度は RPO を満たすように設定する（1 時間間隔以上）

## B. 性能・拡張性

### B-01. 業務量（オンライン・バッチ等）

> **✅ 対応する**: [ADR-0010](../14%20ADR/ADR-0010_B-01_業務量_対応する.md) を参照

システムは、以下の業務量を想定して設計すること。

| 項目                     | 要件                              |
|--------------------------|-----------------------------------|
| 同時オンラインユーザー数 | 100 名                            |
| 総ユーザー数             | 1,000 名                          |
| 日間リクエスト数         | 10 万件                           |
| バッチ処理時間           | 深夜帯（02:00 - 06:00 JST）に完了 |

**補足**

- 初期規模は 100 名を想定し、将来的な拡張を考慮する
- バッチ処理はオンライン処理への影響を最小限に抑える

### B-02. 応答時間

> **✅ 対応する**: [ADR-0011](../14%20ADR/ADR-0011_B-02_応答時間_対応する.md) を参照

システムは、以下の応答時間を確保すること。

| 項目               | 要件                             |
|--------------------|----------------------------------|
| 画面表示時間       | 2 秒以内（95 パーセンタイル）    |
| API 応答時間       | 500 ms 以内（95 パーセンタイル） |
| 検索応答時間       | 3 秒以内（95 パーセンタイル）    |
| バッチ処理応答時間 | 処理内容に応じて定義             |

**補足**

- 応答時間の測定は、本番環境に近い環境で実施する
- 95 パーセンタイルとは、95% のリクエストがその時間以内に応答することを意味する

### B-03. 処理性能・リソース使用率

> **✅ 対応する**: [ADR-0012](../14%20ADR/ADR-0012_B-03_処理性能リソース使用率_対応する.md) を参照

システムは、以下の処理性能とリソース使用率を確保すること。

| 項目             | 要件            |
|------------------|-----------------|
| CPU 使用率       | 平常時 70% 以下 |
| メモリ使用率     | 平常時 80% 以下 |
| ディスク使用率   | 80% 以下を維持  |
| ネットワーク帯域 | 平常時 70% 以下 |

**補足**

- リソース使用率が閾値を超えた場合は、自動スケールアウトまたはアラート通知を行う
- 監視ツールによる常時監視を実施する

### B-04. 拡張性（キャパシティ・プランニング）

> **✅ 対応する**: [ADR-0013](../14%20ADR/ADR-0013_B-04_拡張性_対応する.md) を参照

システムは、以下の拡張性を確保すること。

| 項目                     | 要件                                       |
|--------------------------|--------------------------------------------|
| 水平スケーリング         | 対応（インスタンス追加による拡張）         |
| 垂直スケーリング         | 対応（インスタンススペック変更による拡張） |
| キャパシティプランニング | 四半期ごとに実施                           |
| 拡張のトリガー           | CPU 使用率 70% 超え、メモリ使用率 80% 超え |

**補足**

- オートスケーリング機能を活用し、負荷に応じて自動拡張する
- キャパシティプランニングの結果は、インフラ構成のレビューに反映する

## C. 運用・保守性

### C-01. 運用管理体制

> **✅ 対応する**: [ADR-0014](../14%20ADR/ADR-0014_C-01_運用管理体制_対応する.md) を参照

| 項目           | 要件                                       |

| 変更管理       | 変更申請・承認・実施・検証のプロセスを確立 |
| 定期レビュー   | 月 1 回以上の運用レビューを実施            |

**補足**

- 運用マニュアルは、新規メンバーが自律的に運用できるよう詳細に記述する
- 変更管理は、本番環境へのデプロイを含むすべての変更を対象とする

| ダッシュボード | リアルタイムの監視ダッシュボードを提供                 |

**補足**

#### E-06-01. 機微情報の暗号化

データベースに格納される機微な情報は、AES-256-GCM方式で暗号化して保存すること。

**暗号化対象の機微な情報**

| 情報種類               | 説明                   | 関連エンティティ                              | 暗号化対象            |
|------------------------|------------------------|-----------------------------------------------|-----------------------|
| 個人のファーストネーム | 個人を特定できる名     | User.firstName, Employee.firstName, FirstName | ✅ 暗号化             |
| 個人のラストネーム     | 個人を特定できる姓     | User.lastName, Employee.lastName, LastName    | ✅ 暗号化             |
| 個人のメールアドレス   | 個人を特定できる連絡先 | User.email                                    | ❌ 平文保持（検索用） |
| 個人の電話番号         | 個人を特定できる連絡先 | SampleContact.phoneNumber                     | ❌ サンプルデータ     |
| 検索用名称             | 検索用の名称           | SearchName.value                              | ❌ 平文保持（検索用） |

**実装方針**

- JPA AttributeConverterを使用して、エンティティレベルで暗号化/復号化を透明に行う
- Spring Security CryptoのAesGcmContentEncryptorを利用
- 鍵は環境変数から取得し、本番環境では秘密管理サービスと連携
- 検索機能との兼ね合い：SearchName分離パターンを採用し、表示用氏名は暗号化、検索用名称は平文で保持

#### E-06-02. 鍵管理

暗号化に使用する鍵は、以下の要件を満たす方法で管理すること。

- 鍵は環境変数または秘密管理サービスから取得すること
- 開発環境と本番環境で鍵を分離すること
- 定期的な鍵ローテーションの仕組みを備えること

#### E-06-03. データの安全な廃棄

不要になったデータは、以下の要件を満たす方法で安全に廃棄すること。

- 論理削除：削除フラグを設定し、物理削除は行わない
- 物理削除：保持期間経過後、暗号化鍵を破棄することでデータを復元不能とする
- 廃棄記録：廃棄したデータの内容・日時・責任者を記録する

#### E-06-04. データ漏洩対策

データ漏洩時の影響を最小限に抑えるため、以下の対策を講じるものとする。

- データ分類：機微情報のレベルを定義し、適切な保護措置を適用する
- アクセス制御：機微情報へのアクセスは、必要最小限のユーザーに制限する
- 監査：機微情報へのアクセスをログ記録し、定期的な監査を実施する
- 漏洩時の対応：データ漏洩発生時の対応手順を定義し、訓練を実施する
