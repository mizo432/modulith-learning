# AS 関連付け要望

Association/Relationship Management（AS）モジュールに関する要望を整理します。

## 1. 概要

ASモジュールは、組織・部署・従業員・会社・店舗などの関連付けを管理するコアモジュールです。
JBジョブ管理など他のモジュールからASモジュールのエンティティを参照する仕組みと、ASモジュール自体の拡張要望を記載します。

* Party Roleパターンです

## 2. 業務分析

### 2.1 業務背景

本システムでは、複数の事業領域（JB ジョブ管理、AG アジルーム、AZ 認可など）が組織・従業員情報を参照する必要があります。
各事業領域で独立して組織・従業員情報を管理すると、以下の問題が発生します。

- **データ的不整合**: 各モジュールで同じ組織・従業員情報を重複管理すると、更新時の不整合が生じる。
- **保守コストの増大**: 組織変更や従業員異動時に、複数のモジュールを更新する必要がある。
- **権限管理の複雑化**: 各モジュールで権限範囲の定義が異なると、一貫したアクセス制御が困難になる。

これらの問題を解決するために、ASモジュールが組織・従業員情報を一元管理し、他の事業領域はASモジュールを参照する仕組みを採用します。

### 2.2 Party Roleパターンの業務上の価値

Party Roleパターンを採用することで、以下の業務上の価値を実現します。

#### 実体と役割の分離

- **柔軟な役割変更**: 従業員が部署を移動しても、実体(Party)は変わらず、ロールのみを変更することで履歴を追跡可能。
- **複数の役割の併存**: 同一の従業員が複数の部署に所属するケース（兼務）を自然に表現可能。
- **組織構造の変更対応**: 組織の再編時にも、実体(Party)を維持したままロールの関連付けのみを変更可能。

#### 履歴管理の容易さ

- **部署変更履歴**: 従業員の部署変更履歴を、ロールの有効期間として管理可能。
- **組織変遷の追跡**: 組織の名称変更や階層構造の変更を追跡可能。
- **監査対応**: 誰がいつどの組織に所属していたかを正確に記録可能。

#### 拡張性の向上

- **新しいロールタイプの追加**: 既存のParty構造を変更せずに、新しいロールタイプを追加可能。
- **事業領域横断的な利用**: JB ジョブ管理、AG アジルーム、AZ 認可など、複数の事業領域から共通の基盤として利用可能。

### 2.3 各業務領域間のデータフロー

ASモジュールの4つの業務領域間のデータフローは以下の通りです。

```
Party (実体)
  │
  ├─ PartyRole (ロール定義)
  │     │
  │     ├─ PersonRole (人ロール: 従業員の所属管理)
  │     │     └─ 従業員 → 組織/部署 の関連付け
  │     │
  │     └─ OrganizationRole (組織ロール: 組織階層管理)
  │           └─ 会社 → 部署 → 店舗 の階層構造
  │
  └─ 外部事業領域からの参照
        ├─ JB ジョブ管理: 会社・店舗・従業員情報参照
        ├─ AG アジルーム: プロジェクトメンバー管理
        └─ AZ 認可: ユーザー権限管理
```

### 2.4 外部事業領域からの参照要件

#### JB ジョブ管理からの参照

JB ジョブ管理では、以下の情報をASモジュールから参照します。

- **会社・店舗情報**: ジョブ実行権限のフィルタリング、通知対象の設定
- **従業員情報**: 監査ログの操作者情報、ユーザー権限管理
- **組織階層情報**: 会社・店舗別のデータアクセス制御

具体的な参照パターン:

1. **ジョブ実行時の権限チェック**: 実行ユーザーが対象会社・店舗の権限を持っているか確認。
2. **監査ログの記録**: 操作者の所属組織・部署情報を記録。
3. **通知対象の決定**: 会社・店舗単位で通知対象をフィルタリング。

#### AG アジルームからの参照

AG アジルームでは、以下の情報をASモジュールから参照します。

- **プロジェクトメンバー管理**: 従業員の所属組織・部署情報に基づいてプロジェクトメンバーを管理。
- **権限管理**: 組織階層に基づいた権限範囲の定義。

#### AZ 認可からの参照

AZ 認可では、以下の情報をASモジュールから参照します。

- **ユーザー権限管理**: 組織・従業員情報に基づいて権限範囲を決定。
- **データアクセス制御**: 会社・店舗単位でのデータアクセス権限の管理。

### 2.5 非機能要件の具体化

ASモジュールが満たすべき非機能要件は以下の通りです。

#### パフォーマンス

- **読み取りパフォーマンス**: 一覧APIはページネーション対応し、大量データ時のレスポンス時間を考慮した設計。
- **キャッシュ戦略**: 頻繁に参照される組織・従業員情報はキャッシュを検討。
- **インデックス設計**: 会社コード・店舗コード・従業員ID での検索に最適化されたインデックスを設定。

#### 一貫性

- **トランザクション管理**: 組織変更や従業員異動時の一貫性を保証。
- **楽観ロック**: 同時更新による不整合を防止。

#### 権限管理

- **読み取り専用APIの権限チェック**: 参照APIでも適切な権限チェックを実施。
- **データアクセス制御**: 会社・店舗単位でのデータアクセス制御を支援。

#### 監査対応

- **変更履歴の記録**: 組織・従業員情報の変更履歴を追跡可能。
- **有効期間の管理**: ロールの変更履歴を有効期間として管理。

## 3. JBジョブ管理からのAS参照要望

### 3.1 会社・店舗参照

**要望:** JBジョブ管理からASモジュールのCompany/Storeエンティティを参照したい。

**背景:**

- 会社・店舗別のジョブ実行権限フィルタリングに必要
- 通知対象を会社・店舗単位で設定したい
- 会社・店舗の情報はASモジュールで一元管理されている

**具体的な要望:**

- Companyエンティティの読み取り専用APIを提供してほしい
- Storeエンティティの読み取り専用APIを提供してほしい
- 会社コード・店舗コードで検索できるクエリAPIが欲しい

### 3.2 従業員参照

**要望:** JBジョブ管理からASモジュールのEmployeeエンティティを参照したい。

**背景:**

- ユーザー権限管理で従業員情報を参照したい
- 監査ログに操作者名を記録したい
- 従業員の所属組織・部署情報を取得したい

**具体的な要望:**

- Employeeエンティティの読み取り専用APIを提供してほしい
- 従業員ID・ユーザー名で検索できるクエリAPIが欲しい
- 所属組織・部署情報を含めて取得できるAPIが欲しい

## 4. ASモジュール拡張要望

### 4.1 会社・店舗のクエリAPI追加

**要望:** 会社・店舗の一覧取得・検索APIを追加したい。

**具体的な要望:**

- 会社一覧取得API（有効フラグフィルタ対応）
- 店舗一覧取得API（会社コードフィルタ対応）
- 会社・店舗の詳細取得API

### 4.2 従業員のクエリAPI追加

**要望:** 従業員の一覧取得・検索APIを追加したい。

**具体的な要望:**

- 従業員一覧取得API（組織・部署フィルタ対応）
- 従業員詳細取得API（所属情報を含む）

### 4.3 関連付けクエリAPI

**要望:** 従業員と組織・部署の関連付け情報を取得するAPIを追加したい。

**具体的な要望:**

- 従業員ごとの所属組織・部署一覧取得
- 組織・部署ごとの所属従業員一覧取得

## 5. 非機能要望

### 5.1 パフォーマンス

- 一覧APIはページネーション対応を希望
- 大量データ時のレスポンス時間を考慮した設計を希望

### 5.2 権限管理

- 読み取り専用APIでも適切な権限チェックを希望
- 会社・店舗単位でのデータアクセス制御を希望

## 6. 優先度

| 要望              | 優先度 |
|-------------------|--------|
| 会社・店舗参照API | 高     |
| 従業員参照API     | 高     |
| クエリAPI追加     | 中     |
| 関連付けクエリAPI | 中     |
| ページネーション  | 低     |
