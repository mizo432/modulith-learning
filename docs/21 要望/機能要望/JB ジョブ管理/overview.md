Jobloom 概要設計
1. Jobloomとは
   Jobloom（ジョブルーム） は、複数の業務システムに組み込まれたジョブを、統一的に起動・監視・管理するための分散ジョブ実行・運用管理システムです。
   ジョブの定義、起動要求、スケジュール管理、実行先の選択、実行状況の監視、実行履歴、通知、異常終了後の復旧操作を一元管理します。
   Jobloom の基本方針
   ジョブの実行から復旧まで、確実に。

分散実行の一元管理
複数の業務アプリケーションサーバーに配置されたジョブを統一的に管理する。


実行状況の可視化
実行状態、処理結果、エラー、実行履歴を確認できる。


安全な障害復旧
自動リトライは行わず、運用管理者が原因を確認して再実行・再開を判断する。



2. システム構成
   Jobloom はジョブの実行管理を担当し、実際の業務処理は各業務システムが担当します。
   Jobloom 管理画面
   ジョブ定義・実行状況・履歴・復旧操作

Jobloom 実行管理 API
スケジュール・実行制御・実行先選択・権限・通知

業務サーバー A
業務ジョブと起動 API


業務サーバー B
業務ジョブと起動 API



業務サーバーは必要に応じて複数台に拡張

PostgreSQL
定義・状態・履歴・監査ログ


S3 / MinIO
入力ファイルなどのオブジェクト保管

3. 主な機能
   機能	概要
   ジョブ定義管理	ジョブコード、パラメータ、実行条件、バージョンを管理
   ジョブ起動	管理画面からの手動起動、業務システム API、スケジュールによる起動
   分散実行制御	複数サーバーから実行可能なサーバーを選択し、同時実行数を制御
   実行状況監視	待機中、実行中、成功、失敗などの状態を管理
   実行履歴・ログ	実行結果、処理件数、エラー情報、実行時間を記録
   通知	設定に応じて成功・異常終了などを通知
   障害復旧	運用管理者が再実行または対応ジョブの途中再開を実施
   権限管理	システム、会社、店舗単位で参照・操作権限を制御
   監査ログ	手動起動、再実行、再開などの操作を記録
4. ジョブの実行フロー
1. 起動要求
   管理画面、スケジュール、または業務システムから起動要求を受け付ける。
2. 実行条件の確認
   ジョブの定義、実行権限、バージョン、実行可能なサーバー、同時実行枠を確認する。
3. 実行先への依頼
   Jobloom が対象サーバーの API を呼び出し、業務ジョブの実行を依頼する。
4. 非同期実行
   業務サーバーは受付結果を返し、業務処理をバックグラウンドで実行する。Jobloom は状態照会などで進捗と結果を確認する。
5. 結果の記録と通知
   実行結果、実行時間、処理件数、エラー情報を保存し、設定に応じて通知する。

5. 障害発生時の復旧方針
   Jobloom は、障害時に業務処理を無条件で再実行しないことを基本方針とします。
- 自動リトライは行わない。
- 異常終了を記録し、運用管理者が原因を調査する。
- 最初からの再実行、または対応ジョブのチェックポイントからの再開を手動で判断する。
- 再実行・再開時は新しい実行 ID を発行し、元の実行履歴との関係を保持する。
- 起動 API のタイムアウトなどで結果が不明な場合は、状態を照会して確認する。実行済みの可能性があるため、直ちに別サーバーで再実行しない。
- 途中再開は、業務ジョブ側にチェックポイント管理や重複処理防止の仕組みがある場合に限る。
6. 技術構成
   項目	採用技術・方針
   バックエンド	Java / Spring Boot
   データベース	PostgreSQL
   オブジェクトストレージ	本番：Amazon S3、開発・テスト：MinIO
   ストレージ SDK	AWS SDK for Java 2.x
   テスト	Testcontainers（PostgreSQL、MinIO）
   サーバー構成	複数の業務アプリケーションサーバー
   サーバー間連携	REST API による非同期ジョブ実行
   排他・同時実行制御	PostgreSQL のトランザクションとロックを利用
   バージョン管理	実行時のジョブバージョンを履歴に保存
7. 主要なデータ管理
   テーブル	役割
   job_definition	ジョブ定義
   job_deployment	サーバーごとの配備状況・バージョン
   application_server	業務アプリケーションサーバー情報
   job_execution	ジョブ実行状態・実行結果・実行履歴
   job_execution_slot	同時実行枠の管理
   job_execution_event	状態遷移・実行イベント
   user_company / user_store	会社・店舗単位の権限
   user_notification	通知情報
   uploaded_file	S3 / MinIO 上のファイル参照情報
   ファイルの実体は S3 / MinIO に保存し、PostgreSQL にはバケット名、オブジェクトキー、サイズ、チェックサムなどの参照情報を保存します。
8. 設計上の重要原則
1. 業務処理と実行管理を分離する。 Jobloom は業務ロジックを持たず、業務アプリケーション側がジョブを実装する。
2. 実行受付と処理完了を分離する。 API の受付成功を業務処理の成功とみなさない。
3. 重複起動を防止する。 実行 ID を冪等性キーとして扱い、同じ要求による二重起動を抑止する。
4. 複数サーバーで安全に実行する。 実行枠や排他制御を共有し、サーバー間の競合を防ぐ。
5. 復旧操作を追跡可能にする。 元の実行履歴を残し、再実行・再開の理由や操作者を監査ログに記録する。
6. 業務システムの利用者と運用担当者を分離する。 業務画面やファイルアップロード画面は各業務システムが担当し、Jobloom は実行管理に専念する。
9. 開発の進め方
1. ジョブ実行 API と業務アプリケーション側の共通インターフェースを定義する。
2. ジョブ定義、実行履歴、サーバー管理のデータモデルを実装する。
3. 実行先選択、同時実行制御、非同期状態照会を実装する。
4. 管理画面、権限管理、通知、監査ログを実装する。
5. 手動再実行・再開、結果不明時の復旧、サーバー障害などの結合テストを行う。
   まとめ： Jobloom は、各業務システムに組み込まれたジョブを API 経由で実行し、複数サーバーにまたがる実行管理・監視・履歴・手動復旧を一元化する基盤です。業務処理そのものは各業務システムに任せ、Jobloom は安全で追跡可能なジョブ運用を実現します。
