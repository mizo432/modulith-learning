# Agiloom：画面一覧とユースケース一覧

## 1. 目的と整理方針

Agiloomは、プロダクトの価値仮説づくりから、ユーザーストーリーマッピング、バックログ管理、計画、実行、テスト、リリース、振り返りまでをつなぐスクラム支援システムである。

本資料では、画面を利用者が行う作業単位で整理し、各画面で実現するユースケースを対応付ける。画面は実装上の候補であり、最終的なメニュー構成や画面分割はユーザビリティ検証により調整する。

## 6. 主要な業務フロー

``` mermaid
flowchart TD
    A[プロダクトビジョン・Product Goal] --> B[ペルソナ・ユーザージャーニー]
    B --> C[機会・課題の特定]
    C --> D[ユーザーストーリーマッピング]
    D --> E[Epic / Feature / User Story]
    E --> F[Product Backlogの優先順位付け]
    F --> G[Sprint Planning]
    G --> H[実装・Sprint中の調整]
    H --> I[Sprint Review・フィードバック]
    I --> J[受入・シナリオ・性能テスト]
    J --> K[Release Readiness・リリース判断]
    K --> L[プロダクト指標・振り返り]
    L --> C
```

## 7. 画面設計上の原則

1. **作業の流れをつなぐ**：ジャーニー、ストーリーマップ、バックログ、Sprint、テスト、Releaseを相互リンクする。
2. **判断根拠を残す**：優先順位、範囲変更、受入判定、Release判断に理由・証拠・日時を記録する。
3. **計画と実績を分ける**：計画時点のスナップショットと、その後の変更履歴を保持する。
4. **候補と確定を区別する**：AIやルールが生成した候補は、利用者が確認・採用するまで確定事項として扱わない。
5. **成果と活動量を混同しない**：ベロシティ等はチームの計画・改善に使い、個人評価に利用しない。
6. **SprintとReleaseを分ける**：Releaseは複数Sprint・Epicにまたがり得る。Story完了だけでRelease可能とは判定しない。
7. **Scrumの責任分担を保つ**：POは価値とProduct
   Backlogに責任を持ち、Sprint GoalはScrum Teamで協働し、Sprint
   Backlogの実行計画は開発者が具体化する。

## 9. 次の設計ステップ

- 画面一覧を情報設計（ナビゲーション、画面遷移、主要操作）に落とす。
- 各ユースケースに事前条件、基本フロー、代替・例外フロー、事後条件を定義する。
- ユースケースからApplication層のUse
  Case、Command/Query、権限チェックを導出する。
- 画面単位ではなく業務責務単位でBounded
  Contextを検討し、画面とドメインモデルを直接一対一にしない。
- MVPの対象を決め、ユースケース受入条件とE2Eシナリオに接続する。
