# Agiloom：備えるべきFeature一覧

## 1. 目的と設計方針

Agiloomは、スクラムチームと関係者がプロダクトの課題発見から計画、開発、品質確認、リリース、学習までを一貫して扱えるプロダクト開発支援システムです。

本書では、Agiloomに必要なFeatureをプロダクト領域ごとに整理します。Featureは利用者価値を表す機能単位であり、実装時にはユーザーストーリーやタスクへ分割します。

設計方針：

- プロダクト価値とチームの学習を支援し、管理のための入力負荷を増やしすぎない。
- 従業員、チームメンバー（PO・SM・開発者）、チーム外のトラッキング担当、システム管理者の役割を区別する。
- 所属、スクラム上の役割、プロジェクト権限を別々に管理できるようにする。
- 情報の変更履歴、判断根拠、成果との関連を追跡できるようにする。
- 指標は判断材料として示し、個人評価やチーム間競争を促す使い方を避ける。

## 2. Feature優先度の目安

| 優先度 | 意味                                                       |
|--------|------------------------------------------------------------|
| MVP    | 最初の実用リリースに必要な基盤機能                         |

| 拡張   | 高度な分析、自動化、外部連携など、利用実績を見て広げる機能 |

#### Kanoモデルによる要望評価

各要望について、対象ユーザーに機能の充足・不充足を対にして質問します。

1. **充足質問**：「その機能がある場合、どう感じますか？」
2. **不充足質問**：「その機能がない場合、どう感じますか？」

回答は、たとえば「満足」「当たり前」「無関心」「仕方ない」「不満」から選びます。Agiloomは回答の組み合わせを評価マトリックスに照合し、要望を次の5カテゴリに分類します。

| カテゴリ（品質要素）            | 顧客の心理・状態                                                   | 例（スマートフォンの場合）                           | 開発時の優先度・扱い                                                                       |
|---------------------------------|--------------------------------------------------------------------|------------------------------------------------------|--------------------------------------------------------------------------------------------|
| **当たり前品質（Must-Be）**     | あって当然。ないと強い不満を感じるが、あっても満足度は上がりにくい | 通話ができる、故障しない                             | **最優先**。必須要件として扱い、満たせない場合はリリース可否を慎重に判断する               |
| **一元品質（One-Dimensional）** | あればあるほど嬉しく、なければ不満につながる                       | バッテリーが長持ちする、カメラ画質が良い、操作が速い | **競争力の鍵**。コストと期待効果のバランスを見て強化する                                   |
| **魅力的品質（Attractive）**    | あると感動や差別化につながるが、なくても不満にはなりにくい         | 新しいAI自動編集機能                                 | **差別化要素**。当たり前品質・一元品質を確保したうえで、投資余力や戦略に応じて実装する     |
| **無関心品質（Indifferent）**   | あってもなくても顧客満足度にほとんど影響しない                     | 使われない細かな設定機能、過剰な梱包                 | **原則として開発対象から外す**。コストをかけず、必要性が確認された場合に再評価する         |
| **逆品質（Reverse）**           | 実装により、かえって顧客の不満を招く                               | 多機能すぎて操作が複雑、過剰な認証                   | **そのまま実装しない**。不満の原因や対象ユーザーを確認し、簡素化・任意化・代替案を検討する |

分類は回答の傾向を示す判断材料です。単独で優先順位を自動決定せず、対象者、サンプル数、利用文脈、事業価値、コスト、リスク、技術的依存関係と合わせてPOが解釈します。回答が割れた場合は、ユーザー群や利用場面ごとに分けて分析します。

**優先順位の基本方針**
は、まず当たり前品質を必須要件として満たし、次に一元品質を競争力につながる範囲で強化し、そのうえで魅力品質による差別化を検討することです。無関心品質は原則として開発対象から外し、逆品質はそのまま実装せず、顧客の不満を生む要因を調査して簡素化や任意化などを検討します。

この順序は基本方針であり、固定ルールではありません。法令・セキュリティ上の必須対応、Product
Goalへの寄与、緊急度、リスク低減、実装コスト、依存関係などを考慮し、POが優先順位と例外の理由を記録します。

| Agiloomで管理する情報 | 内容                                                 |
|-----------------------|------------------------------------------------------|
| 対象要望              | 評価するFeatureや要求、背景、想定ユーザー            |
| 質問ペア              | 充足質問と不充足質問の文面                           |
| 回答                  | 各質問に対する回答、回答者属性（必要かつ適切な範囲） |
| 評価結果              | 回答組み合わせ、分類マトリックスの結果、分類カテゴリ |
| 分析状況              | 回答数、回答分布、セグメント別傾向、データ品質       |
| PO判断                | 分類の解釈、優先順位への反映、判断理由、再調査の要否 |

## 5. 推奨する段階的な実装

### フェーズ1：Agiloomの基本運用（MVP）

- 従業員アカウント、チーム、プロジェクト、ロール、基本権限
- Product Vision／Goalと課題・要望受付
- Product Backlog、優先順位、受入条件、変更履歴
- Sprint、Sprint Goal、Sprint Backlog、作業ボード
- 障害・リスク、コメント、通知
- Definition of Done、欠陥管理、Sprint ReviewとRetrospectiveの記録
- ロール別ダッシュボード、トラッキング担当向けプロジェクト状況
- 監査ログ、バックアップ、基本的な管理コンソール

### フェーズ2：計画・協働・品質の強化

- User Journey、Story Mapping、ステークホルダー管理
- Epic Planning、Release Planning、依存関係・見積もり支援
- テストケース、受入テスト、レビュー参加、品質Insights
- 成功指標、Product Goal進捗、改善効果の確認
- 権限申請・棚卸し、SSO／MFA、運用監視、外部連携管理

### フェーズ3：高度な検証と自動化

- 実験・仮説検証の支援
- Gatling等との性能テスト連携と比較分析
- CI/CDやソース管理との連携
- リリース後の利用状況・成果データ連携
- 重複要求やリスク傾向の高度な分析、自動化

導入順は固定せず、チームの課題、セキュリティ要件、利用実績に応じて調整します。各フェーズでは、機能数ではなく、要求から成果までの追跡性、品質、障害解消、ユーザー成果への寄与で効果を確認します。

## 6. MVPの受入観点

初回リリースでは、少なくとも次を確認できる状態を目指します。

- 従業員をチームメンバーとトラッキング担当に分け、適切な権限を付与できる。
- チームメンバーにPO、SM、開発者の役割を設定できる。
- 課題・要望からバックログ、スプリント、テスト・レビューまで関係を追跡できる。
- POがバックログの内容と順序を管理でき、開発者がSprint Backlogを管理できる。
- SMが障害と改善アクションを追跡できる。
- トラッキング担当が許可された範囲で進捗、成果、リスクを確認できる。
- 重要な権限・設定変更を監査でき、データを復旧できる。

## 7. 結論

AgiloomのFeatureは、戦略とDiscovery、要求、バックログと計画、スプリント協働、品質とテスト、レビューとリリース、継続的改善、トラッキング、システム運用を一続きに支援する構成が望まれます。

まず役割・権限と、課題からバックログ、スプリント、成果確認までの基本ループを実用化します。その後、ユーザー理解、Release
Planning、性能テスト、Insights、外部連携を利用実績に基づいて追加します。Agiloomの中心価値は、入力や管理を増やすことではなく、チームと関係者が価値、進捗、品質、学びを共有して適応できることです。
