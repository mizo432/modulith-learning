# Agiloom：汎用サブドメイン一覧

## 1. 目的と定義

本書では、Agiloomのコア業務を支えるうち、多くの業務システムに共通し、標準製品・ライブラリ・外部サービスの利用を検討しやすい
**汎用サブドメイン**を整理します。

汎用サブドメインはAgiloomの差別化の中心ではありません。独自実装を増やすより、信頼できる標準機能を活用し、運用負荷とセキュリティリスクを抑えることを基本方針とします。ただし、Agiloom固有の業務ルールやアクセス境界は、汎用サービスへ無理に委ねずアプリケーション側で明確に扱います。

## 3. サブドメインの詳細

### 3.1 認証・アカウント・権限基盤

認証は「誰が利用しているか」を確認し、認可は「その利用者が何をできるか」を判定します。Agiloomでは両者を混同せず、認証基盤とプロダクト固有のロール・アクセスルールを分けます。

- 認証基盤：ログイン、MFA、SSO、セッション、資格情報の管理。
- アカウント基盤：従業員の識別子、プロフィール、アカウント状態。
- 認可基盤：組織・プロジェクト・操作ごとの許可判定。
- Agiloom固有ルール：従業員、チームメンバー、PO、SM、開発者、トラッキング担当、システム管理者の役割と業務責任。

認証サービスを利用しても、POがバックログ順序に責任を持つことや、トラッキング担当を参照中心にすることなど、Agiloom固有の権限ポリシーはアプリケーション側で明確に定義します。

### 3.2 通知・メール

通知の配信機構は汎用機能ですが、どの業務イベントを誰に知らせるかはAgiloomの業務ルールです。

- 汎用側：メール・プッシュ配信、再試行、配信状態、テンプレート管理。
- Agiloom側：メンション、判断待ち、障害、期限、レビュー依頼などの通知条件。
- 利用者設定：通知チャネル、頻度、ミュート、配信時間帯。

### 3.3 ファイル・検索・データ交換

添付保管、全文検索、CSV等の入出力、API通信は共通技術として提供できます。一方、どのファイルをどの要求・テスト・リリースに関連づけるか、誰が出力できるかはAgiloomのドメインルールに従います。

### 3.4 監査・運用・データ保護

監査ログ、バックアップ、監視、保持期間管理は多くのシステムに共通します。ログに記録する操作、保持期間、復旧目標、アクセス制御は組織方針とAgiloomのリスクに基づき定めます。

## 4. 汎用サブドメインと他サブドメインの境界

| 領域         | 汎用サブドメインが担うこと     | Agiloomのコア／支援ドメインが担うこと            |
|--------------|--------------------------------|--------------------------------------------------|
| 認証・権限   | ログイン、ポリシー評価の仕組み | ロールの意味、プロジェクト参加区分、各業務の責任 |
| 通知         | 配信、再試行、配信状態         | 何をいつ誰に通知するか                           |
| 添付・文書   | ファイル保存、取得、暗号化     | 要求、テスト、レビューなどとの意味的な関連       |
| 監査         | 操作記録の保管・検索           | どの業務判断や管理操作を監査対象とするか         |
| 検索         | インデックス作成、クエリ実行   | 業務上の検索対象、フィルター、表示優先度         |
| API・Webhook | 接続、認証、再試行、形式変換   | Agiloomイベントと外部プロセスの意味づけ          |
| バックアップ | データ複製と復旧機能           | 対象データ、保持方針、復旧優先順位               |
| 請求・利用量 | 決済・計量の仕組み             | プランごとの機能境界や契約ルール                 |

## 5. 実装方針

1. **標準機能を優先する**：認証、メール、ストレージ、監視、決済などは、要件に合う既存サービスを評価する。
2. **コア業務との境界を保つ**：外部サービスのモデルをそのままAgiloomのドメインモデルにしない。
3. **交換可能性を確保する**：外部サービスのAPIやデータ形式をアダプターで隔離する。
4. **セキュリティと監査を組み込む**：権限、秘密情報、保持期間、操作履歴を初期設計に含める。
5. **運用責任を明確にする**：障害、同期失敗、復旧、データ削除の担当と手順を定める。
6. **商用条件を確認する**：費用、データ保存地域、可用性、サポート、利用制限を導入前に評価する。

## 6. 実装の推奨順序

| 段階 | 優先する汎用サブドメイン                       | 理由                                     |
|------|------------------------------------------------|------------------------------------------|
| 1    | 認証、アカウント、基本認可、テナント分離、監査 | 安全な利用と役割別アクセスの前提となる   |
| 2    | 通知、検索、ファイル保管、時刻処理             | 日常的なプロダクト業務の操作性を支える   |
| 3    | バックアップ・復元、可観測性、データ保持       | 安定運用とデータ保護を確保する           |
| 4    | API・Webhook、インポート・エクスポート、多言語 | 移行と外部連携、組織展開を支える         |
| 5    | 請求・利用量管理、機能フラグの高度化           | 商用提供モデルや拡大段階に応じて導入する |

## 7. 結論

Agiloomの汎用サブドメインは、認証・アカウント・権限基盤、組織分離、通知、ファイル、監査、検索、データ交換、バックアップ、運用監視、データ保持などです。これらはプロダクト開発業務を成立させる重要な基盤ですが、Agiloomの差別化の中心となるコアサブドメインとは責務を分けます。

標準サービスを活用して汎用機能の独自実装を抑え、Agiloom固有の価値判断、スクラム運営、バックログ、品質検証、成果適応に設計資源を集中することを推奨します。
