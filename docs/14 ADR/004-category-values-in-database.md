# カテゴリーは検索条件として使用し、DB に保持する

## ステータス

承認済み

## 日付

2026-11-16

## コンテキスト

値集合を持つ項目のうち、処理の分岐には使わず、一覧の絞り込みなどの**検索条件としてのみ使う**ものがある。これを「カテゴリー」と呼び、処理の分岐条件として使う「区分値」（ADR-003）と区別する。AG-01 では、成功指標の更新頻度、要望の出所、ステークホルダーの影響範囲・連絡方法などがカテゴリーにあたる想定である。

カテゴリーを区分値と同じ扱い（アプリ側 enum で値集合を固定し、DB に CHECK 制約を付ける）にすると、値の追加・変更のたびにコード変更とマイグレーションが必要になる。検索条件の選択肢は運用の中で調整したくなる性質のものであり、この扱いは過剰である。

## 決定

**カテゴリーは処理の分岐に使用せず、検索条件としてのみ使用するものと規定し、値は DB に保持する。**

- アプリの処理ロジックは、カテゴリーの値で分岐しない
- カテゴリーの値（コードと表示名）は DB に保持し、データとして管理する。値の追加・変更・表示名の変更はデータの変更として行い、コード変更や CHECK 制約のマイグレーションを要しない
- アプリはカテゴリーを検索条件の選択肢として DB から取得し、検索の絞り込みにのみ使う
- 項目が区分値かカテゴリーかの切り分けは「処理の分岐に使うか」で決める。分岐に使うものは区分値として ADR-003 に従う
- 各カテゴリーの初期値集合は項目辞書で定義する

## 結果

### ポジティブな結果

- カテゴリー値の追加・変更がデータの変更だけで済み、リリースなしに検索条件の選択肢を調整できる
- 区分値（分岐条件）との扱いの違いが明確になり、「この値で処理を分岐してよいか」の判断基準ができる

### ネガティブな結果

- 値集合がコードから見えず、DB を参照しないと分からない
- 表記ゆれや重複した値が入らないよう、データ側の管理（一意制約、登録時の統制）が必要になる

### 中立的な結果

- AG-01 の物理設計では、カテゴリー想定の項目（更新頻度・出所・影響範囲・連絡方法）の列に CHECK 制約を付けていないため、既存の DDL と整合している

## 代替案

### 代替案1：区分値と同様に enum と CHECK 制約で固定する

値集合の統制は効くが、検索専用の値にまでコード変更とマイグレーションを要する扱いは過剰なため採用しない。

### 代替案2：自由記述のテキストとして保持する

入力は柔軟になるが、表記ゆれによって検索条件として機能しなくなるため採用しない。
