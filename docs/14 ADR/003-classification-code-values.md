# 区分値はコード値で DB に保持し、処理の分岐条件として使用する

## ステータス

承認済み

## 日付

2026-11-16

## コンテキスト

AG-01 には、各エンティティの状態や Kano 評価の分類など、決まった値集合から値を取る項目がある。本 ADR の対象は、そのうち**処理の分岐条件として使用するもの**であり、これを「区分値」と呼ぶ（例：状態に応じた操作可否の判定、分類に応じた後続処理の切り替え）。

区分値を DB にどう保持するかで、次の問題が変わる：

- 日本語ラベルをそのまま保持すると、ラベルの文言変更や表記ゆれがそのままデータへ波及する
- 検索・集計・絞り込みの条件が、表示文言に引きずられる
- 表示言語やラベル体系を変えたくなったときに、データ移行が必要になる
- 区分値は処理の分岐条件として使うため、表示文言の変更に影響されず、コード上で型安全に扱える必要がある

なお、値集合を持つ項目でも、処理の分岐に使わず検索条件としてのみ使うものは「カテゴリー」として区別し、本 ADR の対象外とする（ADR-004）。

状態項目については、物理データモデルで既に「英語コード値で保持し、CHECK 制約で値集合を固定、日本語ラベルはアプリ側で対応付ける」方針を取っている（`2_RDRASpec/物理データモデル.md` 3 章のコード表）。この方針を区分値全般へ広げるかどうかが論点だった。

## 決定

**区分値は DB には英語コード値のみを保持し、処理の分岐条件として使用する。**

- DB の列にはコード値（半角英大文字＋アンダースコア）をセットし、CHECK 制約で値集合を固定する
- 日本語の表示ラベルは DB に持たない。アプリ側で対応付ける（enum にコード値と表示ラベルの対応を持たせ、enum を単一の情報源とする。ADR-002）
- 対象は状態・区分・分類など、処理の分岐条件として使う全項目とする。各項目の具体的な値集合は項目辞書で定義する
- 条件判定は enum の定数に対して行い、文字列リテラルや表示ラベルで判定しない
- 値集合の追加・変更は、表示だけの変更ではなく処理への影響を伴う変更として扱い、条件として使われている箇所の影響調査を行う
- 自由記述が本質の項目（名称・本文など）と、検索条件としてのみ使うカテゴリー（ADR-004）は対象外とする

## 結果

### ポジティブな結果

- 表示ラベルの変更がアプリ側の変更だけで済み、データ移行が不要になる
- 表記ゆれがデータに入らず、検索・集計・絞り込みが安定する
- 状態項目と方式が揃い、実装とレビューの判断基準が単純になる
- 分岐条件を enum で型安全に書ける。値の追加時には switch の網羅性チェックなどで、条件として使われている箇所を洗い出せる

### ネガティブな結果

- DB を直接参照したときにコード値の意味が分かりにくい（コード表・項目辞書の参照が必要）
- 値集合への値の追加は、アプリの enum 変更と CHECK 制約のマイグレーションの両方が必要になる

### 中立的な結果

- 状態項目は既にこの方式であり、既存の物理設計（DDL の CHECK 制約、コード表）との整合は取れている

## 代替案

### 代替案1：日本語ラベルをそのまま DB に保持する

DB を直接見たときの分かりやすさはあるが、ラベル変更・表記ゆれ・集計条件の文言依存といった問題がデータに残るため採用しない。特に、区分値を処理の分岐条件として使う以上、条件が表示文言に依存する形は避けるべきである。

### 代替案2：コードマスタテーブルを用意して FK で参照する

運用中に値を追加しやすい反面、値集合が小さく固定的な現時点では過剰である。また、区分値を処理条件として使う場合、値の追加はコード側の条件分岐の追加とセットになるため、マスタでデータだけ増やせる形はかえって不整合の元になる。検索条件専用のカテゴリーについては、逆にこの形（DB 保持）を採用する（ADR-004）。

## 見直しの条件

- 区分値のいずれかが処理条件として使われなくなり、検索条件専用になった場合（その項目はカテゴリーとして ADR-004 の扱いに移す）
- 多言語表示が必要になった場合（ラベル対応付けの置き場所を再検討する）
