# modulith-learning の開発ワークフローに takt の開発フローを移植し、Junie CLI の直接派遣で実行する

## ステータス

承認済み（2026-11-16 に実行方式を変更。本 ADR は同日の前決定「takt を使用し、モデルには Junie Lite を使用する」を置き換える）

## 日付

2026-11-16

## コンテキスト

Muse・Orca・takt の階層構成による開発環境を MacBook Air で試作している。構成の原則は「制御面は Orca 一本化」であり、製造層（実際にエージェントが作業する層）はプロジェクトごとに **Orca orchestration か takt 工場のどちらか**を選ぶことになっている。

本 ADR の前決定では、modulith-learning の製造層に takt を使用し、モデルには Junie Lite（takt の junie-lite プロバイダ経由の Junie CLI）を使うと決めた。しかし 2026-11-16 の試作で、以下の事実が判明した。

- **takt 0.74.0 ＋ junie-lite**：計画ステップは完走し計画の質も高かったが、ステップ遷移の判定フェーズ（タグ抽出と ai_judge）が Junie CLI の返す json-stream 形式の応答を解釈できず、計画が正しくても `rule_no_match` でワークフローが中止した。エンジンとプロバイダの応答形式の不整合である
- **takt 0.75.0**：junie-lite プロバイダ自体が廃止され、Junie を takt 経由で使う経路が閉じた
- **takt 0.75.0 ＋ OpenCode（LM Studio のローカル Qwen2.5-Coder-14B）**：1 回の LLM コールに約 5 分を要し、SSE タイムアウトも発生して実用速度にならない（MacBook Air のメモリ 16GB の制約）
- **takt 0.75.0 ＋ OpenCode 無料モデル**：計画は約 8 分で高品質に完走したが、判定フェーズ直前に無料枠の上限エラーで停止した。無料枠の非公開上限は、ワークフロー 1 本分（数十コール）を賄うには足りない
- **Junie CLI の直接実行**：認証・応答とも正常で、計画の質も高いことをプローブと Issue #493 の計画作成で確認した

つまり、壊れているのは「実行エンジンとしての takt 本体とプロバイダの組み合わせ」であり、「フロー（ステップ構成・遷移ルール・成果物の規律）」自体は健全である。両者は分離できる。

## 決定

**modulith-learning の開発ワークフロー（製造層）では takt 本体を使用せず、takt の開発フローを移植し、Junie CLI の直接派遣で実行する。**

- 移植対象は takt のビルトインワークフロー `development-core` のフロー：`plan`（読み取り専用で計画書を作成）→ `write_tests`（テスト先行）→ `implement` → `peer-review`（裁定・修正・検証）。必要に応じて `replan` に戻る
- 実行はステップごとの Junie CLI 起動（`junie --task <ステップの指示> --model junie-lite`）。成果物はファイル（計画書、コード、テスト）で受け渡す
- ステップ遷移の判定（フロー定義の自然言語ルールへの照合）は、Muse（参謀兼オペレーター）が担う。判定が曖昧な場合はオーナーに確認する。検証の実測（テスト実行）は Muse が行い、ワーカーの自己申告で済ませない
- 制御面は Orca 一本化の原則を維持する
- 手順の正本は共有リポジトリ `agent-guidelines` の workflow ガイドラインに置き、プロジェクトをまたいで共用する
- 本決定は開発プロセス側のものであり、アプリケーション自体の技術スタックには影響しない

## 結果

### ポジティブな結果

- 無料の範囲で実際に回る。Junie Lite の無料枠は、ステップ単位の派遣（1 Issue あたり数回の起動）では足りる。初回実行（Issue #493）では plan 約 4 分、テスト先行、実装まで一巡し、単体・統合テストの green を実測で確認した
- テスト先行・ピアレビュー・再計画というフローの規律は、takt の設計資産をそのまま活かせる
- 判定を Muse が担うため、プロバイダ側の応答形式の都合に左右されない

### ネガティブな結果

- ステップ間の受け渡しと判定が Muse の作業になるため、完全自動ではない（オペレーターの関与が前提の構成）
- Junie CLI の GitHub MCP は現状未接続（docker 用の env ファイル未設定）のため、Issue の内容は task 文で渡す必要がある
- Junie Lite の中身のモデルは JetBrains 側で予告なく差し替えられ得る。再現性はモデル固定のローカル実行より低い

### 中立的な結果

- takt 本体の将来の改善（Junie 系プロバイダの復活、判定フェーズの応答解釈の修正）があれば、エンジンとしての再採用を妨げない
- OpenCode ＋ LM Studio のローカル構成自体は残る（Orca 側・IntelliJ Air 側の選択肢として併存）
- takt の `manager`（実験的な会話 TUI＋daemon）は、実行が結局 takt のプロバイダ経由になるため同じ壁に当たり、今回は採用しない。Muse が担う判定・運用の役割は manager の想定する役割と重なっており、自動化の必要が高まれば再評価する

## 代替案

### 代替案1：takt ＋ 有料クラウドプロバイダ（Claude／Codex 等）を使う

動く可能性は高いが、「無料の範囲で試作する」という前提を外れるため今回は採用しない。

### 代替案2：takt に軽量な自作ワークフローを組む

判定フェーズの不整合はステップ数ではなく応答解釈の問題であり、0.75.0 では Junie 自体が使えないため不成立。

### 代替案3：製造層に Orca orchestration を使う

図の構成では対になる選択肢である。今回はフロー移植の方式で運用を検証することにしたため、modulith-learning では採用しない（将来の選択肢として残る）。

### 代替案4：どちらも使わず手作業でエージェントを操作する

再現性や引き継ぎの面で劣るため採用しない。

## 見直しの条件

- takt が Junie 系プロバイダを復活させる、または判定フェーズの応答解釈が修正された場合（エンジンとしての再採用を検討する）
- Junie Lite の無料枠や仕様が変わり、直接派遣が回らなくなった場合
- 扱うステップや Issue の数が増え、Muse の手作業による遷移管理がボトルネックになった場合（takt manager 等の自動化を再評価する）
