# 001: Spring Modulithアーキテクチャの採用

## ステータス

承認済み

## 日付

2024-01-28

## コンテキスト

当プロジェクトでは、複数のプロジェクトのScrum開発を管理するシステムを構築する必要があります。システムアーキテクチャとして、以下の要件を満たす必要があります：

- モジュール間の明確な境界を持つこと
- 疎結合と高凝集を実現すること
- 将来的にマイクロサービスへの移行パスを確保すること
- ドメイン駆動設計（DDD）の原則を適用すること
- 開発効率と保守性を高めること

現在、モノリシックアプローチとマイクロサービスアプローチの両方が検討されています。

## 決定

Spring Modulithフレームワークを使用したモジュラーモノリス（Modular Monolith）アーキテクチャを採用します。

具体的には：

- Spring Boot 3.4.5をベースとしたアプリケーションを構築
- Spring Modulithを使用してモジュール化を実現
- 各モジュールはクリーンアーキテクチャに基づく内部構造（ビジネス、ドメイン、インフラ、プレゼンテーション層）を持つ
- モジュール間の依存関係を明示的に定義し、循環依存を防止
- 共通コンポーネントは共有モジュールに配置

## 結果

### ポジティブな結果

- モジュール間の明確な境界により、コードの責任分離が実現される
- 単一のデプロイユニットとして管理できるため、運用が簡素化される
- Spring Modulithの検証機能により、モジュール間の依存関係違反を早期に検出できる
- 将来的に必要に応じて特定のモジュールをマイクロサービスとして分離できる柔軟性を持つ
- 開発チームが機能モジュールごとに分かれて並行開発できる

### ネガティブな結果

- モジュール間の境界を維持するための規律が必要
- 完全な独立スケーリングはマイクロサービスほど柔軟ではない
- モジュール間の統合テストが複雑になる可能性がある

### 中立的な結果

- チームはSpring Modulithの学習が必要
- モジュール構造の設計に初期投資が必要

## 代替案

### 代替案1: 従来のモノリシックアーキテクチャ

従来のモノリシックアプローチでは、アプリケーションを単一の大きなコードベースとして構築します。

選ばれなかった理由：

- モジュール間の境界が曖昧になりやすい
- コードベースが大きくなるにつれて保守が困難になる
- 将来的なマイクロサービスへの移行が困難

### 代替案2: マイクロサービスアーキテクチャ

個別のサービスとして各機能を実装し、APIを通じて通信するアプローチ。

選ばれなかった理由：

- 初期の複雑さとオーバーヘッドが高い
- 分散システムの課題（ネットワーク障害、一貫性など）に対処する必要がある
- 現段階ではビジネス要件が完全に明確になっていないため、適切なサービス境界を定義するのが難しい

## 見直しの条件

以下の条件が満たされた場合、この決定を再検討する必要があります：

- プロジェクトの規模が当初の想定を大幅に超え、モジュラーモノリスのアプローチでは対応できなくなった場合
- 特定のモジュールのスケーリング要件が他のモジュールと大きく異なり、独立したデプロイが必要になった場合
- Spring Modulithフレームワークのサポートが終了または大幅に変更された場合
- マイクロサービスアーキテクチャの採用コストが大幅に低下し、利点がリスクを上回るようになった場合
