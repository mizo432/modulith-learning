# 項目制約は値オブジェクトの定数として定義する

## ステータス

承認済み

## 日付

2026-11-16

## コンテキスト

AG-01（プロダクトディスカバリー）の物理設計で、項目ごとの制約（最大長・最小長・最小値・最大値・許容文字セット）を `2_RDRASpec/項目辞書.md` に定義した。

実装段階では、これらの制約値を次のような複数箇所で使う：

- ドメインの入力検証（値オブジェクトの生成時チェック、YAVI のバリデータ定義）
- JPA マッピング（`@Column(length = ...)`）
- API 定義（リクエスト DTO の検証、OpenAPI の `maxLength` 等）
- Flyway の DDL（VARCHAR の桁数）
- 境界値テスト

制約値を各所に数値リテラルで直書きすると、桁数を変更したときに修正漏れが起き、検証・DB・API の間で不整合になる。

## 決定

項目の制約値は、各項目に対応する**値オブジェクトの定数として定義し、コード上の単一の情報源とする**。数値を各所に直書きしない。

- 文字列項目： `MAX_LENGTH` / `MIN_LENGTH` を定数化する。文字セットは `Pattern` 定数として持つ
- 数値項目： `MIN_VALUE` / `MAX_VALUE` を定数化する
- 状態・区分項目： 値集合は enum で表現し、enum 自体を単一の情報源とする（コード値と表示ラベルの対応も enum に持たせる。DB への保持方法は ADR-003）
- 参照方法： `@Column(length = ProductVisionTitle.MAX_LENGTH)` のように、コンパイル時定数をアノテーションから参照する。境界値テストも定数を基準に組み立てる
- Flyway の DDL は SQL のため Java 定数を参照できない。DDL の桁数は項目辞書の値と一致させ、物理データモデルとの突き合わせで担保する
- 情報源の移行： 設計フェーズでは項目辞書が源泉。実装後は値オブジェクトの定数が源泉となり、項目辞書はその写しとして追随させる。値を変えるときは「辞書 → 定数 →（必要なら）DDL」の順に反映する

詳細は `2_RDRASpec/項目辞書.md` の 5 章「実装方針：値オブジェクトへの定数定義」。

## 結果

### ポジティブな結果

- 制約値の変更が定数1か所の修正で済み、検証・JPA・API・テストが自動的に追随する
- コンパイル時定数のため、アノテーション（`@Column`、`@Size`、`@Schema`）からも参照でき、型安全に扱える
- 境界値テストが定数基準になるため、値の変更でテストの前提が静かに腐ることがない

### ネガティブな結果

- 項目ごとに値オブジェクトを用意する手間が増える
- DDL（SQL）だけは定数を参照できず、辞書との二重管理が残る（突き合わせで担保する運用コスト）

### 中立的な結果

- 項目辞書と物理データモデルは、設計ドキュメントとして引き続き維持する

## 代替案

### 代替案1：制約値を各所に直書きする

最も単純だが、変更時の修正漏れと不整合の温床になるため採用しない。

### 代替案2：設定ファイルや DB のマスタで制約値を一元管理する

実行時に読み込む方式ではコンパイル時定数としてアノテーションから参照できず、検証のたびに外部参照が必要になる。制約値は業務ルールでありコードと一体で変更されるべきもののため、採用しない。

- バッチ一括取込など、値オブジェクトを介さない大量データ処理で定数参照の方式が障害になる場合
- コード生成（辞書からの自動生成など）を導入し、情報源の置き方が変わる場合
