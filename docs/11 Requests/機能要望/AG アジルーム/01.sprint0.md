スクラムプロジェクトにおけるスプリント0を支援する機能は、開発を始める前に、プロダクトの方向性・開発チーム・技術基盤・初期バックログを整えるための機能として設計できます。
ただし、Scrum Guide では「Sprint 0」は正式なスクラムイベントや特別なスプリントとして定義されていません。そのため、ツールでは通常の
Sprint と区別しつつ、初期開発の準備を管理する機能として扱うのがおすすめです。

1. スプリント0の支援機能

① プロダクトの方向性を整理する

- プロダクトビジョンの登録
- 解決したい課題・対象ユーザーの整理
- ステークホルダーの登録
- 成功指標（KPI・成果指標）の設定
- プロダクトの対象範囲と対象外の整理

② 初期バックログを作成する

- ユーザージャーニーの作成
- Epic・Feature・User Story の候補抽出
- 受け入れ条件の記述
- ストーリー間の依存関係の整理
- 優先順位・価値・見積もりの登録

③ 技術基盤と開発環境を整える

- システム構成・アーキテクチャ方針
- 開発環境・CI/CD・テスト環境の準備状況
- リポジトリ・ブランチ戦略
- DB・API・認証などの技術的な前提
- 技術的リスク・技術検証タスクの管理

④ チームと作業ルールを整える

- チームメンバー・役割・参加可能時間
- Definition of Done（完成の定義）
- コーディング規約・レビュー方針
- Scrumイベントの予定
- 意思決定方法・連絡方法

⑤ 初回スプリントの準備状況を確認する

- 初回 Sprint Goal の候補
- 優先バックログの準備状況
- 開発・テスト・デプロイの実行可能性
- 未解決の前提・リスク・依存関係
- 準備項目の担当者・期限・完了条件

3. ドメインモデル案
   既存の Product、Epic、Feature、UserStory、Sprint などを再利用し、スプリント0専用のモデルは準備作業の管理に絞ります。
   @startuml
   hide methods
   skinparam classAttributeIconSize 0

class Product {
productId
name
vision
}

class ProductPreparation {
preparationId
productId
status
startedAt
completedAt
}

class PreparationWorkItem {
workItemId
preparationId
category
title
status
dueDate
}

class PreparationDecision {
decisionId
workItemId
decision
reason
decidedAt
}

class PreparationRisk {
riskId
preparationId
description
impact
status
}

class UserStory {
userStoryId
title
priority
}

class Sprint {
sprintId
sprintGoal
startDate
endDate
}

Product "1" -- "0.. *" ProductPreparation
ProductPreparation "1" *-- "0..*" PreparationWorkItem
PreparationWorkItem "1" -- "0..*" PreparationDecision
ProductPreparation "1" *-- "0..*" PreparationRisk
ProductPreparation ..> UserStory : 初期バックログを準備
ProductPreparation ..> Sprint : 初回Sprintの計画へ
@enduml

モデル設計上のポイント

- ProductPreparation は、プロダクトの立ち上げ準備を管理します。準備期間を何度か設ける場合にも対応できます。
- PreparationWorkItem は、環境構築、規約策定、バックログ整備などを共通形式で管理します。
- PreparationDecision は、採用した技術や合意事項など、後から確認したい意思決定を記録します。
- PreparationRisk は、未解決の技術的・業務的リスクを管理します。
- 初期バックログは独自に複製せず、既存の UserStory などへつなぎます。

4. ユースケース
   ユースケース 内容
   CreateProductPreparation プロダクトの準備計画を作成
   DefineProductVision ビジョン・成果指標を定義
   CreateInitialBacklog 初期バックログを作成
   RecordPreparationWorkItem 準備項目を登録
   RecordPreparationDecision 技術・業務上の決定を記録
   AssessPreparationRisk リスクを評価・更新
   EvaluateInitialSprintReadiness 初回 Sprint の準備状況を確認
   CompleteProductPreparation 準備作業を終了し、通常の開発へ移行

EvaluateInitialSprintReadiness
は、単純にすべての項目が完了したかだけで判定しない設計が重要です。未完了でも初回スプリント内で対応できる項目と、開始前に解消すべき項目をチームが判断できるようにします。

5. CQRS の Query Model
   既存のアーキテクチャ方針に合わせ、画面用の Query Model を用意します。

- ProductPreparationDashboardQuery — 全体の準備状況
- PreparationWorkItemListQuery — 未完了項目・期限・担当者
- InitialBacklogReadinessQuery — Story の優先順位・受け入れ条件・依存関係
- TechnicalRiskSummaryQuery — 技術的リスクと未解決事項
- InitialSprintReadinessQuery — 初回 Sprint の候補と不足情報
- PreparationDecisionHistoryQuery — 過去の意思決定
  これらは読み取り専用 DTO として実装し、ドメインモデルやアプリケーションサービスを Spring
  に依存させない構成にできます。

6. MVP で優先する機能
   最初から包括的なプロジェクト管理機能を作るより、次の順序が現実的です。
1. 準備項目の管理 — 担当者、期限、状態、完了条件
2. プロダクト定義 — ビジョン、対象範囲、成果指標
3. 初期バックログ作成 — ユーザーストーリーマッピングとの連携
4. 技術基盤・リスク管理
5. 初回 Sprint の準備状況ダッシュボード
6. 意思決定履歴・準備状況のスナップショット
   特に、すでに検討しているユーザーストーリーマッピングや要件モデル作成機能と連携させると、スプリント0で作った成果物を、そのまま初回
   Sprint Planning に引き継げます。
   おすすめの設計方針は、スプリント0を特別な Sprint 型として実装するのではなく、ProductPreparation
   という独立した準備プロセスとしてモデル化することです。 これなら Scrum の通常の Sprint
   と混同せず、プロジェクト立ち上げの進捗や意思決定を追跡できます。
