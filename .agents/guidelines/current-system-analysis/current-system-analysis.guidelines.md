# 現行システム分析ガイドライン (Current System Analysis Guidelines)

本ガイドラインは、現行システムの分析手順と分析方法を定義し、一貫性のある分析結果を得るための指針を提供します。

現行システム分析は、システム更改や新システム設計の基礎資料を作成するために不可欠な工程です。本ガイドラインに従うことで、分析の抜け漏れを防ぎ、再現性のある分析プロセスを実現します。

---

## 1. 目的と範囲の明確化

### 1.1 目的の定義

現行システムの分析がなぜ必要かを明確にします。

- **性能改善**: 現行システムのパフォーマンス問題を特定し、改善策を提案する
- **新システム設計の基礎資料**: 新システム開発のための現状把握を行う
- **資産棚卸**: 既存システム資産の把握と評価を行う
- **保守効率化**: 保守プロセスの効率化と次期システムの企画・要件定義を行う

**必須事項**: 分析開始前に、分析目的を文書化し、ステークホルダーと合意を取ります。

### 1.2 分析範囲の特定

分析対象とするシステム、サブシステム、モジュール、コンポーネントを決定します。

- 分析対象システムのリストを作成する
- 対象外とする範囲を明確に境界設定する
- 依存関係のある外部システムを特定する

**必須事項**: 分析範囲を越える調査は行わず、スコープクリープを防ぎます。

---

## 2. データ収集

### 2.1 ドキュメントの収集

既存のドキュメントを体系的に収集します。

| 収集対象 | 例 |
|----------|-----|
| システム設計書 | 要件定義書、詳細設計書、アーキテクチャ図 |
| ユーザーマニュアル | 操作マニュアル、画面説明書 |
| 運用ガイド | 運用マニュアル、保守マニュアル |
| 技術資料 | API仕様書、データベース設計書 |
| 過去の分析資料 | 障害報告書、改善提案書 |

**必須事項**: 収集したドキュメントのバージョンと日付を記録し、最新性を確認します。

### 2.2 関連者インタビュー

システム開発者、運用担当者、ユーザーなど関係者へのインタビューを通じて、システムの使用状況や問題点を確認します。

- **インタビュー対象者の選定**: 役割ごとに代表者を選定する
- **インタビュー項目の準備**: 標準的な質問リストを事前に準備する
- **記録の残し方**: インタビュー結果を文書化し、関係者に確認を得る

**必須事項**: インタビュー結果は主観的な情報であるため、複数の情報源でクロスチェックします。

### 2.3 システムモニタリング

システムのログやパフォーマンスデータを収集します。

- **ログ収集**: エラーログ、アクセスログ、操作ログを収集する
- **パフォーマンスデータ**: CPU使用率、メモリ使用率、ディスクI/Oを計測する
- **ネットワーク監視**: ネットワークトラフィック、レスポンスタイムを計測する

**必須事項**: モニタリング期間は、通常の業務パターンをカバーする期間を設定します。

---

## 3. 現状分析

### 3.1 システム構成の把握

ハードウェア、ソフトウェア、ネットワーク構成を詳細に文書化します。

- **ハードウェア構成**: サーバー、ストレージ、ネットワーク機器の種類・配置・役割
- **ソフトウェア構成**: OS、ミドルウェア、アプリケーションの種類・バージョン・配置
- **ネットワーク構成**: ネットワークトポロジー、ファイアウォール設定、通信プロトコル

**出力**: システム構成図（ネットワーク図、サーバー構成図など）

### 3.2 機能分析

システムの主要機能と各モジュールの役割を明確にします。

- **機能リストの作成**: 主要機能を一覧化し、簡潔な説明を付与する
- **モジュール分解**: 各モジュールの役割と依存関係を明確にする
- **機能階層の整理**: 上位機能から下位機能への階層構造を図示する

**出力**: 機能一覧表、モジュール構成図

### 3.3 データフローの分析

データの流れを図示し、データの生成、処理、保存、出力の流れを確認します。

- **データフロー図の作成**: 外部エンティティ、プロセス、データストア、データフローを図示する
- **データ辞書の作成**: 項目名、データ型、制約条件などを定義する
- **データライフサイクルの把握**: データの作成から廃棄までの流れを追跡する

**出力**: データフロー図、データ辞書

### 3.4 パフォーマンス分析

現行システムのパフォーマンスを評価し、レスポンスタイムやスループット、負荷の分布を解析します。

- **レスポンスタイム**: 主要トランザクションの応答時間を計測する
- **スループット**: 単位時間あたりの処理件数を計測する
- **キャパシティ**: リソース使用率とボトルネックを特定する
- **負荷分布**: 時間帯別・曜日別の負荷パターンを分析する

**出力**: パフォーマンス測定結果表、ボトルネック分析レポート

### 3.5 問題点の特定

技術的な欠陥、性能上のボトルネック、業務上の不満点などを整理します。

- **技術的問題**: 技術的負債、アーキテクチャ上の問題、セキュリティリスク
- **性能問題**: レスポンスタイムの遅延、スループットの不足、リソース枯渇
- **業務問題**: 業務効率の低下、ユーザーの不満、運用上の課題

**必須事項**: 各問題点について、影響度と発生頻度を評価します。

---

## 4. 評価と改善提案

### 4.1 問題点の評価

発見された問題点の影響度と優先度を評価します。

| 評価項目 | 評価基準 |
|----------|----------|
| 影響度 | 業務への影響範囲、ユーザー数、経済的損失 |
| 緊急度 | 即時対応が必要か、延期可能か |
| 解決難易度 | 技術的複雑さ、必要なリソース、期間 |

**出力**: 問題点評価マトリックス（影響度×緊急度）

### 4.2 改善提案の作成

各問題に対する具体的な改善策を提案します。

- **改善策の具体化**: 何を、どのように、いつ改善するかを明確にする
- **代替案の検討**: 複数の実現手段を検討し、比較評価する
- **コスト・ベネフィット分析**: 改善コストと期待効果を試算する

**出力**: 改善提案書

---

## 5. ドキュメント化

### 5.1 分析結果の文書化

全ての分析結果を一つのレポートとしてまとめます。

**出力フォーマット**: [現行システム分析ドキュメントテンプレート](./templates/01%20テンプレート%20現行システム分析ドキュメント.md)に従って文書化します。

**必須事項**: 分析結果は、関係者が理解できるレベルで記述し、専門用語は用語集で定義します。

### 5.2 改善計画の策定

改善提案に基づき、実施計画、スケジュール、必要なリソースを明確にします。

- **実施計画**: フェーズごとの実施内容とマイルストーンを定義する
- **スケジュール**: 各フェーズの開始・終了日と依存関係を明確にする
- **リソース計画**: 必要な人員、予算、ツールを特定する

**出力**: 改善計画書

---

## 6. ステークホルダーへの報告

### 6.1 結果の共有

分析結果と改善提案をステークホルダーに対して報告し、フィードバックを受け取ります。

- **報告会の実施**: 分析結果を視覚的に提示し、質疑応答を行う
- **フィードバックの収集**: 関係者からの意見・要望を記録する
- **合意形成**: 改善方向性についてステークホルダーと合意を取る

**必須事項**: 報告資料は、技術者向けと経営者向けの2レベルで準備します。

### 6.2 フィードバックの反映

受け取ったフィードバックを元に、必要に応じて分析結果や改善計画を修正します。

- **フィードバックの分類**: 修正が必要か、参考意見かを分類する
- **修正の反映**: 分析結果や改善計画に修正を反映する
- **変更履歴の記録**: 修正内容と理由を記録する

---

## 7. 次のステップの準備

### 7.1 改善施策の実行準備

提案された改善策を実行するための準備を行います。

- **プロジェクトチームの編成**: 役割と責任を明確にする
- **リソースの確保**: 必要な人員・予算・ツールを確保する
- **リスク管理計画の策定**: 想定リスクと対応策を定義する

### 7.2 継続的なモニタリング

改善施策の効果を評価するために、継続的なモニタリング体制を整備します。

- **KPIの定義**: 改善効果を測定する指標を定義する
- **モニタリング頻度**: 定期的な測定スケジュールを設定する
- **レポート体制**: 測定結果の報告フローを確立する

## 分析手順のチェックリスト

分析プロセスの抜け漏れを防ぐために、以下のチェックリストを使用します。

### フェーズ1: 目的と範囲の明確化
- [ ] 分析目的を文書化し、ステークホルダーと合意した
- [ ] 分析対象範囲を明確に定義した
- [ ] 対象外範囲を境界設定した

### フェーズ2: データ収集
- [ ] 既存ドキュメントを収集・整理した
- [ ] 関係者インタビューを実施し、結果を記録した
- [ ] システムモニタリングデータを収集した

### フェーズ3: 現状分析
- [ ] システム構成を文書化した
- [ ] 機能分析を行い、モジュール役割を明確にした
- [ ] データフローを図示した
- [ ] パフォーマンスを測定・分析した
- [ ] 問題点を特定し、影響度を評価した

### フェーズ4: 評価と改善提案
- [ ] 問題点を影響度×緊急度で評価した
- [ ] 具体的な改善策を提案した
- [ ] コスト・ベネフィットを試算した

### フェーズ5: ドキュメント化
- [ ] 分析結果をテンプレートに従って文書化した
- [ ] 改善計画を策定した

### フェーズ6: ステークホルダーへの報告
- [ ] 分析結果をステークホルダーに報告した
- [ ] フィードバックを収集・反映した

### フェーズ7: 次のステップの準備
- [ ] 改善施策の実行準備を行った
- [ ] 継続的なモニタリング体制を整備した
