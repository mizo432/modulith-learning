# ADR ガイドライン

## 概要

アーキテクチャ決定記録（Architecture Decision
Records、ADR）は、ソフトウェアプロジェクトにおける重要なアーキテクチャ上の決定を文書化するための軽量な方法です。本ガイドラインでは、ADRの目的、構造、作成手順、運用ルールについて定義します。

ADR の記載ルールがレビュー用プロンプトや過去の指摘に分散すると、書き手はレビューを受けるまでルールへ到達できません。本規範に正典を集約し、書き手とレビュー側が同じ基準を参照できる状態にします。

## 目的

ADRを使用する主な目的は以下の通りです：

1. **決定の透明性**: なぜ特定のアーキテクチャ選択がなされたのかを明確にする
2. **知識の共有**: チームメンバー間で決定事項とその理由を共有する
3. **将来の参照**: 後日、決定の背景を思い出す必要がある場合の参照資料となる
4. **オンボーディング**: 新しいチームメンバーが過去の決定を理解するのを助ける

## 基本原則

- **フォーマットを当てはめるだけでは不十分**: ADRに何を残し、何を残さないかの基準を定めることが重要
- **人間が読み返せる状態を維持**: ADRは長期間に渡って読み返される文書であり、意思決定の妥当性を確認する拠り所となる
- **基準を共有する**: 書き手とレビュワーが同じ場所から基準を参照できるようにする
- **実証的に更新する**: 実際のレビューで繰り返される指摘をもとに、基準を適切なタイミングで更新する

## ADRの構造

各ADRは以下の構造に従います：

1. **タイトル**: 決定の簡潔な説明
2. **ステータス**: 提案中、承認済み、廃止、置換など
3. **日付**: 決定が行われた日付
4. **コンテキスト**: 決定が必要となった背景や状況
5. **決定**: 実際に選択された選択肢とその詳細
6. **結果**: この決定から予想される結果（ポジティブ、ネガティブ、中立）
7. **代替案**: 検討されたが選択されなかった他の選択肢
8. **関連**: 関連する他のADRや文書へのリンク
9. **見直しの条件**: 決定から再度判断が必要となる条件

## ADRの作成手順

新しいアーキテクチャ決定を記録する際は、以下の手順に従ってください：

1. `template/template.md` をコピーして新しいADRファイルを作成する
2. ADRに連番を付け、適切なタイトルを付ける（例：`001-database-selection.md`）
3. テンプレートに従って内容を記入する
4. チームでレビューし、合意を得る
5. 必要に応じて関連するADRを更新する

## ADRの運用ルール

### ステータスの管理

ADRのステータスは以下の4種類から選択します：

- **提案中**: 検討中であり、まだ合意が得られていない状態
- **承認済み**: チームで合意が得られ、採用が決定された状態
- **廃止**: 何らかの理由で無効となった状態
- **置換**: 別のADRによって置き換えられた状態

### 連番の付け方

- ADRは3桁の連番で管理する（`001`、`002`、...）
- ファイル名は `ADR-{連番}_{要件コード}_{タイトル}_{対応フラグ}.md` の形式とする（例：
  `ADR-0001_A-04_災害対策免災_対応しない.md`）
- 要件コードは以下のカテゴリから選択する：
    - `A`: 稼働時間・災害対策系
    - `B`: 業務量・応答時間・性能系
    - `C`: 運用管理体制・監視・バックアップ系
    - `D`: 移行スケジュール系
    - `E`: 認証認可・セキュリティ系
    - `F`: 設置環境・法制度・制約系（技術選定は `F-99` を使用）
- 対応フラグは「対応する」または「対応しない」から選択する
- 連番は作成順に割り当て、削除やスキップは行わない

### コンテキストの記述

コンテキストセクションでは、以下の情報を含めることを推奨します：

- 問題点や課題の明確な記述
- 現在の環境や制約条件
- 決定の背景となった出来事や要件

### 決定の記述

決定セクションでは、以下の情報を含めることを推奨します：

- 選択された選択肢の明確な記述
- 具体的な実装方法やアプローチ
- 決定の根拠となる理由

### 結果の記述

結果セクションでは、以下の3つの観点から記述します：

- **ポジティブな結果**: 期待される良い影響
- **ネガティブな結果**: 懸念される悪い影響
- **中立的な結果**: 影響が中立な事項

### 代替案の記述

代替案セクションでは、検討されたが選択されなかった選択肢を記述します。各代替案について、選ばれなかった理由を明確に説明します。

### 関連の記述

関連する他のADRや文書へのリンクを記述します。関連するADRがまだ存在しない場合は、「（未作成）」と明記します。

### 見直しの条件

決定から再度判断が必要となる条件を具体的に記述します。例えば：

- 特定の技術の成熟度が上がった場合
- ビジネス要件が変わった場合
- パフォーマンス問題が発生した場合
- フレームワークのサポートが終了した場合

## ADRの保管場所

- ADRは `docs/14 ADR/` ディレクトリに保管します
- ADRガイドライン関連ファイルは `.agents/guidelines/adr/` ディレクトリに配置します
- テンプレートは `.agents/guidelines/adr/template/template.md` に配置します
- 完成したADRは連番付きで `docs/14 ADR/` ディレクトリに配置します

## ADR記載規約

過去のレビューコメントから抽出した規約を、性質ごとにA〜Gのカテゴリに分類し、IDと強度（MUST/SHOULD）を付与します。

- **MUST**: 満たさなければならない。違反時はマージ不可。
- **SHOULD**: 原則として満たす。外す場合は理由を説明できる状態にする。

### カテゴリ一覧

| カテゴリ | 扱う内容                                                                                                                                           |
|----------|----------------------------------------------------------------------------------------------------------------------------------------------------|
| A        | 何を参照し、どこに書くか。本文にはチケット番号やADR以外へのリンクを書かず、外部への参照はReferences節に、関連ADRや置き換え関係は専用の節にまとめる |
| B        | 参照先をどう指すか。行番号や章番号だけで指さず、他ADRのDecisionは項番号と章題で指すなど、加筆やファイル移動の後も参照先が一意に定まる書き方にする  |
| C        | 事実と根拠。前提事実を一次資料と照合し、出典を示し、ADR単体で読めるようにする                                                                      |
| D        | 意思決定として書くこと・書かないことの線引き。移行計画や実装の詳細を抱え込まず、適用範囲・例外の失効条件・影響を過不足なく書く                     |
| E        | ADR同士・一覧との整合。ステータスの変化やアーカイブに合わせて、一覧や参照元を追従させる                                                            |
| F        | 表記と語彙。用語・タイトル・リンクテキストを揃え、最終更新日のような陳腐化しやすい情報を本文に置かない                                             |
| G        | Accepted化の前の点検。セキュリティ系ADRの完全性を確かめ、未確定事項を残したままAcceptedにしない                                                    |

### 規約リスト

#### カテゴリA：何を参照し、どこに書くか

| ID  | 強度 | 規約                                        |
|-----|------|---------------------------------------------|
| A-1 | MUST | 本文にチケット番号・PR/Issue 番号を書かない |
| A-2 | MUST | 外部への参照はReferences節にまとめる        |
| A-3 | MUST | 関連ADRや置き換え関係は専用の節にまとめる   |

#### カテゴリB：参照先をどう指すか

| ID  | 強度   | 規約                                                                |
|-----|--------|---------------------------------------------------------------------|
| B-1 | MUST   | 物理行番号で参照しない                                              |
| B-2 | MUST   | 他ADRのDecision参照は「ADR-NNN の Decision 項 N（章題）」形式で書く |
| B-3 | SHOULD | 参照先が加筆やファイル移動後も一意に定まる書き方にする              |

#### カテゴリC：事実と根拠

| ID  | 強度 | 規約                                                                      |
|-----|------|---------------------------------------------------------------------------|
| C-1 | MUST | 事実を実コード・一次資料と照合する                                        |
| C-2 | MUST | 出典と確認日を明記する                                                    |
| C-3 | MUST | ADR単体で読めるようにする。会議内容などの再検証できない情報源に依存しない |

#### カテゴリD：意思決定として書くこと・書かないこと

| ID  | 強度   | 規約                                                     |
|-----|--------|----------------------------------------------------------|
| D-1 | MUST   | 移行計画・進捗・タスク表を書かない                       |
| D-2 | MUST   | Decisionを実装の詳細まで抱え込ませない                   |
| D-3 | SHOULD | 適用範囲と「決定しないこと」を明記し、委譲先を名指しする |
| D-4 | SHOULD | Decisionを実装の自由度を奪わない粒度にする               |

**D-4の判定問い**: 決定した実現方式を別方式へ置き換えたとき、ADR本文を書き換える必要があるか。必要なら、その記述はADRではなくDR（Decision
Record）または仕様書に属する。

**ADRから外すべき具体物の例**（PRのdescriptionや仕様書へ移送）:

- 検出アルゴリズム
- テスト方式
- 関数・型の構造
- 個別対象への権限割り当て
- 環境変数名・フォーマット
- メソッド名・クラス名

#### カテゴリE：ADR同士・一覧との整合

| ID  | 強度 | 規約                                       |
|-----|------|--------------------------------------------|
| E-1 | MUST | ステータス変化時に一覧や参照元を追従させる |
| E-2 | MUST | アーカイブ時に参照関係を整理する           |

#### カテゴリF：表記と語彙

| ID  | 強度   | 規約                                                 |
|-----|--------|------------------------------------------------------|
| F-1 | MUST   | 用語・タイトル・リンクテキストを揃える               |
| F-2 | SHOULD | 最終更新日のような陳腐化しやすい情報を本文に置かない |

#### カテゴリG：Accepted化の前の点検

| ID  | 強度 | 規約                                   |
|-----|------|----------------------------------------|
| G-1 | MUST | セキュリティ系ADRの完全性を確認する    |
| G-2 | MUST | 未確定事項を残したままAcceptedにしない |

### OK/NG例

各規約にはOK/NG例を添えます。例はすべて作例（架空の例）で書き、現存するADRを引用しません。

**D-1: 移行計画・進捗・タスク表を書かない**

- **NG**（完了すれば陳腐化する進捗を本文に持つ）:
    - [x] 試験環境へ導入した
    - [ ] 来週までに本番へ反映する
- **OK**: 移行期間中は旧方式と新方式の両方を読み取れる必要がある。

**D-4: Decisionを実装の自由度を奪わない粒度にする**

- **NG**（実装の詳細まで記載）:
    - 判定は送信の出口である `MailAdapter.send()` に置く。環境変数 `XXX`
      （カンマ区切り）が与えられていれば、その一覧に一致する宛先のみへ送信する。
- **OK**（方針のみ記載）:
    - ステージング環境では、許可された宛先以外へメールを送らない。設定漏れのときは送信しない側に倒す。
