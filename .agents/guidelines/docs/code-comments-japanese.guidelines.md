# プログラムコードコメント共通ルール - 日本語として読めるかチェックする (Code Comments Japanese Readability Check Guidelines)

本ガイドラインは、すべてのプログラムコードのコメント作成時に適用する共通ルールです。コードコメントが日本語として自然に読めることを確認します。

---

## 1. 適用範囲

本ルールは、以下のすべてのコードコメント作成時に適用されます。

- **KDoc (JavaDoc)**: クラス、メソッド、フィールドの公開ドキュメントコメント
- **行コメント (`//`)**: 処理の意図や理由を説明する単一行コメント
- **ブロックコメント (`/* */`)**: 複数行にわたる説明コメント
- **TODO/FIXME コメント**: 今後の作業や修正が必要な箇所を示すコメント
- **テストコードのコメント**: テストの意図や前提条件を説明するコメント

適用対象ファイル:
- `backend/` 配下のすべての Java ファイル
- `frontend/` 配下のすべての TypeScript/JavaScript ファイル
- その他、プロジェクト内のすべてのソースコードファイル

---

## 2. チェック項目

コードコメントを作成する際、以下の項目を確認してください。

| チェック項目 | 確認内容 | 判定基準 |
|:---|:---|:---|
| **KDoc の日本語化** | クラス・メソッド・フィールドの KDoc が日本語で書かれているか | 日本語として自然な説明か、機械翻訳のような不自然な表現がないか |
| **行コメントの日本語化** | 行コメントが日本語で書かれているか | コメントの内容が日本語として理解できるか |
| **ブロックコメントの日本語化** | ブロックコメントが日本語で書かれているか | 複数行にわたる説明が日本語として読めるか |
| **TODO/FIXME の日本語化** | TODO/FIXME コメントが日本語で書かれているか | 今後の作業内容が日本語で記載されているか |
| **テストコメントの日本語化** | テストコードのコメントが日本語で書かれているか | テストの意図が日本語として理解できるか |
| **技術用語の扱い** | 技術用語は適切に扱われているか | API名、クラス名、メソッド名などは原文のまま可。それ以外は日本語訳すること |

---

## 3. 注意事項

### 3.1 技術用語

- API名、クラス名、メソッド名、変数名、パッケージ名などは原文（英語）のまま使用してよい
- 例: `Spring Boot`, `REST API`, `EntityName`, `findById()`

### 3.2 固有名詞

- プロダクト名、サービス名、フレームワーク名などは原文のまま使用してよい
- 例: `Spring Cloud Gateway`, `PlantUML`, `Gradle`

### 3.3 コード内の識別子

- コード内の識別子（変数名、メソッド名、クラス名など）は、プロジェクトの命名規則に従い、英語で記述する
- コメント内で識別子を参照する場合は、原文のまま記載する

### 3.4 自然な日本語

- 機械翻訳のような不自然な表現を避け、自然な日本語で記載すること
- 例:
  - ❌ `// このメソッドはユーザーがデータを取得することを可能にする`
  - ✅ `// ユーザーがデータを取得できるようにする`

### 3.5 漢字とひらがなのバランス

- 読みやすいバランスで表記すること
- 例:
  - 「取得する」（✅）
  - 「登録する」（✅）
  - 「登録する」（❌ 誤字）

### 3.6 助詞の正しい使用

- 助詞の使い分けを正しく行うこと
- 例:
  - 「について」（✅）
  - 「对于」（❌ 中国語混入）

### 3.7 句読点の統一

- 句読点は日本語の「、」（読点）と「。」（句号）を使用すること
- 英語のコンマ（`,`）やピリオド（`.`）は使用しない

## 4. KDoc (JavaDoc) の書き方

### 4.1 基本ルール

- KDoc は日本語で記載する
- `@param`, `@return`, `@throws` などのタグの説明も日本語で記載する
- 例:

```java
/**
 * 指定されたIDでエンティティを検索する。
 * 存在しない場合は NotFoundBusinessException をスローする。
 *
 * @param id 検索対象のエンティティID
 * @return 検索結果のエンティティ
 * @throws NotFoundBusinessException 指定されたIDのエンティティが見つからない場合
 */
public Entity findById(SnowflakeID id) {
    // 実装
}
```

### 4.2 禁止事項

- 英語の KDoc をそのまま残さない
- 機械翻訳のような不自然な表現を使用しない
- 例:
  - ❌ `/** Find the entity by the given ID. */`
  - ✅ `/** 指定されたIDでエンティティを検索する。 */`

---

## 5. 行コメントの書き方

### 5.1 基本ルール

- 行コメントは日本語で記載する
- 処理の「何」ではなく「なぜ」を説明する
- 例:

```java
// 在庫数が不足している場合は、予約処理をスキップする
if (stockQuantity < reservedQuantity) {
    continue;
}
```

### 5.2 禁止事項

- 英語のコメントをそのまま残さない
- 例:
  - ❌ `// Skip if stock is insufficient`
  - ✅ `// 在庫数が不足している場合はスキップする`

---

## 6. ブロックコメントの書き方

### 6.1 基本ルール

- ブロックコメントは日本語で記載する
- 複数行にわたる説明が必要な場合のみ使用する
- 例:

```java
/*
 * 以下の処理では、トランザクションの整合性を確保するために、
 * 一度に複数のエンティティを更新する。
 * 途中で例外が発生した場合は、すべての変更がロールバックされる。
 */
transactionTemplate.execute(status -> {
    // 処理
});
```

---

## 7. TODO/FIXME コメントの書き方

### 7.1 基本ルール

- TODO/FIXME コメントは日本語で記載する
- 具体的な作業内容と、可能な限り期限や担当者を明記する
- 例:

```java
// TODO: 2026-11-15 まで - 大量データ時のパフォーマンス最適化が必要
// FIXME: 特定条件下で NullPointerException が発生する可能性あり
```

### 7.2 禁止事項

- 英語の TODO/FIXME コメントをそのまま残さない
- 例:
  - ❌ `// TODO: Optimize performance for large datasets`
  - ✅ `// TODO: 大量データ時のパフォーマンスを最適化する`

---

## 8. テストコードのコメントの書き方

### 8.1 基本ルール

- テストコードのコメントは日本語で記載する
- `@DisplayName` は日本語で記載する（既存ルールに従う）
- テストの前提条件や期待値の説明を日本語で記載する
- 例:

```java
@DisplayName("入力値がnullの場合、例外をスローする")
void shouldThrowExceptionWhenInputIsNull() {
    // 入力値がnullの場合、IllegalArgumentException がスローされることを確認
    assertThatThrownBy(() -> targetMethod(null))
            .isInstanceOf(IllegalArgumentException.class);
}
```

---

## 9. 既存の英語コメントの扱い

### 9.1 新規コード

- 新規に作成するコードでは、すべてのコメントを日本語で記載する

### 9.2 既存コードの修正

- 既存の英語コメントを修正・追加する場合は、日本語に翻訳する
- 大規模なリファクタリング時に、既存の英語コメントを日本語に翻訳することを推奨

---

## 10. チェックリスト

コードコメント作成時、以下のチェックリストで確認してください。

- [ ] KDoc が日本語で書かれている
- [ ] 行コメントが日本語で書かれている
- [ ] ブロックコメントが日本語で書かれている
- [ ] TODO/FIXME コメントが日本語で書かれている
- [ ] テストコードのコメントが日本語で書かれている
- [ ] 技術用語は適切に扱われている
- [ ] 機械翻訳のような不自然な表現がない
- [ ] 助詞の使い分けが正しい
- [ ] 句読点が統一されている
