# テストコードコメント共通ルール - 日本語として読めるかチェックする (Test Code Comments Japanese Readability Check Guidelines)

本ガイドラインは、すべてのテストコードのコメント作成時に適用する共通ルールです。テストコードのコメントが日本語として自然に読めることを確認します。

---

## 1. 適用範囲

本ルールは、以下のすべてのテストコードのコメント作成時に適用されます。

- **テストクラスのコメント**: テストクラスの目的や範囲を説明するコメント
- **@DisplayName**: テストケースの名称（日本語で記載）
- **@Nested クラスのコメント**: テストのグループ化の意図を説明するコメント
- **テストメソッド内の行コメント**: テストの前提条件、期待値、検証内容を説明するコメント
- **テスト用のヘルパーメソッドのコメント**: テスト支援メソッドの目的を説明するコメント
- **テストデータのコメント**: テストで使用するデータの意図や特徴を説明するコメント

適用対象ファイル:
- `backend/` 配下のすべてのテスト Java ファイル（`*Test.java`, `*Tests.java`）
- `frontend/` 配下のすべてのテストファイル
- その他、プロジェクト内のすべてのテストコードファイル

---

## 2. チェック項目

テストコードのコメントを作成する際、以下の項目を確認してください。

| チェック項目 | 確認内容 | 判定基準 |
|:---|:---|:---|
| **@DisplayName の日本語化** | @DisplayName が日本語で書かれているか | テストの意図が日本語として明確に理解できるか |
| **テストクラスコメントの日本語化** | テストクラスのコメントが日本語で書かれているか | テストの範囲や目的が日本語として理解できるか |
| **@Nested クラスコメントの日本語化** | @Nested クラスのコメントが日本語で書かれているか | テストグループの意図が日本語として理解できるか |
| **テスト内行コメントの日本語化** | テストメソッド内の行コメントが日本語で書かれているか | 前提条件や期待値が日本語として理解できるか |
| **ヘルパーメソッドコメントの日本語化** | テスト用ヘルパーメソッドのコメントが日本語で書かれているか | メソッドの目的が日本語として理解できるか |
| **テストデータコメントの日本語化** | テストデータのコメントが日本語で書かれているか | データの意図や特徴が日本語として理解できるか |
| **技術用語の扱い** | 技術用語は適切に扱われているか | API名、クラス名、メソッド名などは原文のまま可。それ以外は日本語訳すること |

---

## 3. 注意事項

### 3.1 技術用語

- API名、クラス名、メソッド名、変数名、パッケージ名などは原文（英語）のまま使用してよい
- 例: `Spring Boot`, `JUnit`, `AssertJ`, `EntityName`, `findById()`

### 3.2 固有名詞

- プロダクト名、サービス名、フレームワーク名などは原文のまま使用してよい
- 例: `Spring Cloud Gateway`, `Mockito`, `Testcontainers`

### 3.3 コード内の識別子

- コード内の識別子（変数名、メソッド名、クラス名など）は、プロジェクトの命名規則に従い、英語で記述する
- コメント内で識別子を参照する場合は、原文のまま記載する

### 3.4 自然な日本語

- 機械翻訳のような不自然な表現を避け、自然な日本語で記載すること
- 例:
  - ❌ `// このテストは入力値がnullの場合に例外がスローされることを検証する`
  - ✅ `// 入力値がnullの場合、例外がスローされることを確認`

### 3.5 漢字とひらがなのバランス

- 読みやすいバランスで表記すること
- 例:
  - 「検証する」（✅）
  - 「確認する」（✅）
  - 「検证する」（❌ 誤字）

### 3.6 助詞の正しい使用

- 助詞の使い分けを正しく行うこと
- 例:
  - 「について」（✅）
  - 「对于」（❌ 中国語混入）

### 3.7 句読点の統一

- 句読点は日本語の「、」（読点）と「。」（句号）を使用すること
- 英語のコンマ（`,`）やピリオド（`.`）は使用しない

## 4. @DisplayName の書き方

### 4.1 基本ルール

- `@DisplayName` は必ず日本語で記載する
- テストの条件と期待結果を簡潔に表現する
- 例:

```java
@DisplayName("入力値がnullの場合、IllegalArgumentExceptionをスローする")
void shouldThrowExceptionWhenInputIsNull() {
    // 実装
}
```

### 4.2 命名パターン

- **条件 + 結果** の形式で記載する
- 例:
  - `@DisplayName("有効なIDの場合、エンティティを返す")`
  - `@DisplayName("存在しないIDの場合、NotFoundBusinessExceptionをスローする")`
  - `@DisplayName("空のリストの場合、空のコレクションを返す")`

### 4.3 禁止事項

- 英語の @DisplayName を使用しない
- 例:
  - ❌ `@DisplayName("Should throw exception when input is null")`
  - ✅ `@DisplayName("入力値がnullの場合、例外をスローする")`

---

## 5. テストクラスのコメントの書き方

### 5.1 基本ルール

- テストクラスの目的や範囲を日本語で説明する
- 例:

```java
/**
 * ユーザー管理機能の単体テスト。
 * ユーザーの作成、更新、削除、検索などの基本操作を検証する。
 */
class UserManagementTest {
    // テストケース
}
```

### 5.2 禁止事項

- 英語のコメントをそのまま残さない
- 例:
  - ❌ `/** Unit tests for user management functionality. */`
  - ✅ `/** ユーザー管理機能の単体テスト。 */`

---

## 6. @Nested クラスのコメントの書き方

### 6.1 基本ルール

- `@Nested` クラスでグループ化するテストの範囲を日本語で説明する
- 例:

```java
/**
 * ユーザー作成処理のテスト。
 * 正常系と異常系の両方を検証する。
 */
@Nested
class CreateUserTest {
    // テストケース
}
```

### 6.2 禁止事項

- 英語のコメントをそのまま残さない
- 例:
  - ❌ `/** Tests for user creation. */`
  - ✅ `/** ユーザー作成処理のテスト。 */`

---

## 7. テストメソッド内の行コメントの書き方

### 7.1 基本ルール

- テストの前提条件（Arrange）、実行（Act）、検証（Assert）の各フェーズを日本語で説明する
- 複雑なテストでは、なぜその検証を行うのかを説明する
- 例:

```java
@DisplayName("在庫数が不足している場合、予約に失敗する")
void shouldFailReservationWhenStockIsInsufficient() {
    // 在庫数が1のアイテムを用意する
    Item item = Item.builder()
            .id(itemId)
            .stockQuantity(1)
            .build();

    // 在庫数を超える量を予約しようとする
    ReservationResult result = reservationService.reserve(item.getId(), 5);

    // 予約が失敗し、在庫不足のエラーが返されることを確認
    assertThat(result.isSuccess()).isFalse();
    assertThat(result.getErrorMessage()).isEqualTo("在庫数が不足しています");
}
```

### 7.2 コメントの付け方

- **Arrangeフェーズ**: テストデータの用意や前提条件の設定を説明する
- **Actフェーズ**: 実行する操作の意図を説明する（必要に応じて）
- **Assertフェーズ**: 期待する結果や検証の理由を説明する

### 7.3 禁止事項

- 英語のコメントをそのまま残さない
- 例:
  - ❌ `// Given an item with stock quantity of 1`
  - ✅ `// 在庫数が1のアイテムを用意する`
  - ❌ `// When trying to reserve more than stock`
  - ✅ `// 在庫数を超える量を予約しようとする`
  - ❌ `// Then reservation should fail`
  - ✅ `// 予約が失敗することを確認`

## 8. テスト用ヘルパーメソッドのコメントの書き方

### 8.1 基本ルール

- テストを支援するメソッドの目的を日本語で説明する
- 例:

```java
/**
 * テスト用のユーザーエンティティを作成する。
 * 必須フィールドのみを設定した最小限のユーザーを返す。
 *
 * @param id ユーザーID
 * @return テスト用のユーザーエンティティ
 */
private User createTestUser(SnowflakeID id) {
    return User.builder()
            .id(id)
            .name("テストユーザー")
            .email("test@example.com")
            .build();
}
```

### 8.2 禁止事項

- 英語のコメントをそのまま残さない
- 例:
  - ❌ `/** Create a test user entity with minimal fields. */`
  - ✅ `/** テスト用のユーザーエンティティを作成する。 */`

---

## 9. テストデータのコメントの書き方

### 9.1 基本ルール

- テストで使用するデータがなぜ那样的な値なのか、どのような特徴を持つのかを日本語で説明する
- 例:

```java
// 有効なメールアドレスのテストデータ
private static final String VALID_EMAIL = "test@example.com";

// 形式が不正なメールアドレスのテストデータ
private static final String INVALID_EMAIL = "not-an-email";

// 边界値：最大文字数の名前（50文字）
private static final String MAX_LENGTH_NAME = "a".repeat(50);
```

### 9.2 禁止事項

- 英語のコメントをそのまま残さない
- 例:
  - ❌ `// Valid email address for testing`
  - ✅ `// 有効なメールアドレスのテストデータ`

---

## 10. モックのセットアップのコメントの書き方

### 10.1 基本ルール

- モックの動作を日本語で説明する
- 例:

```java
@BeforeEach
void setUp() {
    // リポジトリのモックを作成する
    when(userRepository.findById(any())).thenReturn(Optional.of(testUser));

    // 外部サービスのモックをセットアップする
    // メール送信が成功する動作を模擬する
    when(emailService.send(any())).thenReturn(true);
}
```

### 10.2 禁止事項

- 英語のコメントをそのまま残さない
- 例:
  - ❌ `// Mock the repository to return a user`
  - ✅ `// リポジトリがユーザーを返すようにモックする`

---

## 11. 既存の英語コメントの扱い

### 11.1 新規テストコード

- 新規に作成するテストコードでは、すべてのコメントを日本語で記載する

### 11.2 既存テストコードの修正

- 既存の英語コメントを修正・追加する場合は、日本語に翻訳する
- 大規模なリファクタリング時に、既存の英語コメントを日本語に翻訳することを推奨

## 12. チェックリスト

テストコードのコメント作成時、以下のチェックリストで確認してください。

- [ ] @DisplayName が日本語で書かれている
- [ ] テストクラスのコメントが日本語で書かれている
- [ ] @Nested クラスのコメントが日本語で書かれている
- [ ] テストメソッド内の行コメントが日本語で書かれている
- [ ] テスト用ヘルパーメソッドのコメントが日本語で書かれている
- [ ] テストデータのコメントが日本語で書かれている
- [ ] モックのセットアップのコメントが日本語で書かれている
- [ ] 技術用語は適切に扱われている
- [ ] 機械翻訳のような不自然な表現がない
- [ ] 助詞の使い分けが正しい
- [ ] 句読点が統一されている
