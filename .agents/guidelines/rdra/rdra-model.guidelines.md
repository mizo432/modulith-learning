# RDRA モデル (Requirement Analysis Model)

本プロジェクトでは、 **RDRA**（Relationship Driven Requirement Analysis、ラドラ）を要件定義手法として採用しています。

RDRA（ラドラ）は、株式会社バリューソースの神崎善司氏が提唱する要件定義手法です。
システムを構成する要素同士の関係（Relationship）を定義することで、システム全体の構造を明確に捉え、可視化するモデルベースの要件定義手法です。

要件を個別の項目として管理するのではなく、要素同士の関係性を軸にシステム全体を一つの構造として捉えることで、要件の抜け漏れや矛盾を早期に発見し、「なぜ必要なのか」を説明可能な納得感のある要件定義を実現します。

## 0. Core Concept

### RDRAの4つのレイヤー

RDRAはシステム全体を以下の4つのレイヤーで捉えます。各レイヤーは内側から外側に向けて「Why」の依存関係を持ち、下位レイヤーから上位レイヤーに向かって「なぜ？」と問いかけることで、要件に論理的なつながりを持たせます。

```text
┌─────────────────────────────────────────────────────────────┐
│                     Why 依存関係                            │
│  (システム) ← (システム境界) ← (システム外部環境) ← (システム価値) │
└─────────────────────────────────────────────────────────────┘

┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  システム     │   │ システム境界  │   │ システム外部  │   │ システム価値  │
│  レイヤー     │   │ レイヤー      │   │ 環境レイヤー  │   │ レイヤー      │
│              │   │              │   │              │   │              │
│ ・情報       │   │ ・ユースケース│   │ ・業務       │   │ ・要求       │
│ ・状態       │   │ ・画面        │   │ ・BUC        │   │ ・アクター    │
│ ・条件       │   │ ・イベント    │   │ ・アクティビ │   │ ・外部システム│
│ ・バリエーション│  │              │   │ ティ         │   │              │
└──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
```

#### 各レイヤーの概要

| レイヤー                     | 説明                                                                                     | 主な要素                                        |
|------------------------------|------------------------------------------------------------------------------------------|-------------------------------------------------|
| **システム価値レイヤー**     | システムが実現すべき価値。誰にとって、どのような価値を提供するか                         | 要求（機能/非機能）、アクター、外部システム     |
| **システム外部環境レイヤー** | システムがどのように使われるか。誰が何の業務を行い、どんな価値を提供するか               | 業務、ビジネスユースケース(BUC)、アクティビティ |
| **システム境界レイヤー**     | ユーザーや外部システムと開発対象システムとの接点。誰がどこに接点を持ち、何を入出力するか | ユースケース(UC)、画面、イベント                |
| **システムレイヤー**         | システム化する情報、状態、ビジネスルール。要件の要として整合性を維持                     | 情報、状態、条件、バリエーション                |

### RDRAのダイアグラム

要件定義は以下のダイアグラム単位で作成し、プロジェクトの状況に応じて使い分けます。

| ダイアグラム               | レイヤー         | 説明                                                                 |
|----------------------------|------------------|----------------------------------------------------------------------|
| **システムコンテキスト図** | システム価値     | システム化の目的を端的に表す。価値を提供するアクターと外部システム   |
| **要求モデル図**           | システム価値     | 要求を整理し、システム化の方向性を明確にする                         |
| **ビジネスコンテキスト図** | システム外部環境 | システム化対象の最上位のビジネス単位「業務」を明らかにする           |
| **ビジネスユースケース図** | システム外部環境 | 「業務」をビジネスユースケースに細分化する                           |
| **業務フロー図**           | システム外部環境 | ビジネスユースケースをアクティビティ図で表す                         |
| **利用シーン図**           | システム外部環境 | 「フロー」がない場合の使われ方を記述する                             |
| **UC複合図**               | システム境界     | ユースケース、画面、イベント、情報、条件を関連づける（PlantUML使用） |
| **バリエーション/条件図**  | システム         | ビジネスルールを表現する                                             |
| **情報モデル図**           | システム         | システム化したいビジネス上の用語とその関係                           |
| **状態モデル図**           | システム         | 状態遷移図で「xx済」「xx待ち」「xx中」などを表す（PlantUML使用）     |

### ダイアグラムの関係

各ダイアグラムは大きく4つの分類されます。

1. **方向性を求めるもの**: システムコンテキスト、要求モデル
2. **階層化でスコープを表すもの**: ビジネスコンテキスト → ビジネスユースケース →
   業務フロー/利用シーン → UC複合図
3. **ユースケース横断で整合させるもの**: 情報モデル、状態モデル
4. **要件定義の詳細を定義するもの**: バリエーション/条件

### システムレイヤーのモデル

システムレイヤーの要素を取りまとめるためのモデルには、以下のようなものがあります。

| モデル           | 説明                                                                                                                                                   |
|------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------|
| **コンテキスト** | 同じ役割をもつ情報、状態、条件、バリエーションをまとめる。システムの特定領域（ドメイン）のシステムレイヤーの要素をまとめて管理する単位として利用できる |
| **情報モデル**   | 複数の「情報」をひとつのモデルにまとめたもの                                                                                                           |
| **状態モデル**   | 複数の「状態」と、それらの間の遷移をまとめて定義したモデル                                                                                             |

### V字モデルにおける位置づけ

RDRAは要件定義の手法であり、主にV字モデルにおける要件定義（業務要件定義、システム要件定義）に位置付けられます。

| V字モデルのフェーズ | RDRAのレイヤー対応                             |
|---------------------|------------------------------------------------|
| 企画プロセス        | 事業の背景や狙い、要求を入力として受け取る     |
| 業務要件定義        | システム価値レイヤー、システム外部環境レイヤー |
| システム要件定義    | システム境界レイヤー、システムレイヤー         |

企画プロセスで整理された事業の背景や狙い、要求を入力として受け取り、「システム価値レイヤー」で定義します。
業務要件定義の内容は「システム外部環境レイヤー」、システム要件定義の内容は「システム境界レイヤー」と「システムレイヤー」で定義します。

### RDRAのツール

RDRAには、目的に応じて複数のツールが用意されています。

| ツール                  | 役割                                                                                                                                                                     |
|-------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **RDRA定義・分析Sheet** | RDRAによる要件定義作業の中心。システムを構成する要素とそれらの関係性を表形式で整理・定義。要件を関係性とともに構造化して記述し、RDRAモデルの基盤となる情報を一元的に管理 |
| **RDRA Graph**          | 定義・分析Sheetで定義した内容をグラフィカルなモデルとして視覚的に俯瞰。トレーサビリティや凝集度・結合度の把握など、さまざまな視点から定義情報を分析。参照専用            |

### RDRAのモデル要素

RDRAでは、システムを構成する要素を以下のモデルで定義します。

| モデル             | 説明                                                                                           |
|--------------------|------------------------------------------------------------------------------------------------|
| **アクター**       | システムに関わる人の役割を表す                                                                 |
| **アクター群**     | 同じような役割を持つ「アクター」をまとめ、組織の役割を示す                                     |
| **外部システム**   | システムと連携する外部のシステムを表す                                                         |
| **外部システム群** | 同じような関係を持つ「外部システム」をまとめる                                                 |
| **コンテキスト**   | システムを表すモデル「情報」「状態モデル」「条件」「バリエーション」をまとめる                 |
| **情報**           | システムが扱うビジネス上の情報を表す。ビジネス上管理されているID単位に存在する                 |
| **状態**           | 情報の変化を状態として扱い、ビジネス上管理する対象となる。状態を遷移させながらビジネスが進む   |
| **業務**           | 最上位の会社の機能（マーケティング、販売や在庫管理など）。BUCを構成要素に持つ                 |
| **BUC**            | 業務の価値を実現する単位で、業務フローの単位になる。同じ業務内でも関わるアクターや外部システムの違いでBUCが分かれる |
| **アクティビティ** | 意味をもったまとまった一つの作業。仕事で関りのあるものを関連させる                             |
| **UC**             | システムを使ってまとまった一つの意味をもつ作業。システムとの接点となり関りのあるものを関連させる |
| **画面**           | アクターとシステムとのインターフェースになる                                                   |
| **イベント**       | 外部システムとのインターフェースになる                                                         |
| **タイマー**       | ビジネス上の時間的な区切りを表す（例: 25日締め、月末）                                         |

### モデル間のつながりの規則

RDRAでは、モデル間のつながりに以下の規則が適用されます。

- **業務**は複数の**BUC**を配下にもつ
- **BUC**は複数の**アクティビティ**を配下にもつ
- **アクティビティ**（仕事）を行う**アクター**がつながる
- **アクティビティ**（仕事）でシステムを使う場合は**UC**につながる
- **UC**は**情報**を操作する
- **アクター**は**画面**を使って**UC**を操作する
- **外部システム**は**イベント**で**UC**と連携する
- **UC**が定時に活動する場合に**タイマー**につながる
- **情報**は**情報**につながることで構造化する
- **状態モデル**は複数の**状態**を持つ
- **UC**が**状態**を遷移させる
- 状態遷移は**状態モデル**内で**状態**を変える
- **コンテキスト**は**情報**、**状態モデル**、**条件**、**バリエーション**を配下に複数持つ
- **コンテキスト**内の構成要素は同一のIDで管理される
- **条件**は**バリエーション**と**状態モデル**の組合せで出来ている
- オブジェクトは必ず対応するメタモデルが存在し、オブジェクトのつながりはメタモデル間のつながりの規則に従う

### 定義内容は各モデルのオブジェクトとして定義する

RDRAでは、各モデルに対応するオブジェクトとして定義内容を記述します。

| 例             | モデル         | オブジェクト       |
|----------------|----------------|--------------------|
| **会員**       | アクター       | 会員               |
| **受注**       | 情報           | 受注               |
| **受注を登録する** | UC         | 受注を登録する     |

### RDRASheetの構造

RDRASheetは表形式で要件定義を行うための形式です。要件定義はシステムの可視化と同じです。ファイル内では階層構造を表すために、空白セルは上位のセルの値を引き継ぐことで階層構造を表現します。

#### 表形式のメリット

- **表形式によるシステム可視化**: 表形式では、同じ行に並ぶ項目同士が関連しているとみなすため、ダイアグラムでの配置や線による関係性の明示よりも、要件の定義に集中できる
- **ダイアグラム形式との違い**: 表形式はアイコンや線での直接的な関連付けは行えませんが、同じ行やファイル間での名前のリンクを活用することで、各要素の関連性を表現できる
- **反復的な精度向上**: 最初は大まかに全ファイルを埋め、その後、各ファイル間の関連を確認しながら精度を上げていくプロセスが推奨される
- **タブ区切りファイル(tsv)の利用**: 定義した内容はファイル毎にtsvファイルとして出力する

#### トレーサビリティの実現

- **ファイル間のリンク**: 個々の要素がそれぞれのファイルで定義されると同時に、BUCファイルなどで各要素を統合的に関連付けることで、システム全体のトレーサビリティ（追跡可能性）が向上する
- **ビジネスルールの整理**: 条件ファイルでは、ビジネスルールを定義し、バリエーションファイルと連動して、システムの動作ルールを数式や組み合わせとして整理する

#### 各ファイルの列構造

RDRASheetは以下のファイルで定義を行います。各ファイルの列構造は以下の通りです。

**「アクター」ファイル**

| 列         | 説明                           |
|------------|--------------------------------|
| アクター群 | アクターを分類するグループ     |
| アクター   | システムに関わる人の役割       |
| 説明       | アクターの説明                 |

**「外部システム」ファイル**

| 列              | 説明                             |
|-----------------|----------------------------------|
| 外部システム群  | 外部システムを分類するグループ   |
| 外部システム    | システムと連携する外部システム   |
| 説明            | 外部システムの説明               |

**「BUC」ファイル**

| 列              | 説明                                                                                           |
|-----------------|------------------------------------------------------------------------------------------------|
| 業務            | 「販売業務」などの業務を分類する単位                                                           |
| BUC             | 業務フローの単位となり、業務内に複数存在する                                                   |
| 先              | フローの分岐先ラベル                                                                           |
| アクティビティ  | 業務フロー内の各アクティビティを表す                                                           |
| 次              | 業務フローの単位となり、業務内に複数存在する                                                   |
| UC              | 上記アクティビティに対応し、システムが行うことをユースケースとして表す                           |
| 関連モデル1     | 「情報」「条件」「画面」「イベント」「タイマー」から選択する                                     |
| 関連オブジェクト1 | 関連モデル1に対応するオブジェクト名                                                          |
| 関連モデル2     | 「アクター」「外部システム」から選択する                                                       |
| 関連オブジェクト2 | 関連モデル2に対応するオブジェクト名                                                          |
| 説明            | 「アクティビティ」また「UC」の説明                                                             |

**「情報」ファイル**

| 列         | 説明                                                                                           |
|------------|------------------------------------------------------------------------------------------------|
| コンテキスト | 情報をまとめる単位                                                                           |
| 情報       | ユニークなIDで一意に識別できる                                                                 |
| 属性       | 情報が扱う属性を表します、「、」区切りで複数の属性を一つの文字列で表す                           |
| 関連情報   | 情報間の関係を表します、「、」区切りで複数の情報を一つの文字列で表す                             |
| 状態モデル | 状態で管理する状態モデルを表します、「、」区切りで複数の状態モデルを一つの文字列で表す           |
| バリエーション | 情報に従属するバリエーションを表します、「、」区切りで複数のバリエーションを一つの文字列で表す |
| 説明       | 情報の説明                                                                                     |

**「状態」ファイル**

| 列               | 説明                                                                                           |
|------------------|------------------------------------------------------------------------------------------------|
| コンテキスト     | 状態モデルが対応する情報と同じコンテキストを表す                                                 |
| 状態モデル       | 状態遷移の管理単位で情報に対応する                                                               |
| 状態             | 情報が取る状態を表す                                                                           |
| 遷移UC           | 状態を遷移させるユースケースを表す                                                               |
| 遷移先状態       | 遷移された状態を表す                                                                           |
| 状態モデル・状態の説明 | 状態モデル・状態の説明                                                                     |

**「条件」ファイル**

| 列           | 説明                                                                                           |
|--------------|------------------------------------------------------------------------------------------------|
| コンテキスト | 条件が所属するコンテキストを表す。条件に関わる情報のコンテキストを使う                           |
| 条件         | ビジネスルールの名前を表す                                                                       |
| 条件の説明   | バリエーションを表す                                                                             |
| バリエーション | 条件の縦軸/横軸となるバリエーションを表す（バリエーションファイルで定義したものに対応する）    |
| 状態モデル   | 条件の縦軸/横軸となる状態モデルを表す（状態ファイルで定義したものに対応する）                   |

**「バリエーション」ファイル**

| 列             | 説明                                                                                           |
|----------------|------------------------------------------------------------------------------------------------|
| コンテキスト   | バリエーションが所属するコンテキストを表す                                                       |
| バリエーション | 区分や種別などの業務上の分類を表し、条件で使われる                                               |
| 値             | 区分や種別を表す                                                                               |
| 説明           | バリエーションの説明                                                                           |

#### 各ファイル間の参照関係

ファイル間には他のファイルを参照する関係があります。

| 定義ファイル     | 参照ファイル                                       |
|------------------|----------------------------------------------------|
| **BUC**          | アクター、外部システム、情報、条件                 |
| **情報**         | 状態、バリエーション                               |
| **状態**         | BUC                                                |
| **条件**         | バリエーション、状態                               |

#### 階層構造

各ファイルの階層構造は以下の通りです。空白セルは一つ上のセルの値を引き継ぎ、同じカラムで上下に同じ場合は親の値と見なされます。

| シート         | 親/子                              |
|----------------|------------------------------------|
| アクター       | アクター群/アクター                |
| 外部システム   | 外部システム群/外部システム        |
| 情報           | コンテキスト/情報                  |
| 状態           | コンテキスト/状態、遷移先状態      |
| 条件           | コンテキスト/条件                  |
| バリエーション | コンテキスト/バリエーション        |

### RDRAGraphの変換ルール

RDRAGraphは、表形式のRDRASheetからグラフ形式の関連データへ変換して視覚的に表示するための形式です。

#### 関連データの構造

関連データは1行目と2行目以降でフォーマットが異なります。

**1行目のフォーマット**

1カラムでシステム名を表します。

**2行目以降のフォーマット**

4カラムから構成されます。

| カラム | 説明                                                                                           |
|--------|------------------------------------------------------------------------------------------------|
| A      | 関係: `#child` `#edge` `#comment` `#arrow` `#stereotype` `#attribute`                          |
| B      | モデル1: モデル名を表す                                                                        |
| C      | モデル2: モデル名を表す                                                                        |
| D      | オブジェクト同士の関連を表す結合された文字列（オブジェクト1@@オブジェクト2//オブジェクト1@@オブジェクト2//～） |

#### 文字列の結合ルール

オブジェクト同士の関連を表す結合された文字列は、以下のルールで構成されます。

- **オブジェクト1**: モデル1に対応したオブジェクト名
- **オブジェクト2**: モデル2に対応したオブジェクト名
- **@@**: オブジェクト1と2を分離する文字
- **//**: オブジェクトの関連を分離する文字

モデル1とモデル2のペアが同じ場合は、`オブジェクト1@@オブジェクト2`のペアを`//`で区切って一つの文字列にし、モデルの組合せ毎に一つの行としてまとめます。

#### 各シートからの関連データ変換

**「アクター」シート**

| 関係     | モデル1   | モデル2 | 説明                           |
|----------|-----------|---------|--------------------------------|
| #child   | アクター群 | アクター | アクター群とアクターの階層関係 |
| #comment | アクター  | 説明    | アクターの説明                 |

**「外部システム」シート**

| 関係     | モデル1      | モデル2     | 説明                             |

## 2. RDRA ワークフロー

RDRAによる要件定義は「7つのフェーズ」で進めます。
一度で完璧を目指すのではなく、何度も見直して精度を上げていくのがポイントです。

### 2.1 フェーズ1: 初期要望から要素を抽出する

**目的**: 初期要望からRDRAモデルの全要素を抽出し、要件定義の基盤を構築する。

**対応レイヤー**: 全レイヤー（システム価値、システム外部環境、システム境界、システム）の要素を初期要望から洗い出す。

フェーズ1では、初期要望を分析し、RDRAモデルを構成する全要素を抽出します。各要素は独立して抽出され、後続のフェーズで関係性を定義していきます。

#### 初期要望分析

初期要望の内容を分析し、RDRAのモデル要素との関りを整理します。

- 初期要望の内容を分析し構造を把握する
- RDRA構造と対比し、具体的に書かれていることと書かれていないことを分析する
- 初期要望に書かれていることをそのまま出力せず、抽象的な分類として「～について記述されている」形式で出力する

#### 要求の抽出

初期要望から機能要求と非機能要求を洗い出します。

- 要求は「～したい」「～すること」「～できる」などで表現される
- **機能要求**: 具体的なビジネス、システムの機能に対する要求
- **非機能要求**: 使いやすさやレスポンス時間など、具体的な機能ではない要求

#### アクターの抽出

初期要望からシステムに関わる人の役割（アクター）を洗い出します。

- アクターは役割として命名し、個人名や組織名は使わない
- アクターは顧客（社外の価値受益者）と提供者（価値を提供するアクター）に分かれる
- アクター群はアクターを分類する組織単位

#### 外部システムの抽出

初期要望から連携が必要な外部システムを洗い出します。

- 外部システムは役割に応じて分類する
- 外部システム名は役割が分かる名前にする

#### 業務の抽出

初期要望から業務とビジネスユースケース(BUC)を洗い出します。

- 業務は「販売管理」「在庫管理」などのように企業の中の大きな管理単位
- BUCは業務フローの単位となり、価値受益アクターに価値を提供する
- BUCには必ず一人の価値を得るアクターがいる
- 業務は1つ以上のBUCを含み、階層構造になる

#### 情報の抽出

初期要望からビジネスとして管理すべき情報を洗い出します。

- 情報は必ずユニークなIDを持ち、一意に識別できる
- ビジネスは情報に状態を保持する

#### 状態の抽出

初期要望から状態モデルを洗い出します。

- 状態モデルは状態が遷移する状態の集合
- 状態モデルは必ず複数の状態を持つ
- ビジネスは状態を使って今の状況を把握し、次の状態に遷移させる

#### ビジネスパラメータの抽出

初期要望からビジネス上必要になる区分、分類、種別などのパラメータを洗い出します。

- システムの仕組み上の区分、分類、種別は含めない
- 記述されていない場合は、記述されていることから必要となるビジネスパラメータを類推する

#### ビジネスポリシーの抽出

初期要望からビジネスに関するポリシー（方針）を洗い出します。

- ビジネスとシステムを深堀りする時の様々な判断基準とするポリシー
- 記述されていない場合は、記述されていることから必要となるビジネスポリシーを類推する

### 2.2 フェーズ2: 要素を再整理し詳細化する

**目的**: フェーズ1で抽出した要素を再整理し、業務はアクティビティ/UCにブレークダウンし、情報は属性と関連を定義し、状態は状態遷移に分解する。

**対応レイヤー**: システム外部環境レイヤーとシステムレイヤーの詳細化。

フェーズ2では、フェーズ1で抽出した業務・情報・状態を、フェーズ1で得た他の要素（要求、ビジネスポリシー、アクターなど）を参照して再整理・詳細化します。

#### 業務の詳細化

フェーズ1で抽出した業務をベースに、アクティビティとUC（ユースケース）にブレークダウンします。

- フェーズ1の業務.tsvをベースに業務/BUCをアクティビティとUCに分解する
- 要求に関わるアクティビティとUCを洗い出す
- 初期要望に業務フローの要素があればアクティビティとして追記する
- 初期要望にシステムの機能について記述があればUCとして追記する
- 状態モデル内の状態遷移はUCによって遷移される
- 状態モデルに関わるBUCを識別し、状態を遷移させるUCは業務内のUCに対応する
- 価値受益アクターと価値提供アクターをアクティビティ/UC毎に分割する
- UCは価値受益アクターか価値提供アクターのどちらかのアクターと結びつく

#### 情報の詳細化

フェーズ1で抽出した情報をベースに、属性と関連情報を定義します。

- フェーズ1の情報.tsvをベースに情報を再整理する
- 機能要求/非機能要求を実現するために必要な情報を洗い出す
- BUCの中で利用する情報を洗い出す
- フェーズ1に存在しない情報は追加する
- 情報が持つべき属性を洗い出す
- 情報同士の関連を関連情報として洗い出す
- 初期要望にデータの属性に関わる記述があれば属性として追記する
- 初期要望にデータ同士の関連に関わる記述があれば関連情報として追記する

#### 状態の詳細化

フェーズ1で抽出した状態モデルをベースに、状態遷移に分解します。

- フェーズ1の状態.tsvをベースに状態を状態遷移に分解する
- 機能要求/非機能要求を実現するために必要な状態モデルと状態、遷移先状態を洗い出す
- フェーズ1の情報に対応する状態モデルの有無を調べ、足りていない場合は追加する
- フェーズ1の業務/BUCで行うことに対応する状態モデルの有無を調べ、足りていない場合は追加する
- フェーズ1のビジネスポリシーから行わなければならない対応する状態モデルの有無を調べ、足りていない場合は追加する
- 状態モデルの複数の状態を状態と遷移先状態に分解する
- 状態遷移に分解する時は遷移の数分だけ複数行として出力する
- 最初の状態は「状態：start、遷移先状態：最初の状態」で表現する
- 最後の状態は「状態：最後の状態、遷移先状態：end」で表現する

#### 条件の派生

フェーズ1で抽出したビジネスポリシーから条件（ビジネスルール）を派生させます。

- ビジネスルールを条件として洗い出す
- 必要なルールを条件の説明として定義する
- ビジネスルールが必要な場面と理由を利用場面として定義する

#### バリエーションの派生

フェーズ1で抽出したビジネスパラメータからバリエーションを派生させます。

- バリエーションはビジネス上の区分や種類を表す
- バリエーション内の取り得る複数の値を定義する

### 2.3 フェーズ3: 要素を再整理する

**目的**: フェーズ2で詳細化した要素を再整理し、BUCはUC・情報・条件・外部システムと紐付け、アクターは業務から再整理し、情報はコンテキストで分類して状態モデルとバリエーションと関連付ける。

**対応レイヤー**: システム外部環境レイヤーとシステムレイヤーの再整理。

フェーズ3では、フェーズ2で詳細化したBUC・アクター・情報を、他の要素との関係性を考慮して再整理します。

#### BUCの再整理

フェーズ2で詳細化したBUCをベースに、UC・情報・条件・外部システムと紐付けます。

- フェーズ2の業務.tsvをベースに同じレコード件数のBUC.tsvを出力する
- フェーズ2の業務.tsvとBUC.tsvで同じ項目の場合はそのまま出力する
- フェーズ2の業務の説明を参考にUCにつながる情報、条件、外部システムを追記する
  - アクティビティが行う仕事をシステムで行う場合はユースケース（UC）に情報、条件、外部システム、アクターとの連携で記述する
  - UCで行うことをシステムで整合させるために情報とつなげる
  - システムが外部のシステムと連携する場合に外部システムをUCにつなげる
    - 外部システムはフェーズ1で定義された外部システムだけを使う
      - 外部システム.tsvに記述されていない外部システムを生成しない
  - システムがビジネスルールに従うときに条件とつなげる
  - 初期要望分析にUCとつながる情報、条件（ビジネスルール）、外部システムの関係の記述があれば、それを含める
  - 以下の関連モデルと関連オブジェクトの成約に従う
    - 関連モデル1:「情報」、関連オブジェクト1:「情報.tsv」で定義された情報を設定する。新たに情報を生成しない
    - 関連モデル1:「条件」、関連オブジェクト1:「条件.tsv」で定義された条件を設定する。新たに条件を生成しない
    - 関連モデル2:「外部システム」、関連オブジェクト2:「外部システム.tsv」で定義された外部システムを設定する。新たに外部システムを生成しない

#### アクターの再整理

フェーズ1で抽出したアクターをベースに、業務から新たなアクターを追加し、主担当業務を設定します。

- フェーズ2の業務を読込、「価値受益アクター」と「価値提供アクター」をフェーズ1のアクターにないものをフェーズ3のアクターに追加して出力する
- フェーズ1のアクターから初期要望にアクターの記述がなく、フェーズ1の業務の「価値受益アクター」と「価値提供アクター」に該当するものがないアクターは出力しない
- 業務の「価値受益アクター」に対応するアクターには、主担当業務として設定する
- アクターはアクター群としてグループ化する

#### 情報の再整理

フェーズ2で詳細化した情報をベースに、コンテキストで分類し、状態モデルとバリエーションと関連付けます。

- フェーズ2の情報.tsvをベースにコンテキストで分類し、状態モデル、バリエーションと紐付けて出力する
- 情報を役割に応じてコンテキストとして分類する
- コンテキストは情報を中心とした管理単位となる
- コンテキストはドメインのグループとして活用する
- フェーズ2の情報.tsvを順次読込以下のことを行う
  - 情報に関係する状態モデルを関連付ける
  - 情報はユニークなIDを持ち、状態モデルもユニークなIDの状態遷移を表す
  - 同じIDをもつものを関連付ける
  - 情報に従属するバリエーションを関連付ける
    - 例：会員ランク（バリエーション）は会員（情報）に従属する
  - 初期要望分析にUCと情報、条件（ビジネスルール）、外部システムの関係の記述があれば、それを含める
  - 情報のIDと同じIDをもつ「状態.tsv」の状態モデルは、状態モデルカラムに設定する
  - バリエーションが情報に従属する場合はバリエーションに設定する
- 状態モデルカラムに設定する名前は「状態.tsv」に定義されている状態モデルを設定、新たに状態モデルを生成しない
- バリエーションカラムは「バリエーション.tsv」に定義されているバリエーションを設定、新たにバリエーションを生成しない

### 2.4 フェーズ4: 要素を関連付ける

**目的**: フェーズ3で再整理した要素を最終的なRDRA Sheet形式に変換し、BUCは関連モデル形式へ展開し、バリエーション・条件・状態にコンテキストを紐付ける。

**対応レイヤー**: システム外部環境レイヤーとシステムレイヤーの最終整理。

フェーズ4では、フェーズ3で再整理したBUC・バリエーション・条件・状態を、最終的なRDRA Sheet形式に変換します。

#### BUCの関連モデル形式への変換

フェーズ3で再整理したBUCをベースに、関連モデル1・関連オブジェクト1・関連モデル2・関連オブジェクト2の形式に変換し、複数行に展開します。

- フェーズ3の業務.tsvをベースにBUC.tsvを出力する
- フェーズ3の業務.tsvとBUC.tsvで同じ項目の場合はそのまま出力する
- フェーズ3の業務の説明を参考にUCにつながる情報、条件、外部システムを追記する
  - アクティビティが行う仕事をシステムで行う場合はユースケース（UC）に情報、条件、外部システム、アクターとの連携で記述する
  - UCで行うことをシステムで整合させるために情報とつなげる
  - システムが外部のシステムと連携する場合に外部システムをUCにつなげる
    - 外部システムはフェーズ1で定義された外部システムだけを使う
      - 外部システム.tsvに記述されていない外部システムを生成しない
  - システムがビジネスルールに従うときに条件とつなげる
  - 初期要望分析にUCとつながる情報、条件（ビジネスルール）、外部システムの関係の記述があれば、それを含める
- カラム内の値に「、」か「,」がある場合は値を分割し、分割した数に応じて複数行で出力する
- 関連モデルと関連オブジェクトの変換ルール:
  - 「情報」は関連モデル1を「情報」にし、関連オブジェクト1に情報名をセット
  - 「条件」は関連モデル1を「条件」にし、関連オブジェクト1に条件名をセット
  - 「アクター」は関連モデル1を「画面」にし、関連オブジェクト1に画面名をセット、関連モデル2を「アクター」にし、関連オブジェクト2にアクター名をセット
  - 「外部システム」は関連モデル1を「イベント」にし、関連オブジェクト1にイベント名をセット、関連モデル2を「外部システム」にし、関連オブジェクト2に外部システム名をセット
- 画面名はUCが提供する画面として適切な名前にし、UCとアクターをつなげた単純な名前にはしない
- イベント名はUCと外部システムとの連携として適切な名前にし、UCと外部システムをつなげた単純な名前にはしない

#### バリエーションのコンテキスト紐付け

フェーズ2のバリエーションをベースに、フェーズ3の情報からコンテキストを紐付けて再整理します。

- フェーズ2のバリエーション.tsvをベースにコンテキストを追記して出力する
- フェーズ3の情報.tsvのバリエーションに対応するバリエーションがあれば、その情報のコンテキストをバリエーションのコンテキストとする
- 情報に対応するバリエーションがない場合はバリエーションの役割を分類する名前をコンテキストとする

#### 条件のコンテキスト・バリエーション・状態モデル紐付け

フェーズ2の条件をベースに、コンテキスト・バリエーション・状態モデルを紐付けて再整理します。

- フェーズ2の条件.tsvをベースにコンテキスト、バリエーション、状態モデルを追記して出力する
- 条件は計算式や判断条件に名前を付けたものか、表形式の縦横の組合せ形式のものに分かれる
- 条件が表形式の場合にバリエーションと状態モデルに関わる場合がある
  - 表形式の条件の縦軸か横軸に当てはまるものを設定する
    - 状態モデルが当てはまる場合は、条件の状態モデルに対応する名前を設定する
    - バリエーションが当てはまる場合は、条件のバリエーションに対応する名前を設定する
- 条件のコンテキストは条件に関わる情報のコンテキストを使う

#### 状態のコンテキスト・遷移UC紐付け

フェーズ2の状態をベースに、コンテキストと遷移UCを紐付けて再整理します。

- フェーズ2の状態.tsvをベースにコンテキストと遷移UCを追記し出力する
- フェーズ3の情報.tsvの状態モデルに対応する状態モデルがあれば、その情報のコンテキストを状態モデルのコンテキストとする
- 状態はUCが遷移させる
  - 遷移UCカラムは状態から遷移先状態への遷移を行うUCをフェーズ3のBUC.tsvのUCから設定する
  - 設定するUCはフェーズ3のBUC.tsvのUCからだけ設定し、新たに生成しない

### 2.5 フェーズ5: システム概要を定義する

**目的**: 初期要望からシステム名とシステム概要を抽出し、システム全体の概要を定義する。

**対応レイヤー**: システム価値レイヤーの最上位定義に相当します。

フェーズ5では、初期要望からシステムの名前と概要を抽出し、JSON形式で出力します。これはRDRAの他のフェーズが要素中心の整理であるのに対し、システム全体の概要を定義するステップです。

#### システム名の抽出

- 「初期要望.txt」の内容から自然な日本語のシステム名を1つ抽出・決定する
- システムの目的や対象業務を反映した適切な名前とする

#### システム概要の生成

- 「初期要望.txt」の内容を要約し、システム概要を生成する
- 具体性を保ちつつ簡潔にまとめる（長すぎない文章量）
- システムが解決する課題や提供する価値を明確にする

#### 出力形式

- 出力先: `1_RDRA/システム概要.json`
- 形式: `{"system_name":"システム名","system_overview":"システム概要"}`
- JSONのみを出力し、既存ファイルがある場合は上書きする

### 2.6 フェーズ6: 仕様を生成する

**目的**: RDRA定義から具体的な仕様を生成し、論理データモデル、ビジネスルール、画面一覧を作成する。

**対応レイヤー**: システムレイヤーとシステム境界レイヤーの仕様化。

フェーズ6では、フェーズ1~5で定義したRDRA要素を基に、具体的な仕様を生成します。論理データモデル(ER図)、ビジネスルール(テーブル形式)、画面一覧(JSON)の3つの仕様を作成し、後続の設計プロセスに引き継ぎます。

#### 論理データ生成

RDRAの「情報」から論理データモデル(ER図)を生成します。情報の属性構造や親子関係に基づいて正規化し、Mermaid ER図として出力します。

**論理データの構造**

論理データは以下のカラムから構成されます。

| カラム     | 説明                                                                                           |
|------------|------------------------------------------------------------------------------------------------|
| データ名   | entity名                                                                                       |
| 項目名     | カラム名                                                                                       |
| タイプ     | 「string」or「number」or「enum」or「boolean」                                                    |
| isKey      | boolean (true: 主キー、false: 主キー以外)                                                       |
| 説明       | 項目名の説明                                                                                   |

**情報から論理データへの変換ルール**

- 情報の属性で構造を持っているものは別論理データとして抜き出す
  - 例: 住所は{郵便番号, 都道府県, 市区町村}で構成される場合は、住所を別論理データとする
- 親子関係がある情報は親と子の論理データに分割する
  - 例: 受注情報は受注と受注明細に分け、受注明細に外部キー「受注ID」を持つ
  - 例: 会員情報は会員と個人情報に分け、会員に外部キー「個人情報ID」を持つ

**論理データ作成ルール**

- データはユニークな主キーを必ず持ち、項目名は「データ名＋"_ID"」とする
- 項目がバリエーションの場合は、バリエーション名を項目名にする
- タイプの「enum」はRDRAのバリエーションに対応する
- データ名_IDはユニークな数字で0からシーケンスにアップする
- 他データを参照する項目名はデータ名にIDを付けた名前にする「データ名_ID」
- 論理データの構造は「情報」の関連情報を参考に正規化に従って作成する
- 親子関係は子エンティティに親のIDを保持する
- 状態モデルの状態を管理する項目を持つ

**出力ルール**

- 論理データを元にER図を「Mermaid Diagram」で作成する
- Diagramの前後は必ず「```mermaid」と「```」で囲む
- 出力ファイル: 「2_RDRASpec/論理データモデル.md」

#### ビジネスルール生成

RDRAの「条件」をビジネスルールとしてMarkdownのテーブル形式で出力します。

**ビジネスルールの表現形式**

ビジネスルールの出力は2種類に分かれます。

1. **名前の付いた計算式**: 条件名と計算式のペアで表現
   - 例: 消費税: 金額 × 0.1

2. **2次元のマトリックス**: 縦横の組合せで規定される
   - 条件に状態モデルが関係しているときは、縦軸か横軸に状態モデルの各状態を結びつける
   - 条件にバリエーションが関係しているときは、縦軸か横軸にバリエーションの各値を結びつける
   - 条件に状態モデルとバリエーションの両方が設定されているときは縦軸と横軸で組み合わせる
   - マトリックスの縦軸と横軸の組合せの中の値は、条件の役割から導かれる値を設定する

**出力ルール**

- 出力ファイル: 「2_RDRASpec/ビジネスルール.md」
- 各ビジネスルールは目的と使われ方を説明する
- ビジネスルールはMarkdownのテーブル形式で出力する

#### 画面一覧生成

RDRA定義から画面一覧(JSON)を生成します。画面項目(fields)、画面データ(screen_datas)、機能(operation)を定義します。

**画面の項目を洗い出す**

- 画面に必要な項目は画面につながるUCに必要な項目から決まる
- 画面の項目は以下の観点で洗い出す
  - 画面と関係する情報の項目: 画面 → UC → 情報
  - 画面につながるアクターの役割から必要な項目
  - 画面につながるUCの役割から必要な入力項目
- 画面の項目typeの決め方
  - バリエーションや分類、状態モデル、状態などの複数の値を持つ場合は「enum」を設定する
  - 名前や住所などの場合は「string」を設定する
  - 金額や数量などの場合は「number」を設定する
  - 上記以外は「string」を設定する

**機能名の種類**

| 機能名 | 説明                                                                                           |
|--------|------------------------------------------------------------------------------------------------|
| 一覧   | 一覧形式でデータを表示する                                                                     |
| 照会   | 現在の状況の把握。データを表示する                                                             |
| 登録   | 画面から情報を入力し新たな情報を追加、更新、削除する                                           |
| 分析   | データを分析する機能をもつ                                                                     |
| 申請   | ワークフローで申請する情報を入力する                                                           |
| 承認   | ワークフローで登録されたデータを承認/却下する                                                  |

**画面データ**

- 画面毎に3件のダミーデータを生成する
- dummy_dataはfieldsの項目名に対応する項目を持つ

**出力フォーマット**

```json
{
  "screens": [{
    "screen_name": "画面名",
    "fields": [{
        "field_name": "項目名",
        "type": "string|number|enum",
        "tooltip": "項目の説明"
    }],
    "screen_datas": [{
        "display_name": "表示用のデータ",
        "dummy_data": [{"field_name": "項目名", "value": "値"}]
    }],
    "operation": "機能名",
  }]
}
```

- 出力ファイル: 「2_RDRASpec/Phase1/画面一覧.json」

#### BUC画面生成

画面と業務/BUC、アクターとの関係をJSON形式で定義します。

**構造**

- 関連データから全「業務」を抽出
- 各業務に関連する「BUC」を抽出
- BUCに関連する「アクター」を抽出 (業務 → BUC → アクティビティ → UC → 画面 → アクター)
- アクターにつながる「画面」を抽出
- 画面は「画面一覧.json」で定義されているものを使用し、架空の画面を生成しない

**出力フォーマット**

```json
{
  "businesses": [{
    "business_name": "業務名",
    "BUCs": [{
        "buc_name": "BUC名",
        "actors": [{
            "actor_name": "アクター名",
            "screen_names": ["画面名"]
        }]
    }]
  }]
}
```

- 出力ファイル: 「2_RDRASpec/phase1/BUC画面.json」

#### アクター画面生成

画面とアクターの関係をJSON形式で定義します。

**構造**

- 関連データから全「アクター群」を抽出
- 各アクター群に関連する「アクター」を抽出
- アクターにつながる画面を配置
- 画面は「画面一覧.json」で定義されているものを使用し、架空の画面を生成しない

**出力フォーマット**

```json
{
  "actorGroups": [{
    "group_name": "アクター群",
    "actors": [{
      "actor_name": "アクター名",
      "screen_names": ["画面名"]
    }]
  }]
}
```

- 出力ファイル: 「2_RDRASpec/phase1/アクター画面.json」

### 2.7 フェーズ7: 画面照会を生成する

**目的**: 画面一覧.jsonにデータアクセス情報を追記し、BUC画面.jsonとアクター画面.jsonとまとめて画面照会.jsonを生成する。

**対応レイヤー**: 画面と論理データの関係性を定義し、UI定義を完成させる。

フェーズ7では、フェーズ6で生成した画面一覧.json、BUC画面.json、アクター画面.jsonを統合し、画面が操作する論理データへのアクセス情報を追記して画面照会.jsonを作成します。

#### 画面照会の生成

画面一覧.jsonの「screens」にデータアクセス「data_access」を追記し、BUC画面.jsonの「businesses」とアクター画面.jsonの「actorGroups」とまとめて出力します。

**データアクセス（data_access）の追加**

- 画面の機能に必要なentityを「論理データモデル.md」から洗い出す
- 画面に必要な項目を満たす項目を持つ論理データ(entity)から関係を洗い出す
- 画面とEntityの関係は以下の関係データを頼りに類推する
  - 画面 → UC → 情報
  - 情報と論理データの関係を類推する

**データアクセスの構造**

関係するentityとの関係をC,R,U,Dで示し、複数設定可能です。

| CRUD | 説明                           |
|------|--------------------------------|
| C    | 登録、追加などを表す           |
| R    | 参照、表示などを表す           |
| U    | 更新、変更などを表す           |
| D    | 削除を表す                     |

- isMain: true(主として操作するEntity) / false(主Entityから参照されるEntity)
- 一つの画面に主となるEntityは一つ

**出力フォーマット**

```json
{
  "businesses":[{
    "business_name":"業務名",
    "BUCs":[{
        "buc_name":"BUC名",
        "actors":[{
            "actor_name":"アクター名",
            "screen_names":["画面名"]
        }]
    }]
  }],
  "actorGroups":[{
    "group_name":"アクター群",
    "actors":[{
      "actor_name": "アクター名",
      "screen_names": ["画面名"]
    }]
  }],
  "screens":[{
    "screen_name": "画面名",
    "fields": [{"field_name": "項目名",
        "type": "string|number|バリエーション",
        "tooltip":"項目の説明"
    }],
    "screen_datas": [{
        "display_name":"表示用のデータ",
        "dummy_data":[{"field_name": "項目名","value": "ダミーデータ"}]
    }],
    "operation":"機能名",
    "data_access":[{"entity":entity名,"CRUD":["C","R","U","D"],"isMain":true}]
  }]
}
```

**出力ルール**

- 出力ファイル: 「2_RDRASpec/画面照会.json」
- 関連データ.txtの「画面-アクター」定義を全て網羅する
- 同一画面に複数アクターがいる場合、全てのアクターを出力する
- businesses内のscreensが全ての画面を網羅していることを確認する

### 2.8 要件組み立てフェーズ: 要素を関連付け、要件を具体化する

**目的**: 抽出した要素同士を関連付け、ユースケースを中心に要件を具体化する。

**対応レイヤー**: システム境界レイヤーおよびシステムレイヤーを詳細化するプロセスに相当します。

#### トップダウンで要件を組み立てる

ユースケースを起点に、システムがどのように使われるかを定義し、要素を関連付けていきます。

**画面、イベント、タイマーを定義し、ユースケースに関連付ける**

- **画面**: ユーザーがシステムと対話するためのUIを定義し、ユースケースに関連付ける
- **イベント**: 外部システムとの連携や、システム内で発生する出来事を定義し、ユースケースに関連付ける
- **タイマー**: 時間ベースで発生するトリガーを定義し、ユースケースに関連付ける

**アクター、外部システムを関連付ける**

- **アクターと画面の関連付け**: どのUIからアクターが操作するかを定義する
- **外部システムとイベントの関連付け**: 外部システムと外部インターフェースの関連付けを行う

#### ボトムアップで詳細を見直す

トップダウンで組み立てた要件を、システムレイヤーの要素から逆に見直し、整合性を確認します。

**情報の定義**

- 業務で扱う「情報」を構造化し、設計する
- 情報をユースケースに関連付ける
- 情報モデル図を作成し、情報同士の関係性を可視化する
- 各情報の属性を定義し、属性一覧（MD/TSV）を作成する

**条件の定義**

- システムが動く「条件」（ビジネスルール）を抽出する
- 条件をユースケースに関連付ける
- 例: 単価表、承認ルール、判定条件など

**業務ルールの種類**

業務ルール（条件）を定義する際には、以下の5つの種類を意識して分類します。

| 業務ルールの種類   | 英語表記        | 説明                                                                             |
|--------------------|-----------------|----------------------------------------------------------------------------------|
| **意思決定支援**   | DecisionSupport | 判断や意思決定を支援するルール。推奨事項や評価基準を提供し、担当者の判断を助ける |
| **ポリシー**       | Policy          | 組織やシステムが遵守すべき規範や方針。違反が許されない強制力のあるルール         |
| **コミットメント** | Commitment      | システムや組織が約束する行動や保証。SLAやサービスレベルの約束など                |
| **オペレーション** | Operation       | 日常的な業務手順や運用ルール。標準的な処理フローや操作方法を規定する             |
| **ポテンシャル**   | Potential       | 将来の拡張や改善の可能性を示すルール。オプション機能や拡張ポイントを定義する     |

業務ルールをこれらの種類に分類することで、ルールの性質や優先度を明確にし、要件定義の精度を高めることができます。

**状態の定義**

- 業務の中で「こういう状態になる」というものを定義する（例: 「xx済」「xx待ち」「xx中」）
- 状態遷移図（ステートマシン図）を作成し、状態の変化を可視化する
- ユースケースによる情報の変化を状態として表すことで、ユースケースの妥当性を評価する

**UC複合図の作成**

- 洗い出したユースケース、画面、イベント、情報、条件をPlantUMLで関連づけたUC複合図を作成する
- UC複合図は `03.システム境界/UC複合図.md` に配置する
- アクター、外部システム、ユースケース、画面、イベント、情報、条件の関係性を視覚的に表現する

#### 最後に：要件組み立てフェーズの成果物の全体像

要件組み立てフェーズで定義する主な要素およびモデルは、以下のとおりです。

| カテゴリ             | 要素                                                                       |
|----------------------|----------------------------------------------------------------------------|
| システム境界レイヤー | ユースケース、画面、イベント、タイマー、UC複合図                           |
| システムレイヤー     | 情報、状態、条件                                                           |
| 関連付け             | アクター×画面、外部システム×イベント、情報×ユースケース、条件×ユースケース |

### 2.9 システムレイヤーの要素同士を関連付ける

**目的**: システムレイヤーの要素（バリエーション、状態、情報、条件）同士を関連付け、要素間の関係を確定させる。

システムレイヤーの要素同士を関連付けることで、「どの情報にどの分類軸が適用されるのか」「情報がどの状態遷移を持つのか」などが構造として明らかになります。この関連付けにより、開発対象となるシステムモデルの網羅性が高まります。

#### バリエーションを洗い出す

バリエーションとは、ビジネス上あらかじめ定義された区分を持ち、対象をどの観点で分類するかを定めるモデル要素です。バリエーションが表すのは、名称による種別だけではありません。ビジネスルールの詳細条件を示す区分も、バリエーションに含まれます。

例えば、遅延日数に応じて取扱いを分ける場合には、遅延日数が3日未満、7日未満、7日以上といった数値条件による区分を定義します。

**バリエーションと状態の違い**

RDRAでは、「バリエーション」と「状態」を明確に区別します。両者は似ているように見えますが、モデル上の役割が異なります。

| 要素               | 役割                                                   | 例                                                            |
|--------------------|--------------------------------------------------------|---------------------------------------------------------------|
| **バリエーション** | 対象を分類する軸。ビジネス上の区分や数値条件による区分 | 会員種別（大人・子供）、遅延日数（3日未満・7日未満・7日以上） |
| **状態**           | 情報の変化を表す。ユースケースの実行によって遷移する   | 受注済、出荷準備中、配送中、完了                              |

#### 情報の精度を上げる

フェーズ2で定義した情報の精度を、バリエーションや状態モデルとの関連付けによって上げます。

**情報とバリエーションを関連付ける**

各情報が取り得るバリエーション（分類軸）を明示します。例えば、「会員」という情報が「会員種別」（大人、子供）というバリエーションを取り得ることを定義します。これにより、どの情報にどの分類軸が適用されるのかが構造として明らかになります。

**情報と状態モデルを関連付ける**

各情報が持つ状態遷移を明示します。例えば、「蔵書」という情報が「蔵書の状態」という状態モデルと関連付けられていることを定義します。

#### 条件の精度を上げる

フェーズ2で定義した条件（ビジネスルール）の精度を、バリエーションや状態モデルとの関連付けによって上げます。

**条件とバリエーションを関連付ける**

ビジネスルールの結果が、複数のバリエーションの組み合わせによって決まることを明示します。例えば、「貸出制限」という条件が「遅延日数」と「会員種別」というバリエーションと関連付けられていることを定義します。

バリエーションを明示することで、ビジネスルールを構造として捉えることができ、条件の抜け漏れや重複を検証しやすくなります。縦軸と横軸にバリエーションを整理すると、各マスがバリエーションの組み合わせごとに適用されるビジネスルールの結果を表す表構造になります。

**条件と状態モデルを関連付ける**

ビジネスルールの結果が、状態によって決まることを明示します。例えば、「貸出予約一覧出力条件」という条件が「蔵書の状態」という状態モデルと関連付けられていることを定義します。

#### 関連付けの成果

システムレイヤーまで関連付けが完了したモデルは、静的な構造（情報、状態、条件、要素同士の関連等）と動的な振る舞い（状態遷移、条件による分岐）の整合が取れた状態となります。解釈のずれを生むことなく、そのまま仕様へと展開できる設計基盤となります。

### 2.10 整合性を確認し精度を高める

**目的**: 要素間の参照関係の誤りや、定義された要素が実際のユースケースで使用されていないといった問題を早期に発見し、要件定義の整合性と網羅性を高める。

システムレイヤーの要素同士の関連付けが完了したモデル全体を見直し、矛盾を解消して整合性を高めます。

#### 不整合を検出する仕組み（「✖不整合」シート）

RDRAでは、要素同士の関係が増えるほど、定義漏れや参照ミスといった不整合が発生しやすくなります。「RDRA定義・分析Sheet」には「✖不整合」シートが用意されており、シート間の関連やシート内の関係定義に不整合がある場合、一覧として表示されます。これにより、不整合を自動的に検出し、修正すべき箇所を明確にします。

「✖不整合」シートは、大きく次の2種類の不整合検出に分類されます。

**参照された名前が定義されていない**

他シートで未定義なものをBUCシートで参照している不整合を検出します。例えば、BUC（ビジネスユースケース）シートで情報・状態・条件を参照しているが、それらが定義元シートで定義されていない場合などです。具体的には、以下の3種類のシートで検出されます。

- **情報シート**: BUCシートで参照されている情報が、情報シートで定義されていない
- **状態シート**: BUCシートで参照されている状態が、状態シートで定義されていない
- **条件シート**: BUCシートで参照されている条件が、条件シートで定義されていない

**定義されているが参照されていない**

定義元シートで定義されている要素が、BUCシートで使用されていない不整合を検出します。「定義されているが「BUC」シートで参照されていない」として一覧表示されます。解消方法は以下の通りです。

- 定義元シートの要素名が誤っている場合は、定義元シートの要素名を修正する
- BUCシートの参照名が誤っている場合は、BUCシートを修正する
- BUCシートで参照する必要がある場合は、参照を追加する
- BUCシートで参照する必要がない場合は、定義元シートの定義を削除する

#### 要素間の関係を俯瞰する仕組み（「UC_PIVOT」シート）

不整合を解消した後、ユースケースを軸に定義全体を俯瞰しながら、定義全体の妥当性を確認します。「RDRA定義・分析Sheet」には「UC_PIVOT」シートが用意されており、ユースケースとアクター、外部システム、情報の関係を一つの表で確認できます。

ユースケースと各要素の関係を、横軸と縦軸の2つの視点で確認します。

- **横軸**: ユースケースおよびビジネスユースケース単位での確認。どのようなアクターや外部システムが関係し、どのような情報を扱うかを把握できる
- **縦軸**: アクター、外部システム、情報などの各要素を軸に、どのユースケースやビジネスユースケースと関係しているかを確認する

また、アクターと業務フローの関係を俯瞰する仕組みも備えています。アクターを縦軸に、業務フローを横軸に配置し、各セルに該当するアクティビティやユースケースを表示することで、どのアクターがどの業務フローに関与しているかを一目で把握できます。ユースケースの欄が空白の場合は、該当のアクターが業務フローの中でシステムのユースケースとは関係せず、アクティビティのみと関係していることを示しています。

これにより、個々の定義だけでは見えにくい関係の偏りや抜け漏れを把握し、定義全体の妥当性を見直すことができます。

#### 整合性確認の成果

不整合の検出と全体俯瞰の仕組みを組み合わせることで、RDRAでは要件定義の整合性と網羅性を高めることができます。整合性確認まで終了することで、要件の「仕様化」が可能になります。要件の仕様化とは、要件を具体的な仕様へと落とし込むことで、開発者が実装をイメージできるレベルまでインターフェース仕様や処理ロジックを明確にすることを指します。

> **注意**: 参考書籍の『RDRA3.0 ハンドブック』では、整合性確認はプロジェクトの状況や後続プロセスによっては、必ずしも実施する必要がない旨が記載されています。

## 4. RDRAの成果物と設計プロセスとの連携

RDRAによる要件定義の成果物が、設計プロセスにどのように引き継がれるかを整理します。

### 要件定義の目的とゴール

要件定義の目的とゴールは以下のとおりです。

- **要件定義の目的**：「何を作るか（What）」を決めること
- **要件定義のゴール**：設計プロセスを円滑に進めるための明確で具体的なインプットを提供すること

RDRAで定義した各成果物が、クラス設計、データベース設計、画面・API・バッチ処理の設計へと体系的に引き継がれることで、要件定義のゴールが達成されます。

### RDRAのスコープ外となる要件定義の成果物

RDRAがスコープとしない要件定義の成果物には、以下があります。

| 成果物             | 説明                                                                                                                                                                                             |
|--------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **非機能要件一覧** | RDRAでは「非機能要求」を定義しますが、それを「非機能要件」へ整理するプロセスは規定されていません。非機能要求を取捨選択し、洗練して非機能要件一覧を別途作成する必要があります                     |
| **システム構成図** | 主に非機能要件をもとに、システム全体の構造（システムアーキテクチャ）と設計方針を定めたものです。ハードウェアやソフトウェアの主要コンポーネント、それらの相互関係、通信方式、配置などが含まれます |

### RDRAの成果物とクラス設計の関係

クラス設計（ドメインモデル設計）では、RDRAの成果物を以下のように引き継ぎます。

| RDRA成果物         | クラス設計への反映                                                                                                             |
|--------------------|--------------------------------------------------------------------------------------------------------------------------------|
| **情報モデル**     | 情報モデルで定義された「情報」がクラス（ドメインモデル）の基盤となります。情報同士の関係性がクラス間の関係性として反映されます |
| **状態モデル**     | 状態モデルで定義された「状態」がクラスの属性やステータスとして反映されます                                                     |
| **条件**           | 条件（ビジネスルール）がクラスのメソッドや振る舞いとして反映されます                                                           |
| **バリエーション** | バリエーションがクラスの属性や列挙型として反映されます                                                                         |

クラス図は、これらのクラス同士の構造や関係を可視化したもので、システムの静的な設計構造を理解するための重要な設計図です。その中でも、業務の中で扱う実体（顧客・注文・商品など）とその関係、業務ルールや振る舞いを表現したものを「ドメインモデル」と呼び、設計全体の中核となります。

### RDRAの成果物とデータベース設計の関係

データベース設計はRDRAの成果物から直接導出するものではありませんが、RDRAの情報モデル・状態モデル・バリエーションなどの要件がクラス図を経てスキーマに適切に反映されているかを確認することが重要です。

データベース設計では、永続化すべき情報をテーブルとして定義し、属性やリレーションをデータ構造として具体化します。

### RDRAの成果物と画面・API・バッチ処理の設計の関係

RDRAでユースケースと関連付けられた画面・イベント・タイマーが、それぞれ以下の設計の対象となります。

| RDRA要素     | 設計対象       |
|--------------|----------------|
| **画面**     | 画面設計       |
| **イベント** | API設計        |
| **タイマー** | バッチ処理設計 |

これらの設計では、RDRAの「条件」と「バリエーション」を参照し、業務ロジックや分岐を仕様に反映します。

また、処理で使用するデータについては、データベース設計で作成した「ER図」や「テーブル定義」を参照します。

さらに、「システム構成図」に記載された技術要素を前提とし、「非機能要件一覧」に定義された性能やセキュリティなどの非機能要件も考慮して設計します。

### 要件定義とソフトウェアアーキテクチャ設計

RDRAとソフトウェアアーキテクチャ設計は、直接の対応関係はありません。ただし、RDRAで定義された非機能要求を整理した「非機能要件一覧」を通じて、間接的に関係します。

ソフトウェアアーキテクチャは、ソフトウェアシステムの全体構造と主要な設計上の決定を体系的に示したものです。「システム構成図」で表現されるシステムアーキテクチャがハードウェア・ネットワークを含むシステム全体の構成を指すのに対し、ソフトウェアアーキテクチャはソフトウェア部分の構造や相互作用を対象にします。

ソフトウェアアーキテクチャの設計では、「システム構成図」に記載されたフレームワークやミドルウェアを前提とし、「非機能要件一覧」に定義された性能やセキュリティなどの非機能要件も考慮して設計します。

## 情報一覧の情報種類

「03 機能要件」のシステム層における情報一覧では、各情報を以下の4つの情報種類に分類します：

| 情報種類     | 説明                                         | 例                                           |
|--------------|----------------------------------------------|----------------------------------------------|
| **イベント** | システムで発生するイベント情報               | パーティ登録完了、組織登録完了               |
| **リソース** | エンティティや主要なデータリソース           | パーティ、個人、法人、組織、ユーザー         |
| **対応表**   | 2つの情報間の対応関係（N:1, 1:N, N:M）       | ロール割り当て、住所、銀行口座、パーティ関係 |
| **対照表**   | コードと名称などの対照関係（マスターデータ） | 都道府県、金融機関、祝日                     |

### 分類ガイドライン

1. **リソース**: 独立したエンティティとして存在する主要なデータ。主キーを持ち、他の情報が参照する対象。
2. **対応表**: 2つ以上のリソース間の関係性を表す情報。結合キーや外部キーを持つ。
3. **対照表**: コードと名称の対応など、マスターデータとして参照される情報。lookupテーブル的な役割。
4. **イベント**: システム内で発生する出来事を表す情報。タイムスタンプを持つ。

## 情報一覧の履歴管理要列

情報一覧には「履歴管理要」列を追加し、履歴管理が必要なリソースに「Y」、不要なリソースに「N」を出力します。

| 値    | 意味                                                 | 例                                                                                                           |
|-------|------------------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| **Y** | 状態が変化するビジネスエンティティ。履歴の追跡が必要 | パーティ、個人、法人、組織、部署、従業員、ロール、ロール割り当て、住所、銀行口座、パーティ関係、ユーザー     |
| **N** | マスターデータや構造情報。履歴の追跡が不要           | 都道府県、市区町村、町字、金融機関、支店、祝日、データベース、スキーマ、テーブル、View、カラム、インデックス |

### 判定ガイドライン

1. **Y（履歴管理要）**:
   ビジネスプロセスにおいて状態が変化し、その変化の履歴を追跡する必要があるリソース。有効期間（validFrom/validTo）を持つエンティティや、ロール割り当てなどの関係情報。
2. **N（履歴管理不要）**: 参照用のマスターデータやシステム構造情報。変更頻度が低く、履歴追跡の必要性がない情報。

| 値    | 意味                                                                          | 例                                                                                                                                         |

### 判定ガイドライン

1. **Y（証跡要）**:
