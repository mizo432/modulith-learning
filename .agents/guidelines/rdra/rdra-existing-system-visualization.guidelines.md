# RDRA 既存システムの可視化ガイドライン

本ガイドラインは、RDRA（Relationship Driven Requirement Analysis）の手法を用いて、混とんとした既存システムから役に立つ情報を抽出し可視化するための手順と方針を定義します。

既存システムの分析では、最新の資料が手に入らないことが多く、存在してもメンテナンスされていない断片的なものばかりです。ソースコードは存在するものの、それ以外のドキュメントは不足しています。また、システム全体を理解している人がおらず、各担当者は自分の担当部分しか把握していないため、全体の連携やつながりを把握している人もいません。

このような状況でも RDRA を使い、分析の目的や状況に応じたアプローチにより、効率的に全体を俯瞰できるようになります。

---

## 1. 二つの目的

既存システムの可視化の目的は大きく分けて、以下の 2 つに分かれます。

### 1.1 システム再構築に向けた既存システムの分析

- **ToBe 開発のために AsIs を理解するために**現状のシステムを理解する
- 再構築案件で AsIs を知る必要がある場合に適用

### 1.2 保守開発の品質向上に向けた既存システムの分析

- **影響度分析ができるようなベースを作成する**
- 保守開発の品質が悪くリリースの度にトラブルが起こる場合に適用

---

## 2. 何を調べるのか

### 2.1 実装（プログラム）に左右されずに仕様を明らかにする

システムを理解する上で大事なことは：

- **主要な機能は？**
- **主要な情報は？**
- **機能と情報の関係は？**

### 2.2 現実とつながりながら現実の混沌に影響されずに整理する

以下の 2 つの視点で整理します：

1. **実装に左右されずに仕様を明らかにする**
2. **RDRA の構造に当てはめて体系的に構造化する**

綺麗なモデルは結局何を表しているのか？ 現実とつながりながら現実の混沌に影響されずに整理することが重要です。

---

## 3. 方針

### 3.1 システム再構築に向けた分析の方針

**何を調べたいのか**

- 「現在のシステムはこうなっている」
- 「次のシステムの方向性はこうだ！」
- 「だから次のシステムはこうする」

**必要なことを判断出来る情報が重要！**

- 判断するためには「何を何のために」が分かる必要がある

**つまり つじつまのあう説明ができる**

- 必要以上に分析を進める必要はない

### 3.2 保守開発の品質向上に向けた分析の方針

**影響度分析ができるベースを作成する**

- 変更箇所がどの範囲に影響するかを迅速に判断できる構造を作る
- 機能・情報・画面・イベントの対応関係を明確にする
- ソースコードとのマッピングを整理する

---

## 4. 可視化のゴール

### 4.1 システム再構築向けのゴール

| カテゴリ | 内容 |
|----------|------|
| **アクター・外部システム** | 関係するアクターと外部システムを分かる範囲で洗い出す |
| **情報** | RDB のテーブルを情報とはしない。ビジネスで管理している ID を洗い出す |
| **状態** | 状態の存在を認識できた場合に洗い出す |
| **条件** | ビジネスルールを洗い出す（存在が分かる程度）。※仕組みとしてのルールは含めない |
| **バリエーション** | 区分・種別からバリエーションを整理する |
| **業務・BUC・アクティビティ** | ToBe の議論の広がりのために業務を網羅的に出す。アクティビティは UC を出すためのもので正確でなくてよい |
| **UC 周辺** | 調査で明らかになった画面とイベントを適用させる。アクター／画面から UC を洗い出す。外部システム／イベントから UC を洗い出す |

### 4.2 保守開発向けのゴール

| カテゴリ | 内容 |
|----------|------|
| **機能・画面の対応** | 機能と画面の対応関係を明確にする |
| **情報・テーブルの対応** | ビジネス上の情報と RDB テーブルの対応を整理する |
| **ソースコードのマッピング** | 機能・UC・画面・情報とソースコードの対応を整理する |
| **影響範囲の可視化** | 変更がどの範囲に影響するかを判断できる構造を作る |

---

## 5. トップダウン分析

システムの外側から内側に向かって分析するアプローチです。

### 5.1 画面から整理する

**手順**

1. **① 画面を分類し、ユースケース（UC）を求める**
   - 現在使われている画面をベースに整理する
   - 画面の役割ごとに分類する（入力・照会・一覧・レポートなど）
   - 各画面から UC を導出する

2. **② アクター／画面から UC を洗い出す**
   - どのアクターがどの画面を使うかを整理する
   - 画面操作から UC の名前と説明を導出する

### 5.2 イベントから整理する

**手順**

1. **① イベントを分類し、ユースケース（UC）を求める**
   - 外部システムとの連携ポイントを整理する
   - イベントの種類（同期・非同期・バッチ・リアルタイム）を分類する

2. **② イベントと外部システムの関係を整理する**
   - どの外部システムからどのイベントが来るかを整理する
   - 外部システム／イベントから UC を洗い出す

3. **③ イベントを分類しユースケースを求める（画面から求めた UC を再利用）**
   - 既に画面分析で導出した UC と統合する
   - 重複する UC は統合する

### 5.3 データから整理する

**手順**

1. **① DB のスキーマを整理する**
   - DB のスキーマ情報を出力し、ビジネスにつながる（ID が識別できる）データ（情報）を洗い出す
   - RDB のテーブルをそのまま情報とはしない
   - ビジネス上で管理されている ID を持つデータを情報として特定する

2. **② ファイル一覧を分類し、役割別（情報）に整理する**
   - 外部ファイル、バッチファイル、設定ファイルなどを分類する
   - 各ファイルがどのような情報を持つかを整理する

3. **③ 情報と UC をつなぐ**
   - 各情報がどの UC によって操作されるかを整理する
   - 情報の作成・更新・削除・参照を行う UC を特定する

4. **④ 情報から状態を洗い出し、遷移に UC を当てはめる**
   - 情報に状態遷移が存在するかを確認する
   - 状態間の遷移をどの UC が引き起こすかを整理する

---

## 6. ボトムアップ分析

ソースコードと格納しているフォルダーを分析するアプローチです。

### 6.1 フォルダーの分析

**手順**

- ソースコードと格納しているフォルダーを分析する
- フォルダー構成やプログラムの分割単位などから仕様として取り出せるものを探します
- トップダウンで分析した BUC や UC などの名称とフォルダーの対応関係を整理し、ソースコードへのインデックスとして使用します

### 6.2 ソースコードの分析

**手順**

- フォルダー分析の結果をもとにソースコードを分析する
- トップダウンで分析した UC、画面、イベント、情報とソースコードの対応を整理する
- 各ソースコードファイルがどの UC や情報に対応するかをマッピングする

---

## 7. 手に入る資料から整理

代表的な資料と RDRA の対応関係を活用し、手に入ったものをベースとして整理します。対応するものがなければ類推して整理します。

### 7.1 資料と RDRA の対応関係

| 資料 | RDRA での対応 | 整理方法 |
|------|---------------|----------|
| **機能一覧** | 業務・BUC・UC | 大中小の分類を一旦、業務・BUC・UC に当てはめる。全体を俯瞰しながら適切な単位に変えていく |
| **画面一覧** | 画面・UC | 現在使われている画面をベースに整理する |
| **インターフェース一覧** | 外部システム・イベント | なければ外部企業との資料から整理する |
| **テーブル一覧・ER 図** | 情報・状態 | スキーマ情報から整理する |
| **機能詳細** | UC・情報・状態 | 機能一覧に対応する形で詳細な機能を記述した資料から整理する |

### 7.2 資料が不足している場合の対応

- 手に入ったものをベースとして整理する
- 対応するものがなければ類推して整理する
- ソースコードから逆引きして補完する
- 担当者へのヒアリングで補完する

---

## 8. 分析アプローチの選択ガイド

### 8.1 目的に応じたアプローチ

| 目的 | 推奨アプローチ | 重点項目 |
|------|----------------|----------|
| **システム再構築** | トップダウン分析 | 業務・BUC・UC・情報の網羅的整理 |
| **保守開発品質向上** | ボトムアップ分析 + ソースコードマッピング | 機能・画面・情報とソースコードの対応 |
| **両方** | トップダウン + ボトムアップの併用 | 両方の結果を統合し相互検証 |

### 8.2 利用可能な資料に応じたアプローチ

| 利用可能な資料 | 推奨アプローチ |
|----------------|----------------|
| 機能一覧・画面一覧がある | トップダウン分析から開始 |
| ソースコードのみ | ボトムアップ分析から開始 |
| 断片的な資料のみ | 手に入る資料から整理し、不足分を類推 |
| 資料がほぼない | ソースコード分析 + 担当者ヒアリング |

## 10. ベストプラクティス

### 10.1 分析の実施

- **目的に合わせた範囲で**: 必要以上に分析を進める必要はない。つじつまのあう説明ができるレベルを目指す
- **RDRA の構造を活用する**: 入手可能な情報を RDRA の構造に当てはめて体系的に構造化する
- **複数のアプローチを組み合わせる**: トップダウンとボトムアップの結果を相互検証する
- **ビジネス視点を持つ**: RDB のテーブルをそのまま情報とせず、ビジネスで管理している ID を情報として特定する

### 10.2 ドキュメント化

- **RDRA ダイアグラムを使用する**: 利用シーン図、ユースケース図、情報 ER 図、ステートマシン図などを使用して視覚化する
- **RDRASheet を使用する**: 表形式で RDRA モデルを定義し、整合性を検証する
- **バージョン管理**: 分析ドキュメントは Git でバージョン管理し、変更履歴を追跡可能にする

### 10.3 統合と検証

- **トップダウンとボトムアップの統合**: 両方の分析結果を統合し、矛盾や不一致を特定する
- **関係者との確認**: 分析結果を関係者と共有し、認識のズレを是正する
- **反復的な改善**: 分析結果を反復的に見直し、精度を高める
