# 見積もりガイドライン

## 概要

本ガイドラインは、IPA/SEC「ソフトウェア開発見積りガイドブック」に基づき、システム開発プロジェクトにおけるソフトウェア開発の見積り活動の基本的な考え方・手順・方法をまとめたものです。ユーザ企業とベンダ企業の双方が相互に納得できる見積りを実現し、プロジェクトの健全な運営を可能にするための指針を提供します。

---

## 1. 見積りの基本原則

### 1.1 見積りの成功要因

見積りに当たっての成功要因は、次の4点に尽きます。

1. **ユーザとベンダは、必要な情報を互いに出しあったうえで、その妥当性を互いに確認し合う**
2. **ユーザは、見積りを確定するうえで必要な情報を可能な限り示す**
3. **ベンダは見積りの根拠を明確にする**
4. **プロジェクトには常にリスクがつきものであることをお互い理解し、ユーザとベンダ双方が協力し、リスクを極力早期に小さくする**

### 1.2 見積りにおける3つの課題

見積り活動において解決すべき基本的な課題は以下の3点です。

1. **ソフトウェア規模の尺度に関する「ことば」の共通理解**
   - ファンクションポイント（FP）、ソースコード行数、ユースケースなど、それぞれに基づいた見積り結果が何を表しているのかを共通に理解できることが必要
2. **ソフトウェア開発にかかわる「影響要因」がコストへ及ぼす影響についての認識の共有、抜けの防止**
   - 品質・信頼性・セキュリティ・複雑度・先進性などの要件やユーザ・ベンダ間の意思疎通などの要因により、通常の水準との差に応じてコストが上下することを関係者で共有する
   - 考慮しておくべき事項に抜けがないか確認し、コントロールできるのは誰か、お互いの役割は何かを共通に理解する
3. **見積りにおける不確実な要素をプロジェクトにかかわるリスクとして関係者で共有し、相互協力によるコントロール**
   - 要求内容の不確実性、新規技術の導入リスクなどを共有し、プロジェクトの破綻をきたさないよう協力する

### 1.3 見積りの定義

本書でいう「見積り」とは、規模、工数、工期、品質（信頼性、性能など）、コストなどのさまざまな要素を広く対象とするものです。特に**規模、工数、工期、コスト**の見積りに焦点を当てます。品質は、それぞれの関係に影響を及ぼす要因として捉えます。

## 2. 見積りの手順

### 2.1 見積りの基本フロー

見積りは、以下の順序で実施します。

```
┌─────────────────────────────────────────────────┐
│  ① 要件の洗い出しと記述（ベースライン定義）       │
│      ↓                                          │
│  ② 規模見積り                                    │
│      ↓                                          │
│  ③ 変動要因の設定                                │
│      ↓                                          │
│  ④ 工数・コスト見積り                            │
│      ↓                                          │
│  ⑤ 工期見積り                                    │
│      ↓                                          │
│  ⑥ 複数見積りによる相互検証                      │
│      ↓                                          │
│  ⑦ プロジェクト計画の決定                        │
└─────────────────────────────────────────────────┘
```

### 2.2 各ステップの詳細

#### ステップ1: 要件の洗い出しと記述

- 機能要件および非機能要件を洗い出し、記述する
- 全体のすべてが確定しなくても、ある程度確からしい部分的な情報が明らかになった時点で見積る
- 洗い出した要件を記述して確からしさを評価し、見積りにインプットする要件の**ベースライン**を定義する

#### ステップ2: 規模見積り

- 見積りにインプットする情報は、見積り時期により変わる
- 見積り時期に応じて利用できるインプット情報に基づき、採用する見積り手法を選択する
- 主として使用する手法と、見積り結果の比較・妥当性の評価に使用する手法とに区分けする

#### ステップ3: 変動要因の設定

- 規模見積り後または並行して、プロジェクトの特性やリスクなどに起因するベースラインからの変動率を変動要因ごとに設定（見積り）し、その総和を求める

#### ステップ4: 工数・コスト見積り

- 規模見積りの結果を入力として、工数・コストを見積る
- 組織における過去のプロジェクトデータに基づいて、ベースラインと変動要因を設定する

#### ステップ5: 工期見積り

- 工数見積りの結果を入力として、工期を見積る
- 工数と工期の関係モデルを用いて算出する

#### ステップ6: 複数見積りによる相互検証

- 「銀の弾はない」— 見積り手法にも絶対のものはない
- ① 類推法、② 積み上げ法、③ パラメトリック法の三つの方法で相互検証することが現実的な実践
- 大幅な違いが生じた場合は、必要に応じて見直しを行う

#### ステップ7: プロジェクト計画の決定

- 複数の見積りの結果に基づき、プロジェクト計画をシミュレートする
- それぞれの計画の良否を比較して、いずれを採用するか決定する

## 3. 規模見積り

### 3.1 規模見積りの手法

規模見積りには、主に以下の3つの手法があります。

| 手法 | 説明 | 前提条件 |
|------|------|----------|
| **類推法** | 類似した過去のプロジェクトの実績から推定 | 類似プロジェクトの実績データが必要 |
| **積み上げ法** | 各機能・各作業を細かく分解し、個別に見積ったものを合計 | 要件の詳細が一定程度確定していること |
| **パラメトリック法** | 規模と工数の関係式（統計モデル）を用いて推定 | 実績データベースが必要 |

### 3.2 規模の尺度

規模を計測するための代表的な尺度は以下の通りです。

- **ファンクションポイント（FP）**: ユーザ視点での機能規模
- **ソースコード行数**: 実装視点での規模
- **オブジェクト数、データ項目数、画面数・帳票数、文書量**など

### 3.3 規模見積りの手順

1. **機能要件の分析**: 外部入力（EI）、外部出力（EO）、外部問い合わせ（EQ）、内部論理ファイル（ILF）、外部インターフェースファイル（EIF）を特定
2. **未調整FPの算出**: 各データファンクションおよびトランザクションファンクションの複雑度に基づき算出
3. **調整FPの算出**: 14つの一般システム特性（GSC）を評価し、値掛係数を適用

## 4. 工数・コスト見積り

### 4.1 基本的な活動

工数・コストを規模から見積る場合、以下の2つの活動を行い、計算方法を確立しておくことが必要です。

#### (a) ベースラインの設定

- 組織における過去の実績データなどに基づいて、見積りの基準値となるベースラインを設定する
- 規模と工数、規模と金額などの関係のベースラインは、基本的に組織における過去の実績データの分析に基づき設定する

#### (b) ベースラインからの変動要因の設定

- 組織横断的に個別のプロジェクトで共通となる変動要因を洗い出す
- その影響度合いの基準と個別のプロジェクトでの評価方法を確立する
- 実際の見積りでは、ベースラインを基準として、さまざまな変動要因を評価して変動値を求める

### 4.2 生産性の単位

見積り対象が工数かコストかに応じて、以下の単位を設定します。

- **人月／規模**: 単位規模あたりの開発にかかる工数（人時など）
- **金額／規模**: 単位規模あたりの開発にかかる金額

### 4.3 規模と工数の関係式

基本的な関係式としては、以下の2つが主に利用されています。

- **線形関係**: 工数 ＝ α × 規模
- **累乗関係**: 工数 ＝ α × 規模^β

### 4.4 ベースライン設定時の注意事項

- ベースラインは組織の過去の実績データに基づいて設定する
- 単一プロジェクトの実績ではなく、複数のプロジェクトのデータを統計的に分析する
- 外れ値の処理方法を事前に定義する
- データの収集時期・集計方法を一貫させる

## 5. 工期見積り

### 5.1 工数と工期の関係

工数から工期を見積る場合、以下の要素を考慮します。

- **開発者数**: 同時並行で作業できる人数
- **コミュニケーションオーバーヘッド**: 開発者数が増えるとコミュニケーションコストが増加
- **タスクの依存関係**: 並行できない作業がある場合

### 5.2 工期見積りのモデル

基本的な工期見積りのモデルは以下の通りです。

```
工期 ＝ 工数 ÷ （開発者数 × 生産性係数）
```

ただし、開発者数と工期の関係は単純な逆比例ではなく、以下の点に注意が必要です。

- 「9人の女で1ヶ月で赤ちゃんを生むことはできない」— 開発者数を増やしても工期が比例して短縮されるわけではない
- コミュニケーションコストは開発者数の2乗に比例して増加する

## 6. 見積り活動のサイクル

### 6.1 見積り活動の5つのフェーズ

見積り活動は、以下のサイクルで継続的に改善していきます。

```
┌─────────────────────────────────────────────┐
│  ① 見積り手順の確立                          │
│      ↓                                      │
│  ② 見積りの実践                              │
│      ↓                                      │
│  ③ プロジェクトデータ収集                    │
│      ↓                                      │
│  ④ 計画と実績の差異分析                      │
│      ↓                                      │
│  ⑤ 差異分析結果のフィードバック              │
│      ↓                                      │
│  （①に戻る）                                 │
└─────────────────────────────────────────────┘
```

### 6.2 計画と実績の差異分析

プロジェクト終了時の差異分析は、どのような組織でも最低限実施する必要があります。

- **プロジェクト進行中**: リアルタイムに計画と実績の差をチェックし、変動要因の発生状況を把握
- **プロジェクト終了時**: 見積り結果（計画）と実績値との間の差異の原因を探り、差異の発生を次回から抑える方策を検討

### 6.3 差異分析のプロセス

1. **実施した見積りの振り返り**: いつ振り返り、どういう知見を得、それをどこに活かすのかを整理
2. **再見積り**: 初見積りの誤差を補正し、見積り自体をブラッシュアップ
3. **知見の蓄積**: 個別プロジェクトで学んだことをまとめ、将来にその知見を活用できるように整備

## 7. 見積り活動に関する組織成熟度（EML）

### 7.1 見積り成熟度のレベル

組織の見積り能力の成熟度（Estimation Maturity Level: EML）は、以下の5レベルで定義されます。

| レベル | 名称 | 特徴 |
|--------|------|------|
| **EML1** | 初期レベル | 見積りが恣意的に行われる。再現性がない |
| **EML2** | 繰り返し可能レベル | 基本的な見積り手順が確立され、プロジェクト間で再現可能 |
| **EML3** | 定義済みレベル | 組織横断的な標準手順が確立され、プロジェクトに応じて適応可能 |
| **EML4** | 管理済みレベル | 見積り精度が定量的に管理され、目標値が設定されている |
| **EML5** | 最適化レベル | 継続的な改善が制度化され、新しい手法の導入が積極的に行われる |

### 7.2 成熟度向上のための活動

- **EML1 → EML2**: 見積り手順の文書化、過去のプロジェクトデータの収集
- **EML2 → EML3**: 組織横断的な標準手順の確立、変動要因の定義
- **EML3 → EML4**: 見積り精度の定量的管理、ベースラインの統計的分析
- **EML4 → EML5**: 継続的改善プロセスの制度化、新手法の研究・導入

## 8. 見積り手法の選択ガイド

### 8.1 手法選択の基準

見積り手法の選択は、以下の要素に基づいて行います。

| 要素 | 考慮事項 |
|------|----------|
| **見積り時期** | 早期段階では類推法、詳細が確定すれば積み上げ法 |
| **要件の明確さ** | 要件が不明確な場合は複数の手法で相互検証 |
| **組織の成熟度** | 実績データが蓄積されている場合はパラメトリック法 |
| **プロジェクトの規模** | 小規模では類推法、大規模では積み上げ法またはパラメトリック法 |

### 8.2 代表的な見積り手法

| 手法 | 概要 | 適用時期 |
|------|------|----------|
| **類推法（アナロジー法）** | 類似プロジェクトの実績から類推 | 要件が概ね明確な段階 |
| **積み上げ法（ボトムアップ）** | 各作業を細かく分解して合計 | 要件が詳細に確定した段階 |
| **パラメトリック法** | 統計モデルに基づく推定 | 実績データベースが整備されている場合 |
| **COCOMO** | コスト影響要因に基づくモデル | 中〜大規模プロジェクト |
| **ファンクションポイント法** | 機能規模に基づく推定 | ビジネスアプリケーション |
| **プランガンニング** | 理想時間を基準に調整 | 早期段階の概算見積り |

## 9. プロジェクトデータ収集体制

### 9.1 データ収集の重要性

定量的な見積りの成功のためには、プロジェクトデータの精度の高い測定が前提となります。

### 9.2 収集すべきデータ

- **規模データ**: ファンクションポイント、ソースコード行数など
- **工数データ**: 各フェーズ・各作業別の実際の工数
- **工期データ**: 各フェーズ・各作業別の実際の工期
- **品質データ**: 欠陥数、欠陥密度など
- **変動要因データ**: 品質要求レベル、技術的複雑度など

### 9.3 データ収集のポイント

- 開発現場にデータの精度の重要性を理解してもらう
- 確実なフィードバックによるデータ収集のインセンティブを維持する
- データ収集の負荷を低減するため、ツールなどの利用を工夫する
- 収集データが実態を反映していることを確認する

## 10. 見積りの実践における留意点

### 10.1 見積り時期とリスク

| 見積り時期 | リスク | 対応 |
|------------|--------|------|
| **早期段階** | 要件が不明確、規模の誤差が大きい | 複数の手法で相互検証、リスクマージンを設定 |
| **要件定義後** | 非機能要件の不確実性 | 変動要因を詳細に評価 |
| **設計後** | 技術的リスク | プロトタイピングによる検証 |

### 10.2 見積りの不確実性の管理

- 見積り値には常に不確実性（誤差範囲）を付随させる
- 信頼区間を用いて「〜%の確率でこの範囲内」と表現する
- プロジェクトの進行に伴い、不確実性を徐々に低減させる

### 10.3 契約形態と見積り

- 見積りの確からしさに応じて、適切な契約形態を選択する
- 要件が不明確な場合は、時間材料契約またはアジャイル契約を検討する
- 要件が明確な場合は、固定価格契約を検討する

## 11. アジャイル開発における見積り

### 11.1 アジャイル見積りの特徴

- スプリント単位での見積り
- 相対見積り（ストーリーポイント）の活用
- 速度（Velocity）に基づく予測

### 11.2 アジャイル見積りの手順

1. **ストーリーポイントによる相対見積り**: 複雑度・不確実性・作業量を総合的に評価
2. **スプリントプランニング**: スプリントで実行可能なバックログアイテムを選択
3. **速度の測定**: 過去のスプリント実績に基づく速度を算出
4. **リリース予測**: 速度に基づき、リリース時期を予測

---

## 12. 見積り精度の向上

### 12.1 精度向上のための活動

1. **実績データの蓄積**: 過去のプロジェクトデータを体系的に収集・管理
2. **ベースラインの更新**: 定期的に組織のベースラインを見直し・更新
3. **変動要因の精緻化**: 新たな変動要因の発見と影響度の定量
4. **差異分析の徹底**: 計画と実績の差異を分析し、原因を特定
5. **フィードバックループの確立**: 差異分析の結果を見積り手順に反映

### 12.2 精度の評価指標

- **誤差率**: （実績値 − 見積り値）÷ 見積り値 × 100
- **過少見積り率**: 実績値が見積り値を上回った割合
- **信頼区間内収容率**: 実績値が信頼区間内に収まった割合
