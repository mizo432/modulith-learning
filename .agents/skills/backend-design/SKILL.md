### Backend Design Guide (`backend-design`)

このスキルは、 **modulith-learning** リポジトリのバックエンド（`backend`
）において、アーキテクチャ設計、モジュール分割、ドメインモデル設計、層間の依存関係管理を行う際に適用する設計ガイドラインです。

---

### 1. いつこのスキルを使用するか (When To Use)

- 新規モジュールの設計・実装を行うとき
- 既存モジュールのアーキテクチャ見直しやリファクタリングを行うとき
- ドメインモデル（エンティティ、値オブジェクト）の設計を行うとき
- モジュール間の境界（公開API/SPI）を定義するとき
- 層構成（Domain / useCase / Infrastructure / Presentation）に沿った実装を行うとき
- リポジトリパターン、ドメインイベント、ドメインサービスの設計を行うとき
- 例外処理戦略（`BusinessException`, `SystemException`, `ResultMessage`）を設計するとき
- Null安全性（JSpecify）の設計ルールを適用するとき

---

### 2. アーキテクチャ設計原則 (Architecture Design Principles)

#### 2.1 モジュラーモノリス (Spring Modulith)

- **モジュール独立性**: 各モジュールは独立して開発・テスト・デプロイ可能な単位とする。
- **循環依存禁止**: `ApplicationModules.of(ModulithDemoApplication.class).verify()` で循環依存を検出。
- **モジュール粒度**: 業務ドメインごとにモジュールを分割し、共通機能は `shared` モジュールに集約。

#### 2.2 ドメイン駆動設計 (DDD)

- **エンティティ**: 一意のIDを持ち、ライフサイクルを通じて同一性を保つオブジェクト。
- **値オブジェクト**: 不変（Immutable）で、プロパティの組み合わせで同一性を判定するオブジェクト。
- **ドメインサービス**: エンティティや値オブジェクトに収まらないドメインロジックを収容。
- **ドメインイベント**: ドメイン内で発生した重要な事象を非同期で通知するパターン。
- **リポジトリ**: ドメインオブジェクトの永続化を抽象化するインターフェース。

#### 2.3 オニオンアーキテクチャ (Onion Architecture)

依存関係は内側（Domain）に向き、外側（Infrastructure/Presentation）は内側に依存する。

| 層                 | 責務                                                                                         |
|:-------------------|:---------------------------------------------------------------------------------------------|
| **Domain**         | エンティティ、値オブジェクト、ドメインイベント、ドメインサービス、リポジトリインターフェース |
| **useCase**        | ユースケース、Command/Queryサービス、アプリケーションロジック                                |
| **Infrastructure** | JPA/Hibernate実装、リポジトリ実装、外部サービス通信、Flywayマイグレーション                  |
| **Presentation**   | RESTコントローラー、リクエスト/レスポンスDTO、バリデーション、例外ハンドラー                 |

### 3. モジュール設計規則 (Module Design Rules)

#### 3.1 パッケージ構成

```
undecided.<domain>.<module>
├── domain          # ドメイン層（エンティティ、値オブジェクト、ドメインサービス）
├── useCase         # ユースケース層（アプリケーションロジック）
├── infrastructure  # インフラ層（リポジトリ実装、JPAエンティティ）
├── presentation    # プレゼンテーション層（RESTコントローラー、DTO）
└── internal        # モジュール内部実装（他モジュールから参照禁止）
```

#### 3.2 公開APIと内部実装の分離

- **公開API/SPI**: 他モジュールから利用されるインターフェースは公開パッケージに配置。
- **internalパッケージ**: モジュール内部のロジックは `internal` パッケージに配置し、他モジュールから直接参照禁止。
- **モジュール境界テスト**: モジュール間の不正な依存関係をテストで検出。

#### 3.3 モジュール間通信

- **同期通信**: 公開API/SPIを介した直接呼び出し。
- **非同期通信**: Spring Modulithのドメインイベントを介した疎結合通信。
- **イベントリスナー**: `@EventListener` アノテーションでドメインイベントを購読。

### 4. ドメインモデル設計 (Domain Model Design)

#### 4.1 エンティティ設計

- **ID生成**: Snowflakeアルゴリズムによる分散IDを使用。
- **不変条件**: エンティティの作成・更新時にビジネスルールを検証。
- **事前条件チェック**: `*Precondition` クラスで入力値を検証。
- **Lombok活用**: `@Value`（値オブジェクト）、`@Getter`（エンティティ）でボイラープレートを削減。

#### 4.2 値オブジェクト設計

- **不変性**: 値オブジェクトは `final` クラスとし、プロパティは `final` フィールドで定義。
- **equals/hashCode**: プロパティの組み合わせで同一性を判定。
- **バリデーション**: コンストラクタで事前条件をチェックし、不正な状態の生成を禁止。

#### 4.3 リポジトリパターン

- **インターフェース**: Domain層にリポジトリインターフェースを定義。
- **実装**: Infrastructure層でSpring Data JPAを使用して実装。
- **クエリメソッド**: 単純なクエリはメソッド名から生成、複雑なクエリは `@Query` アノテーションを使用。

### 5. 例外処理設計 (Exception Handling Design)

#### 5.1 例外階層

| 例外クラス          | 用途                     | HTTPステータス |
|:--------------------|:-------------------------|:---------------|
| `BusinessException` | ビジネスルール違反       | 4xx            |
| `SystemException`   | システムエラー           | 5xx            |
| `ResultMessage`     | 処理結果のメッセージ伝達 | -              |

#### 5.2 例外ハンドリング戦略

- **Domain層**: ビジネスルール違反時に `BusinessException` をスロー。
- **useCase層**: 例外をキャッチせず、上位層に伝播。
- **Presentation層**: `@ControllerAdvice` でグローバル例外ハンドリング。
- **ResultMessage**: 処理結果をメッセージとして返すパターン。

### 6. Null安全性設計 (Null Safety Design)

#### 6.1 JSpecifyアノテーション

- `@Nullable`: Null許容の型を示す。
- `@NonNull`: Null不許容の型を示す。
- `@NonNullApi`: パッケージレベルでデフォルトをNull不許容に設定。

#### 6.2 Null安全性ルール

- **メソッド引数**: デフォルトで `@NonNull` とし、Null許容の場合は明示的に `@Nullable` を付与。
- **戻り値**: Collectionは空コレクションを返し、Nullを返さない。
- **Optional**: 存在しない可能性がある単一オブジェクトは `Optional` でラップ。

### 7. データベース設計 (Database Design)

#### 7.1 スキーマ分離

- **事業領域・業務領域ごとにスキーマ分離**: Flywayで事業領域・業務領域ごとにマイグレーションを管理。
- **スキーマ命名**: 事業領域区分によってスキーマ名の付け方が異なります。
    - **事業領域区分が「汎用」の場合**: `undecided_<業務領域コード>` の形式で命名。
    - **事業領域区分が「汎用」以外の場合**: `undecided_<事業領域コード>` の形式で命名（例:
      `undecided_as`,
      `undecided_do`）。
    - 事業領域コードの詳細は事業領域一覧.tsvを、業務領域コードの詳細は業務領域一覧.tsvを参照してください。

  > 参照: `docs/11.事業領域/事業領域一覧.tsv`
  > 参照: `docs/12 RDRA モデル/02 業務領域/業務領域一覧.tsv`

#### 7.2 JPAエンティティ設計

- **テーブルマッピング**: `@Table` アノテーションでスキーマとテーブル名を明示。
- **インデックス**: 頻繁に検索されるカラムにインデックスを適用。
- **外部キー**: モジュール間の外部キー制約は避ける（スキーマ分離のため）。

---

### 8. API設計 (API Design)

#### 8.1 REST API規約

- **URL命名**: 名詞の複数形でリソースを表現（例: `/api/customers`）。
- **HTTPメソッド**: GET（取得）、POST（作成）、PUT（更新）、DELETE（削除）。
- **ステータスコード**: 200（成功）、201（作成）、400（クライアントエラー）、404（NotFound）、500（サーバーエラー）。

#### 8.2 DTO設計

- **リクエストDTO**: バリデーションアノテーションを付与。
- **レスポンスDTO**: 機密情報を除外し、API消費者に必要な情報のみを公開。
- **Mapper**: DTOとドメインオブジェクトの変換は専用のMapperクラスで管理。

---

### 9. 設計チェックリスト (Design Checklist)

設計時・実装時に以下の項目を確認してください。

- [ ] モジュール境界が明確か（公開API/SPIとinternalの分離）
- [ ] 層構成がオニオンアーキテクチャに沿っているか
- [ ] ドメインモデルの不変条件が保護されているか
- [ ] 値オブジェクトが不変（Immutable）か
- [ ] リポジトリインターフェースがDomain層に定義されているか
- [ ] 例外処理が適切に階層化されているか
- [ ] Null安全性がJSpecifyで保証されているか
- [ ] モジュール間の循環依存がないか
- [ ] ドメインイベントで疎結合な通信が実現されているか
- [ ] APIのステータスコードとレスポンス形式が一貫しているか
