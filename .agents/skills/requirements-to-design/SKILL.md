### 要件定義書から詳細設計書への変換スキル (`requirements-to-design`)

このスキルは、**要件定義書**（`docs/22 要件定義書/`）を基に**詳細設計書**（`docs/23 詳細設計書/`）を作成するためのガイドラインです。RDRAモデル（情報・UC・画面・状態・条件・バリエーション）からデータベース設計、API設計、バッチ設計、フロントエンド設計を体系的に導出します。

---

### 1. いつこのスキルを使用するか (When To Use)

- 要件定義が完了し、詳細設計フェーズに入ったとき
- 新規事業領域・業務領域の詳細設計書を作成するとき
- 要件定義の変更を詳細設計に反映するとき
- RDRAモデルから実装可能な設計書を導出したいとき

---

### 2. 基本概念

#### 要件定義書と詳細設計書の関係

```
要件定義書 (docs/22)                    詳細設計書 (docs/23)
┌──────────────────────────┐           ┌──────────────────────────┐
│ 01.システム価値           │           │ 01 データベース設計       │
│   - アクター             │           │   - テーブル一覧          │
│   - 外部システム          │    ──►    │   - テーブルカラム定義    │
│   - 要求                  │           │   - viewカラム定義        │
│                           │           │                          │
│ 02.外部環境               │           │ frontend/                 │
│   - 業務                  │    ──►    │   - 画面設計              │
│   - BUC                   │           │                          │
│                           │           │ backend/                  │
│ 03.システム境界            │    ──►    │   - api/ (API設計)        │
│   - ユースケース           │           │   - batch/ (バッチ設計)   │
│                           │           │                          │
│ 04.システム                │           │                          │
│   - 情報                  │    ──►    │ (データベース設計)         │
│   - ステート              │    ──►    │ (状態遷移設計)            │
│   - 画面                  │    ──►    │ (画面設計・API設計)        │
│   - 条件                  │    ──►    │ (ビジネスルール実装)       │
│   - バリエーション        │    ──►    │ (列挙型定義)              │
└──────────────────────────┘           └──────────────────────────┘
```

#### 変換の基本原理

| 要件定義要素 | 詳細設計要素 | 変換ルール |
|------------|------------|-----------|
| 情報 | テーブル | 情報をテーブルに変換、属性をカラムに変換 |
| 情報間の関連 | 外部キー | 親子関係は子テーブルに親のIDを保持 |
| 状態モデル | 列挙型カラム | 状態をENUMまたはVARCHARカラムとして定義 |
| バリエーション | 列挙型カラム | バリエーションをENUMカラムとして定義 |
| UC (画面経由) | REST API | 画面とUCの組み合わせからAPIエンドポイントを導出 |
| UC (外部システム経由) | バッチ/API | 外部システムとの連携からバッチまたはAPIを導出 |
| 条件 | ビジネスルール | 条件をアプリケーションロジックとして実装 |
| 画面 | フロントエンド設計 | 画面属性からUIコンポーネントを導出 |

### 7. 重要ルール (Important Rules)

1. **要件定義を忠実に反映する**:
   - 要件定義にない機能を詳細設計に追加しない
   - 要件定義にある機能を詳細設計から漏らさない

2. **既存スキルのガイドラインに従う**:
  - データベース設計は `data-design` スキルに従う
  - API設計は `api-design` スキルに従う
  - バックエンドアーキテクチャは `backend-design` スキルに従う
  - フロントエンド設計は `frontend-design` スキルに従う

3. **情報とテーブルの対応**:
   - 1つの情報は原則として1つのテーブルに対応
   - 親子関係がある情報は親と子のテーブルに分割
   - 属性で構造を持っているものは別テーブルとして抜き出す

4. **UCとAPIの対応**:
   - 画面経由のUCはREST APIとして導出
   - 外部システム経由のUCはバッチまたはAPIとして導出
   - 1つのUCは1つ以上のAPIエンドポイントに対応可能

5. **命名規則の一貫性**:
   - テーブル名は情報のエンティティ名を使用
   - APIパスはリソース名（名詞の複数形）を使用
   - 事業領域コードは `docs/11 事業領域/事業領域一覧.tsv` を参照

6. **スキーマ分離**:
   - 事業領域・業務領域ごとにスキーマを分離
   - スキーマ名は `undecided_<事業領域コード>` または `undecided_<業務領域コード>`
