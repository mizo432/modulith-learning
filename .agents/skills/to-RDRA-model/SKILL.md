# RDRA (Relationship Driven Requirement Analysis) Skill
---

## Purpose

このSkillは、要求を整理し、

1. RDRAによる4レイヤーの要求モデル構築
2. 3フェーズ9ステップの要件定義プロセスの実行
3. ダイアグラムによる可視化と整合性検証
4. DDDモデル候補の抽出
5. 要求の抜け漏れ・矛盾・重複の検証
6. サブドメイン毎にユースケース図を作成
7. ユースケース毎にユースケース記述を作成
8. ユースケースに現れる 名詞 / 名詞句を元にサブドメイン毎に用語辞書を作成

をまとめる。

**RDRA**（ラドラ）は、「Relationship Driven Requirement
Analysis」の略称で、モデルベースの要件定義手法です。

RDRAは、システムを構成する要素同士の関係（Relationship）を定義することで、システム全体の構造を明確に捉え、可視化します。これにより、要件の抜け漏れや矛盾を早期に発見し、「なぜ必要なのか」を説明可能な納得感のある要件定義を実現します。

AIは要求を一方的に決定してはならない。
AIは「候補の生成」「質問」「整理」「検証」を行い、
最終的な要求の確定はユーザーが行う。

# Core Concept

## RDRAの4つのレイヤー

RDRAはシステム全体を以下の4つのレイヤーで捉えます。各レイヤーは内側から外側に向けて「Why」の依存関係を持ち、下位レイヤーから上位レイヤーに向かって「なぜ？」と問いかけることで、要件に論理的なつながりを持たせます。

```text
┌─────────────────────────────────────────────────────────────┐
│                     Why 依存関係                            │
│  (システム) ← (システム境界) ← (システム外部環境) ← (システム価値) │
└─────────────────────────────────────────────────────────────┘

┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
│  システム     │   │ システム境界  │   │ システム外部  │   │ システム価値  │
│  レイヤー     │   │ レイヤー      │   │ 環境レイヤー  │   │ レイヤー      │
│              │   │              │   │              │   │              │
│ ・情報       │   │ ・ユースケース│   │ ・業務       │   │ ・要求       │
│ ・状態       │   │ ・画面        │   │ ・BUC        │   │ ・アクター    │
│ ・条件       │   │ ・イベント    │   │ ・アクティビ │   │ ・外部システム│
│ ・バリエーション│  │              │   │ ティ         │   │              │
└──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
```

### 各レイヤーの概要

| レイヤー                     | 説明                                                                                     | 主な要素                                        |
|------------------------------|------------------------------------------------------------------------------------------|-------------------------------------------------|
| **システム価値レイヤー**     | システムが実現すべき価値。誰にとって、どのような価値を提供するか                         | 要求（機能/非機能）、アクター、外部システム     |
| **システム外部環境レイヤー** | システムがどのように使われるか。誰が何の業務を行い、どんな価値を提供するか               | 業務、ビジネスユースケース(BUC)、アクティビティ |
| **システム境界レイヤー**     | ユーザーや外部システムと開発対象システムとの接点。誰がどこに接点を持ち、何を入出力するか | ユースケース(UC)、画面、イベント                |
| **システムレイヤー**         | システム化する情報、状態、ビジネスルール。要件の要として整合性を維持                     | 情報、状態、条件、バリエーション                |

## RDRAのダイアグラム

要件定義は以下のダイアグラム単位で作成し、プロジェクトの状況に応じて使い分けます。

| ダイアグラム               | レイヤー         | 説明                                                               |
|----------------------------|------------------|--------------------------------------------------------------------|
| **システムコンテキスト図** | システム価値     | システム化の目的を端的に表す。価値を提供するアクターと外部システム |
| **要求モデル図**           | システム価値     | 要求を整理し、システム化の方向性を明確にする                       |
| **ビジネスコンテキスト図** | システム外部環境 | システム化対象の最上位のビジネス単位「業務」を明らかにする         |
| **ビジネスユースケース図** | システム外部環境 | 「業務」をビジネスユースケースに細分化する                         |
| **業務フロー図**           | システム外部環境 | ビジネスユースケースをアクティビティ図で表す                       |
| **利用シーン図**           | システム外部環境 | 「フロー」がない場合の使われ方を記述する                           |
| **UC複合図**               | システム境界     | ユースケース、画面、イベント、情報、条件を関連づける               |
| **バリエーション/条件図**  | システム         | ビジネスルールを表現する                                           |
| **情報モデル図**           | システム         | システム化したいビジネス上の用語とその関係                         |
| **状態モデル図**           | システム         | 状態遷移図で「xx済」「xx待ち」「xx中」などを表す                   |

## ダイアグラムの関係

各ダイアグラムは大きく4つの分類されます。

1. **方向性を求めるもの**: システムコンテキスト、要求モデル
2. **階層化でスコープを表すもの**: ビジネスコンテキスト → ビジネスユースケース →
   業務フロー/利用シーン → UC複合図
3. **ユースケース横断で整合させるもの**: 情報モデル、状態モデル
4. **要件定義の詳細を定義するもの**: バリエーション/条件

```text

│                   (時間の10%、議論の土台作り)                 │

                              │
                              ▼

│                                                             │
│  Step5: 業務からユースケース(UC)を導き出す                   │

                              │

│  Step9: 条件とバリエーションを詳細化し、実装レベルにする      │
└─────────────────────────────────────────────────────────────┘
```

### 3. 各フェーズの詳細手順 (Detailed Steps)

#### 3.1 フェーズ1: 枠組みを作る (議論の土台作り)

**目的**: システム化対象となる業務全体とシステム化の範囲を早期に可視化し、関係者間で共通認識を形成するための「議論の土台」を整える。

**Step1: アクター/外部システムと業務を洗い出す**

- **システム価値レイヤー**の定義
    - 機能要求、非機能要求を記載する
    - システムを利用する人や組織の役割（アクター）をリストアップする
    - 連携が必要な既存システムや外部サービス（外部システム）をリストアップする
- **システム外部環境レイヤー**の定義
    - システム化の対象となる「業務」と、その業務を構成する「ビジネスユースケース (BUC)」を洗い出す
    - 1つの「業務」は、部署や課やチームなどの組織単位で担われる業務のまとまり

**Step2: 業務の流れを把握し、アクティビティを見える化する**

- ビジネスユースケース (1つの業務フロー)を構成する「アクティビティ」を洗い出す
- アクティビティとは、業務フローの中で実行される個々の作業や行動
- アクティビティを洗い出すことで、1つのビジネスユースケースが業務フローを一連の目的を持った流れとして過不足なく表しているかを確認
- BUCが大きすぎる場合は分割し、細かすぎる場合は統合

**Step3: 業務で扱う情報を明らかにする**

- **システムレイヤー**の定義
    - 業務で扱う「情報」をリストアップする
    - システムで管理すべき情報を特定する
    - 情報は複数のユースケース間の連携を表す

**Step4: 業務の中で「状態」を洗い出す**

- 業務の中で「こういう状態になる」というものを洗い出す
- 「状態」をリストアップする（例: 「xx済」「xx待ち」「xx中」）
- 状態の遷移はユースケースが実現すべき情報の変化を表す

##### チェックリスト

詳細な確認項目は [checklists/requirement.md](checklists/requirement.md) を参照してください。

---

#### 3.2 フェーズ2: 要件を組み立てる (要件の具体化)

**目的**: フェーズ1で整えた枠組みを前提として、「システム要件定義」を中心に要件を具体化し、要件同士の関係性を明確にする。

**Step5: 業務からユースケース (UC)を導き出す**

- **システム境界レイヤー**の定義
    - 業務からユースケース (UC)を導き出し、システム化する部分を整理する
    - ユースケースを洗い出すことで、どの業務をシステムでサポートするのかが明らかになり、システム化の範囲を可視化
    - 画面（人と関わる入出力）とイベント（外部システムとの連携）を特定する

**Step6: 情報や状態とUCを関連づけ、要件の精度を上げる**

- 洗い出した情報や状態とユースケースを関連づける
- 情報をハブとして他のユースケースと繋ぐ
- ユースケースによる情報の変化を状態として表すことでユースケースの妥当性を評価
- アクター、外部システムをユースケースに関連付ける

##### チェックリスト

詳細な確認項目は [checklists/api.md](checklists/api.md) を参照してください。

---

#### 3.3 フェーズ3: 整合性・網羅性を確認し精度を高める (仕上げと仕様化の準備)

**目的**: 要素間の参照関係の誤りや、定義された要素が実際のユースケースで使用されていないといった問題を早期に発見し、要件定義の整合性と網羅性を高める。

**Step7: システムが動く「条件」を整理する**

- **システムレイヤー**の詳細化
    - システムがどんなときに動くのか、という「条件」を整理する
    - 条件（ビジネスルール）をユースケースに関連付ける
    - 例: 単価表、承認ルールなど

**Step8: 「条件」を成り立たせる「バリエーション」を洗い出す**

- 「条件」を成り立たせるための「バリエーション」を洗い出す
- 例: 取引先、商品種類、顧客タイプなど

**Step9: 条件とバリエーションを詳細化し、実装レベルにする**

- それぞれの条件とバリエーションについて具体的な要素を洗い出す
- 実装に必要なレベルまで詳細にする
- RDRAモデル全体の整合性を確認
    - 不整合の検出: 要素間の参照関係の誤りや未使用要素を発見
    - 全体俯瞰: ユースケースを軸に、アクター・外部システム・情報などの要素との関係を俯瞰的に確認

##### チェックリスト

詳細な確認項目は [checklists/issue-creation.md](checklists/issue-creation.md) を参照してください。

#### 3.4 Wikiへの出力と完了報告

1. **RDRA モデルのユーザー確認**:
    - 構築したRDRAモデル（4レイヤー、ダイアグラム）をユーザーに提示する
    - モデルの内容について質問・修正を促し、最終確認を得る
    - AIは要求を一方的に決定してはならない

2. **Wiki への出力**:
    - 確認済みのRDRAモデルを `docs/12 Requirement definition` ディレクトリにMarkdownとして出力する
    - 入力元は `docs/11 Requests` ディレクトリ内のファイルを使用する
    - 要件の階層構造、トレーサビリティ、ダイアグラムを整理して記録する
    - 元の要件ドキュメントは変更せず、新しいRDRAモデルファイルを出力する

3. **完了報告**:
    - Wikiに出力したファイルパスまたはページURLをユーザーに報告する
    - 実装順序の推奨と次のステップ（必要に応じてIssue作成）を提案する
    - **GitHub Issuesはこのスキルでは作成しない**。Issue作成はユーザーの判断に委ねる

### 4. 重要ルール (Important Rules)

1. **RDRAはモデルベースの要件定義手法**:
    - RDRAは「Relationship Driven Requirement Analysis」の略称で、読み方は「ラドラ」
    - システムを構成する要素同士の関係（Relationship）を定義することで、システム全体の構造を明確に捉える
    - 要件を個別の項目として管理するのではなく、要素同士の関係性を軸にシステム全体を一つの構造として捉える

2. **4つのレイヤーを厳格に区別する**:
    - システム価値レイヤー: 要求、アクター、外部システム
    - システム外部環境レイヤー: 業務、BUC、アクティビティ
    - システム境界レイヤー: ユースケース、画面、イベント
    - システムレイヤー: 情報、状態、条件、バリエーション
    - 各レイヤーは「Why」の依存関係を持ち、下位から上位に向かって「なぜ？」と問いかける

3. **ダイアグラム単位で要件定義する**:
    - 要件定義はダイアグラム単位で作成する
    - プロジェクトの状況に応じてダイアグラムを使い分ける
    - ダイアグラムはドキュメントとして保持するものではなく、コミュニケーションツール

4. **Wiki は読み取りと出力先**:
    - Wiki ドキュメントは要件の読み取り元であり、構築したRDRAモデルの出力先でもある
    - 元の要件ドキュメントは変更せず、新しいRDRAモデルファイルを出力する

5. **Issue は作成しない**:
    - このスキルはRDRAモデルをWikiにまとめることに特化している
    - GitHub Issues の作成は行わず、ユーザーの判断に委ねる

6. **ユーザーの確認が必要**:
    - RDRAモデルをWikiに出力前に、必ずユーザーの確認を得る
    - AIは要求を一方的に決定してはならない
    - AIは「候補の生成」「質問」「整理」「検証」を行い、最終的な要求の確定はユーザーが行う

7. **粒度は要件レベルで統一する**:
    - UC（ユースケース）: それを実行することで実行した人に何かうれしいことがある（何かが実現できる）
    - 情報モデル: エンティティレベル以上
    - 粒度を統一するとメンテナンスしやすい

### 3.5 ユースケース記述の作成手順 (Use Case 3.0 に基づく)

ユースケース記述（Use-Case Narrative）は、Ivar JacobsonのUse Case 3.0実践に基づいて作成します。Use Case
3.0は、ユースケースを軽量かつ構造化された形式で記述し、インクリメンタルな配信を可能にする実践ファミリーです。

#### 3.5.1 Use Case 3.0の基本概念

Use Case 3.0は以下の10の原則に基づいています：

1. **普遍的に適用可能**: あらゆる種類のシステムに適用できる
2. **大きな絵から始める**: システム全体の価値を可視化する
3. **価値に焦点を当てる**: ユーザーが得る価値を優先する
4. **ステークホルダーを関与させる**: 関係者との対話を重視する
5. **全体の話語る**: システムの全体像を伝える
6. **対話を引き出す**: 要件定義はコミュニケーションのきっかけ
7. **読みやすさを優先する**: 誰でも理解できる形式で記述する
8. **必要な分だけ、必要な時に**: 過度な詳細化を避け、必要に応じて詳細化する
9. **段階的に実装する**: 重要なフローを先に実装し、後に追加する
10. **スライスでシステムを構築する**: エンドツーエンドの価値パスをスライスとして分割して開発する

#### 3.5.2 ユースケース記述の作成プロセス

ユースケース記述は、以下の4つのアクティビティを順に実行して作成します：

**1. アクターとユースケースを特定する (Find Actors and Use Cases)**

- ステークホルダーとワークショップを行い、システムを利用するアクターとユースケースを特定する
- すべてのユースケースを網羅しようとするのではなく、価値を提供する重要なユースケースに焦点を当てる
- ユースケースをリリース計画に合わせて優先順位をつける
- 出力: ユースケースモデルの概要、アクターリスト、ユースケースリスト

**2. ユースケースを議論しスライスする (Discuss and Slice a Use Case)**

- ステークホルダーとユースケースのスコープとイベントの流れについて共有理解を構築する
- ユースケースを適度なサイズのスライスに分割する
- 利用可能な時間と予算に適合させる
- ユーザーに最も高い価値を提供するスライスを選択する
- 出力: ユースケーススライス、Basic Flowの概要、Alternate Flowsのリスト

**3. ユースケーススライスを分析する (Analyze a Use-Case Slice)**

- コーディング前に、スライスがシステムに与える影響を評価する
- 何を変更し、何を新規に追加する必要があるかを特定する
- 出力: ユースケース実現（Use-Case Realization）、責任の割り当て

**4. ユースケーススライスを準備する (Prepare a Use-Case Slice)**

- 記述を明確にし、テストケースを定義し、ワークアイテムに分割する
- テストケースがないスライスは準備済みとは見なさない
- 出力: 詳細なユースケース記述、テストケース、ワークアイテム

#### 3.5.3 ユースケース記述（Use-Case Narrative）の構造

ユースケース記述は、以下の構成要素で構成されます：

| 構成要素                                  | 説明                                                                                                     |
|-------------------------------------------|----------------------------------------------------------------------------------------------------------|
| **ユースケース名**                        | ユースケースを簡潔に表す名前（動詞+名詞の形式）                                                          |
| **アクター**                              | ユースケースと相互作用する主要アクターと補助アクター                                                     |
| **目標**                                  | アクターがユースケースの実行によって達成したい機能目標                                                   |
| **前提条件 (Preconditions)**              | ユースケースを開始する前に満たされている必要がある条件                                                   |
| **トリガー (Trigger)**                    | ユースケースのイベントフローを開始するイベント                                                           |
| **基本フロー (Basic Flow)**               | 正常なハッピーパスを単純なステップリストとして記述。各ステップはシステムまたはアクターが何かを行うこと   |
| **代替フロー (Alternate Flows)**          | 特殊ケース、オプションステップ、エラー処理をリスト形式で記述。最初に名前のみを列挙し、必要に応じて詳細化 |
| **後件条件 (Postconditions)**             | ユースケース完了後のシステム状態                                                                         |
| **制約 (Constraints)**                    | ユースケースに適用される制約条件                                                                         |
| **サポート情報 (Supporting Information)** | 用語定義、ビジネスルール、非機能要件など                                                                 |

#### 3.5.4 基本フローの記述ルール

基本フローは、以下のルールに従って記述します：

1. **ステップ形式**: 番号付きの単純なステップリストとして記述する
2. **主語と動詞**: 各ステップは「アクター/システム + 動詞 + 目的語」の形式で記述する
3. **能動態**: 誰が何をするかを明確にするために能動態を使用する
4. **適切な詳細レベル**: 一般的に10〜15ステップ程度を目標とする
5. **設計詳細の省略**: 色、フィールドの位置、ボタン名などの設計詳細は含めない
6. **ビジネスルールの分離**: ビジネスルールはユースケース内に記述せず、別途管理する
7. **終了ステップ**: ユースケースが完了したことを示すステップで終了する

基本フローの例：

```
1. ショッパーが製品を検索することを示す
2. システムが製品リストを表示する
3. ショッパーが購入する製品を選択する
4. システムが選択した製品の詳細を表示する
5. ショッパーが製品をカートに追加する
6. システムがカートに製品を追加したことを確認する
7. ショッパーがチェックアウトを開始する
8. システムが注文確認画面を表示する
9. ショッパーが注文を確認して送信する
10. システムが注文を受け付けたことを確認する
```

#### 3.5.5 代替フローの記述ルール

代替フローは、以下のルールに従って記述します：

1. **名前付きリスト**: 最初に代替フローの名前のみを列挙する
2. **必要に応じて詳細化**: チームが必要とした場合にのみ詳細を追加する
3. **加算的構造**: 基本フローは必須であり、代替フローはオプションとして追加できる
4. **独立した追加**: 各代替フローは独立して追加でき、既存の実装を変更しない

代替フローの例：

```
A1 無効なカード
A2 標準外の金額
A3 領収書が必要
A4 ATMに現金が不足
A5 口座残高が不足
A6 引き落とし超過
A7 カードが詰まる
A8 現金が残る
```

#### 3.5.6 段階的な詳細化アプローチ

Use Case 3.0では、一度にすべてのフローを記述しません。以下の順序で段階的に詳細化します：

1. **Basic Flowを先に記述**: 正常なハッピーパスをまず記述する
2. **Alternate Flowsを自然に発見**: Basic Flowを記述する过程中に、何が間違える可能性があるかを考え、Alternate
   Flowsとしてメモする
3. **後で詳細化**: 必要に応じてAlternate Flowsの詳細を追加する
4. **テストケースを定義**: ユースケースはテストケースが定義されて初めて完全に定義されたものと見なす

#### 3.5.7 ユースケース記述の品質チェックリスト

ユースケース記述を作成する際は、以下の項目を確認します：

- [ ] ユースケース名は簡潔で記述的か
- [ ] アクターは役割として命名されているか（個人名ではない）
- [ ] 主要アクターと補助アクターが明確か
- [ ] 目標はアクターが達成する機能目標として記述されているか
- [ ] 前提条件はユースケース開始前に満たされている条件として記述されているか
- [ ] トリガーはユースケースのイベントフローを開始するイベントとして記述されているか
- [ ] 基本フローは番号付きのステップリストとして記述されているか
- [ ] 各ステップは「アクター/システム + 動詞 + 目的語」の形式か
- [ ] 能動態で使用されているか
- [ ] 設計詳細（色、フィールド位置、ボタン名など）は含まれていないか
- [ ] ビジネスルールは別途管理されているか
- [ ] 終了ステップでユースケースの完了が明確か
- [ ] 代替フローは名前としてリストされているか
- [ ] 後件条件はユースケース完了後のシステム状態として記述されているか
- [ ] 制約は適用される制約条件として記述されているか
- [ ] サポート情報は用語定義やビジネスルールを含んでいるか
- [ ] 読みやすさが優先されているか
- [ ] 過度な詳細化は避けられているか

#### 3.5.8 ユースケーススライスとテストケース

Use Case 3.0では、ユースケースをスライスに分割してインクリメンタルに配信します：

- **ユースケーススライス**: ユースケース内の1つ以上のパスと、それを機能させるための設計・コード・テスト
- **テストケース**: ユースケースを完全に定義するために必須。開発者に完了の基準を示す
- **ワークアイテム**: スライスを実装するための具体的な作業単位。ユーザーストーリーと互換性がある
