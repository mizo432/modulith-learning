# API契約定義チェックリスト (フェーズ2: 要件を組み立てる)

本チェックリストは、RDRAのフェーズ2「要件を組み立てる」における確認項目をまとめたものです。
フェーズ1で整えた枠組みを前提として、「システム要件定義」を中心に要件を具体化し、要件同士の関係性を明確にしているかを確認します。

---

## Step5: 業務からユースケース (UC)を導き出す

### システム境界レイヤー

- [ ] 業務からユースケース (UC)を導き出しているか
- [ ] システム化する部分が整理されているか
- [ ] ユースケースを洗い出すことで、どの業務をシステムでサポートするのかが明らかか
- [ ] システム化の範囲が可視化されているか
- [ ] 画面（人と関わる入出力）が特定されているか
- [ ] イベント（外部システムとの連携）が特定されているか
- [ ] ユースケース一覧が作成されているか
- [ ] ユースケース図が作成されているか

### 画面定義

- [ ] 画面一覧が作成されているか
- [ ] 画面定義が明確か（画面名、関連ユースケース、入力・出力項目）
- [ ] 画面とユースケースの関連付けが適切か

### イベント定義

- [ ] イベント一覧が作成されているか
- [ ] イベント定義が明確か（イベント名、トリガー、関連ユースケース）
- [ ] イベントとユースケースの関連付けが適切か

---

## Step6: 情報や状態とUCを関連づけ、要件の精度を上げる

- [ ] 洗い出した情報とユースケースを関連づけているか
- [ ] 状態とユースケースを関連づけているか
- [ ] 情報をハブとして他のユースケースと繋いでいるか
- [ ] ユースケースによる情報の変化を状態として表しているか
- [ ] 状態を用いてユースケースの妥当性を評価しているか
- [ ] アクターをユースケースに関連付けているか
- [ ] 外部システムをユースケースに関連付けているか
- [ ] UC複合図が作成されているか（ユースケース、画面、イベント、情報、条件を関連づける）

---

## ユースケース記述の品質確認

Use Case 3.0に基づくユースケース記述の確認項目：

- [ ] ユースケース名は簡潔で記述的か（動詞+名詞の形式）
- [ ] アクターは役割として命名されているか（個人名ではない）
- [ ] 主要アクターと補助アクターが明確か
- [ ] 目標はアクターが達成する機能目標として記述されているか
- [ ] 前提条件はユースケース開始前に満たされている条件として記述されているか
- [ ] トリガーはユースケースのイベントフローを開始するイベントとして記述されているか
- [ ] 基本フローは番号付きのステップリストとして記述されているか
- [ ] 各ステップは「アクター/システム + 動詞 + 目的語」の形式か
- [ ] 能動態で使用されているか
- [ ] 設計詳細（色、フィールド位置、ボタン名など）は含まれていないか
- [ ] ビジネスルールは別途管理されているか
- [ ] 終了ステップでユースケースの完了が明確か
- [ ] 代替フローは名前としてリストされているか
- [ ] 後件条件はユースケース完了後のシステム状態として記述されているか
- [ ] 制約は適用される制約条件として記述されているか
- [ ] サポート情報は用語定義やビジネスルールを含んでいるか
- [ ] 読みやすさが優先されているか
- [ ] 過度な詳細化は避けられているか
- [ ] ファイル名が「UC-{番号} ユースケース名.md」の形式か

---

## 共通確認項目

- [ ] 4つのレイヤーが厳格に区別されているか
- [ ] 各レイヤー間の「Why」の依存関係が明確か
- [ ] 粒度が要件レベルで統一されているか
    - UC: それを実行することで実行した人に何かうれしいことがある
    - 情報モデル: エンティティレベル以上
- [ ] AIが要求を一方的に決定していないか（ユーザーの確認を得ているか）
- [ ] 元の要件ドキュメントを変更していないか
