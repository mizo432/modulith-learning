# ボトムアップ分析ガイドライン

このガイドラインは、既存システムをボトムアップで分析し、RDRAモデルとして業務要件をリバースエンジニアリングする手順を詳細に説明します。

---

## 1. 分析の準備

### 1.1 分析対象の特定

分析を開始する前に、以下の情報を整理します：

1. **システム名**: 分析対象のシステム名
2. **分析目的**: システム再構築 / 保守開発の品質向上
3. **分析範囲**: 対象モジュール・非対象モジュール
4. **担当者**: 分析担当者・ヒアリング可能な関係者

### 1.2 資料の収集チェックリスト

以下の資料を収集し、有無を確認します：

- [ ] 画面一覧または画面のハードコピー
- [ ] 外部とのインターフェース一覧
- [ ] DBスキーマ情報（テーブル一覧・カラム情報・制約情報）
- [ ] ファイルフォーマットの資料
- [ ] 機能一覧
- [ ] 機能詳細書
- [ ] 契約書などの外部企業との資料
- [ ] バッチ処理/APIのドキュメント
- [ ] ソースコードへのアクセス権

## 2. 入出力から整理（ステップ2）

### 2.1 画面の分析方法

#### 画面一覧の作成手順

1. 現在使われている画面を全てリストアップ
2. 各画面について以下の情報を記録：
   - 画面ID（例: SCR-001）
   - 画面名
   - 画面の役割（登録・編集・照会・一覧・承認など）
   - 表示項目一覧
   - 入力項目一覧
   - 操作ボタン一覧

#### 画面からUCを導出する手順

1. 画面の役割を機能単位で分類
2. 各機能からUCを導出：
   - 登録画面 → 「[情報]を登録する」
   - 編集画面 → 「[情報]を更新する」
   - 照会画面 → 「[情報]を照会する」
   - 削除ボタン → 「[情報]を削除する」
3. UCの命名ルール：「[情報]を[動詞]する」形式

#### アクターの特定手順

1. 各画面の利用者を特定
2. 利用者を役割として抽象化：
   - 個人名 → 役割名（例: 田中 → 営業担当者）
   - 組織名 → アクター群（例: 営業部 → 営業）
3. 同じ役割を持つアクターをグループ化

### 2.2 イベントの分析方法

#### イベント一覧の作成手順

1. 外部とのインターフェースを全てリストアップ
2. インターフェースがない場合は以下の方法で特定：
   - バッチ処理のジョブ定義から連携箇所を特定
   - APIの呼び出し元・先から連携箇所を特定
   - ログファイルから外部システムとの通信を特定
3. 各イベントについて以下の情報を記録：
   - イベントID（例: EVT-001）
   - イベント名
   - 連携先外部システム
   - 送信・受信データ
   - 実行タイミング（リアルタイム・バッチ・タイマー）

#### イベントからUCを導出する手順

1. イベントを機能単位で分類
2. 画面から求めたUCを再利用できる場合は再利用
3. 外部システムとの連携として新たなUCを導出

---

## 3. データから整理（ステップ3）

### 3.1 DBスキーマの分析方法

#### スキーマ情報の出力

1. データベースのスキーマ情報を出力：
   - テーブル一覧
   - 各テーブルのカラム情報（型・制約・デフォルト値）
   - 主キー・外部キー制約
   - インデックス情報
2. スキーマ情報を構造化して記録

#### テーブルから情報を抽出する手順

1. **ビジネスIDの特定**:
   - テーブルの主キーがビジネス上のIDか確認
   - 技術的なID（連番）とビジネス上のIDを区別
2. **情報の抽出**:
   - ビジネスで管理しているID単位で情報を定義
   - テーブルをそのまま情報とはしない
   - 複数のテーブルを組み合わせて1つの情報とする場合がある
3. **属性の抽出**:
   - カラムから情報の属性を抽出
   - 技術的なカラム（更新日時・更新者など）は除外
4. **関連の抽出**:
   - 外部キー制約から情報同士の関連を抽出
   - 親子関係がある場合は親と子の情報に分割

### 3.2 状態モデルの抽出手順

1. 情報に状態を示すカラムがあるか確認：
   - ステータスカラム（例: status, state, flag）
   - 日付カラムの組合せ（例: 登録日・更新日・削除日）
2. 状態の集合を状態モデルとして定義
3. 状態間の遷移を整理：
   - 状態A → 状態B の遷移パターンを列挙
4. 各遷移をトリガーするUCを特定

### 3.3 情報とUCをつなぐ手順

1. 抽出した情報がどのUCで操作されるかを特定
2. 「画面 → UC → 情報」の関係を頼りに類推
3. 情報同士の関連を関連情報として定義

---

## 4. ソースコードから分析（ステップ4）

### 4.1 フォルダー分析の手順

1. **プロジェクト構造の把握**:
   - ルートディレクトリの構成を確認
   - モジュール・パッケージの階層を把握
2. **業務領域の推測**:
   - パッケージ名から業務領域を推測（例: com.example.order → 受注管理）
   - モジュール名からサブドメインを推測
3. **BUC・UCとの対応**:
   - トップダウンで分析したBUC・UCとフォルダーの対応関係を整理
   - ソースコードへのインデックスとして使用

### 4.2 ソースコード分析の手順

1. **コントローラー/ハンドラーの分析**:
   - URLマッピングから画面との対応を特定
   - リクエストハンドラーからイベントとの対応を特定
2. **サービス層の分析**:
   - サービスメソッドからUCのロジックを特定
   - メソッド名からUC名を推測
3. **リポジトリ/DAO層の分析**:
   - エンティティクラスから情報（エンティティ）との対応を特定
   - クエリメソッドから情報の操作パターンを特定
4. **状態遷移の分析**:
   - 状態変更のロジックから状態モデルを特定
   - 状態遷移のガード条件からビジネスルールを特定
5. **バリデーションの分析**:
   - バリデーションアノテーションから条件を特定
   - カスタムバリデーターからビジネスルールを特定

---

## 5. 手に入る資料から整理（ステップ5）

### 5.1 機能一覧の変換手順

1. 機能一覧の大中小分類をRDRAモデルに当てはめる：
   - 大分類 → 業務
   - 中分類 → BUC
   - 小分類 → UC
2. 全体を俯瞰しながら適切な単位に変えていく
3. 分類が不適切な場合は再調整

### 5.2 機能詳細からの抽出

1. 機能詳細書から以下の情報を抽出：
   - 入力項目 → 情報の属性
   - 処理条件 → 条件（ビジネスルール）
   - 出力項目 → 情報の属性
   - 区分・種別 → バリエーション
2. 条件や区分を洗い出す

### 5.3 契約書からの抽出

1. 契約書などの文書からビジネスルールを条件として抽出
2. 条件につながるバリエーションを全て出す
3. 仕組みとしてのルールは含めない

---

## 6. 欠けているピースを補う（ステップ6）

### 6.1 統合手順

1. 各アプローチで抽出したRDRAモデルを統合
2. 欠けている要素を特定：
   - UCにつながっていない情報
   - 状態遷移に当てはまっていないUC
   - アクター・外部システムにつながっていないUC
3. 各情報をつないで欠けているピースを補う
4. トップダウンとボトムアップの両方からつなげる

### 6.2 整合性確認チェックリスト

- [ ] 全てのUCが情報とつながっている
- [ ] 全ての状態遷移にUCが当てはまっている
- [ ] 全てのアクターがUCとつながっている
- [ ] 全ての外部システムがUCとつながっている
- [ ] 全ての条件がバリエーションと状態モデルとつながっている
- [ ] 未使用の要素がない

---

## 7. RDRAモデルとして出力（ステップ7）

### 7.1 出力ファイルの配置

分析結果は以下のディレクトリに出力します：

```
1_RDRA/[事業領域名]/
├── アクター.tsv
├── 外部システム.tsv
├── BUC.tsv
├── 情報.tsv
├── 状態.tsv
├── 条件.tsv
└── バリエーション.tsv
```

### 7.2 TSVファイルの形式

各TSVファイルの列構造は以下の通りです：

| ファイル | 列 |
|---------|-----|
| アクター.tsv | アクター群\tアクター\t説明 |
| 外部システム.tsv | 外部システム群\t外部システム\t説明 |
| BUC.tsv | 業務\tBUC\t先\tアクティビティ\t次\tUC\t関連モデル1\t関連オブジェクト1\t関連モデル2\t関連オブジェクト2\t説明 |
| 情報.tsv | コンテキスト\t情報\t属性\t関連情報\t状態モデル\tバリエーション\t説明 |
| 状態.tsv | コンテキスト\t状態モデル\t状態\t遷移UC\t遷移先状態\t状態モデル・状態の説明 |
| 条件.tsv | コンテキスト\t条件\t条件の説明\tバリエーション\t状態モデル |
| バリエーション.tsv | コンテキスト\tバリエーション\t値\t説明 |

## 8. 品質保証

### 8.1 可視化のゴール確認

分析が完了したら、以下のゴールを確認します：

**システム再構築の場合**:
- [ ] アクター・外部システムを分かる範囲で洗い出した
- [ ] ビジネスで管理しているIDを洗い出した
- [ ] 状態の存在を認識できた場合に洗い出した
- [ ] ビジネスルールを洗い出した（存在が分かる程度）
- [ ] 区分・種別からバリエーションを整理した
- [ ] 業務を網羅的に出した
- [ ] 調査で明らかになった画面とイベントを適用した

**保守開発の品質向上の場合**:
- [ ] アクター・外部システムを網羅的に整理した
- [ ] ビジネスで管理しているIDを全て洗い出した
- [ ] 状態遷移にUCを適用し欠けてるUCを洗い出した
- [ ] 条件につながるバリエーションを全て出した
- [ ] 業務・BUC・アクティビティ・UCは関連部署の担当者と共通認識が取れるベースになった

### 8.2 RDRAGraphでの視覚化

分析結果をRDRAGraph形式に変換し、視覚的に確認します：

1. TSVファイルをRDRAGraph形式に変換
2. グラフ上で要素間の関係を視覚的に確認
3. 不整合や欠落を特定し、修正する
