### Current System Analysis Guide (`current-system-analysis`)

このスキルは、**modulith-learning** リポジトリにおいて、現行システムの分析を行う際に適用する手順ガイドラインです。
システム構成の把握、機能分析、データフロー分析、パフォーマンス分析、問題点の特定、改善提案の作成、ドキュメント化までを体系的に行います。

---

### 1. いつこのスキルを使用するか (When To Use)

- 現行システムの分析が必要なとき（新システム設計の基礎資料作成、性能改善、技術的負債の把握など）
- 既存システムの構成・機能・データフローを文書化する必要があるとき
- システムの問題点やボトルネックを特定し、改善策を提案する必要があるとき
- ステークホルダー向けに分析結果を報告する必要があるとき
- 現行システムから新システムへの移行計画を立てる必要があるとき

---

### 2. 分析手順 (Analysis Procedure)

#### 2.1 目的と範囲の明確化

**目的の定義**

- 現行システムの分析がなぜ必要かを明確にする（例：性能改善、新システム設計の基礎資料、技術的負債の把握など）。
- 分析の結果をどのように活用するかを事前に定義する。

**分析範囲の特定**

- 分析対象とするシステム、サブシステム、モジュール、コンポーネントを決定する。
- 分析範囲外の項目も明示し、スコープを明確にする。

> 参照: `docs/01 Current system analysis/index.md`（現行システムを分析する理由）

#### 2.2 データ収集

**ドキュメントの収集**

- システム設計書、ユーザーマニュアル、運用ガイドなど、既存のドキュメントを収集する。
- プロジェクト内の `docs/` 配下のドキュメントを優先的に参照する。
- 要件定義書、DDDモデル候補、ステートマシン図などの設計資料も収集対象とする。

**関連者インタビュー**

- システム開発者、運用担当者、ユーザーなど関係者へのインタビューを通じて、システムの使用状況や問題点を確認する。
- インタビュー結果は構造化して記録し、分析に反映する。

**システムモニタリング**

- システムのログやパフォーマンスデータを収集する。
- 負荷テスト結果、エラーログ、アクセスログなどを分析材料とする。

#### 2.3 現状分析

**システム構成の把握**

- ハードウェア、ソフトウェア、ネットワーク構成を詳細に文書化する。
- 以下の構成要素を特定し、図示する。
  - アプリケーションサーバー、データベースサーバー、外部システム
  - ミドルウェア（API Gateway、サービスレジストリ、メッセージキューなど）
  - ネットワーク構成（VPC、サブネット、セキュリティグループ）

**機能分析**

- システムの主要機能と各モジュールの役割を明確にする。
- 機能一覧を作成し、各機能の責務、入力・出力、関連モジュールを記載する。
- 既存の要件定義書やDDDモデルを参照し、機能の網羅性を確認する。

**データフローの分析**

- データの流れを図示し、データの生成、処理、保存、出力の流れを確認する。
- 以下の観点でデータフローを分析する。
  - データソース（入力元）
  - 処理プロセス（変換・検証・集計など）
  - データストア（保存先）
  - 出力先（画面、ファイル、外部システムなど）

**パフォーマンス分析**

- 現行システムのパフォーマンスを評価し、レスポンスタイムやスループット、負荷の分布を解析する。
- 以下のメトリクスを収集・分析する。
  - APIレスポンスタイム（平均、P95、P99）
  - スループット（リクエスト数/秒）
  - CPU・メモリ使用率
  - データベースクエリパフォーマンス
  - 同時接続数・セッション数

**問題点の特定**

- 技術的な欠陥、性能上のボトルネック、業務上の不満点などを整理する。
- 問題点は以下のカテゴリで分類する。
  - **技術的負債**: 時代遅れの技術、不適切な設計、コードの重複など
  - **パフォーマンス問題**: レスポンスタイムの遅延、スループットの不足、リソースの枯渇など
  - **運用問題**: 監視の不備、デプロイの複雑さ、バックアップの不十分さなど
  - **セキュリティ問題**: 認証・認可の不備、データ漏洩のリスク、コンプライアンス違反など
  - **ユーザビリティ問題**: 操作性の悪さ、情報の見つけにくさ、エラーメッセージの不十分さなど

#### 2.4 評価と改善提案

**問題点の評価**

- 発見された問題点の影響度と優先度を評価する。
- 評価マトリクス（影響度 × 発生頻度）を使用して優先度を決定する。

| 優先度 | 影響度 | 発生頻度 | 対応方針 |
|:-------|:-------|:---------|:---------|
| 高 | 大 | 頻繁 | 早期対応 |
| 中 | 中 | 時々 | 計画的対応 |
| 低 | 小 | 稀 | 機会対応 |

**改善提案の作成**

- 各問題に対する具体的な改善策を提案する。
- 改善提案には以下の要素を含める。
  - 問題の説明
  - 改善策の詳細
  - 期待される効果
  - 実施に必要なリソースと期間
  - リスクと緩和策

#### 2.5 ドキュメント化

**分析結果の文書化**

- 全ての分析結果を一つのレポートとしてまとめる。
- ドキュメント構成は以下の通り。

> 参照: `.agents/guidelines/current-system-analysis/templates/現行システム分析ドキュメント.md`

```
現行システム分析レポート
├── 1. 概要
│   ├── 1.1 分析目的
│   ├── 1.2 分析範囲
│   └── 1.3 分析方法
├── 2. システム構成
│   ├── 2.1 全体構成図
│   ├── 2.2 ハードウェア構成
│   ├── 2.3 ソフトウェア構成
│   └── 2.4 ネットワーク構成
├── 3. 機能分析
│   ├── 3.1 機能一覧
│   ├── 3.2 モジュール役割
│   └── 3.3 機能詳細
├── 4. データフロー
│   ├── 4.1 データフロー図
│   ├── 4.2 データソース
│   ├── 4.3 データストア
│   └── 4.4 データ変換
├── 5. パフォーマンス
│   ├── 5.1 パフォーマンスメトリクス
│   ├── 5.2 ボトルネック分析

├── 6. 問題点と改善提案

    ├── 7.1 分析のまとめ
    ├── 7.2 改善計画
    └── 7.3 継続的なモニタリング
```

**改善計画の策定**

- 改善提案に基づき、実施計画、スケジュール、必要なリソースを明確にする。
- フェーズごとに優先順位を付け、マイルストーンを定義する。

#### 2.6 ステークホルダーへの報告

**結果の共有**

- 分析結果と改善提案をステークホルダーに対して報告し、フィードバックを受け取る。
- 報告資料は、技術者向けと経営者向けの2種類を準備することを推奨する。

**フィードバックの反映**

- 受け取ったフィードバックを元に、必要に応じて分析結果や改善計画を修正する。
- フィードバックの記録と対応状況を管理する。

#### 2.7 次のステップの準備

**改善施策の実行準備**

- 提案された改善策を実行するための準備を行う（例：プロジェクトチームの編成、リソースの確保など）。
- 改善施策の実施順序と依存関係を明確にする。

**継続的なモニタリング**

- 改善施策の効果を評価するために、継続的なモニタリング体制を整備する。
- 改善前後のメトリクスを比較し、効果を定量的に評価する。

### 4. 分析チェックリスト (Analysis Checklist)

分析時・ドキュメント化時に以下の項目を確認してください。

- [ ] 分析目的と範囲が明確に定義されている
- [ ] 既存ドキュメントが網羅的に収集されている
- [ ] 関連者インタビューが実施され、結果が記録されている
- [ ] システム構成図が作成されている
- [ ] 機能一覧が作成され、各モジュールの役割が明確である
- [ ] データフロー図が作成されている
- [ ] パフォーマンスメトリクスが収集・分析されている
- [ ] 問題点が特定され、カテゴリ別に分類されている
- [ ] 問題点の評価マトリクスが作成されている
- [ ] 改善提案が具体的で、期待効果が明確である
- [ ] 分析結果がドキュメント化されている
- [ ] 改善計画が策定され、スケジュールが明確である
- [ ] ステークホルダーへの報告が計画されている
- [ ] 継続的なモニタリング体制が整備されている

### 6. ベストプラクティス (Best Practices)

#### 6.1 分析の実施

- **客観的なデータに基づく**: 主観的な意見だけでなく、ログデータ・メトリクス・インタビュー結果などの客観的なデータを分析の根拠とする。
- **比較対象の設定**: 改善前後の比較が可能なよう、分析時の状態を基準値として記録する。
- **複数視点の統合**: 技術者・運用者・ユーザーの複数の視点から分析し、偏りを避ける。

#### 6.2 ドキュメント化

- **図解の活用**: 構成図・データフロー図・シーケンス図など、図解を使用して複雑な情報を視覚化する。
- **バージョン管理**: 分析ドキュメントはGitでバージョン管理し、変更履歴を追跡可能にする。
- **レビューの実施**: 分析結果は関係者でレビューし、正確性と網羅性を確認する。

#### 6.3 改善提案

- **優先順位の明確化**: 全ての改善策を同時に実施するのではなく、優先順位を付けて段階的に実施する。
- **ROIの考慮**: 改善策の実施コストと期待効果を比較し、ROIの高いものから優先する。
- **フィードバックループ**: 改善施策の実施後も継続的にモニタリングし、効果を評価・改善する。
