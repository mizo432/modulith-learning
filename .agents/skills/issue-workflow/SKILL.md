# issue-workflow

## When to Use (いつ使うべきか)

- GitHub Issue に対応する作業を開始するとき
- ブランチ作成のルールを確認したいとき
- コミットやプッシュのタイミングについて確認したいとき
- PR 作成のルールやタイミングについて確認したいとき
- Issue 対応の全体フローを理解したいとき

---

## Quick Start (処理フロー)

1. **Issue の見直し**: 対象 Issue の内容、要件、ラベル、優先度を再確認し、作業の妥当性を検証
2. **ブランチ作成**: メインブランチから feature ブランチを作成
3. **実装とテスト**: 要件に基づき実装し、テストを作成・実行
4. **コミットとプッシュ**: 機能単位でコミットし、ブランチにプッシュ
5. **PR 作成**: 実装完了後に PR を作成
6. **PR レビュー**: `pr-review` スキルによる3回の反復レビューを実施
7. **マージと Issue クローズ**: レビュー完了後にマージし、Issue をクローズ

---

## Guidelines (ガイドライン)

### 1. Issue の見直しルール (Issue Review Rules)

Issue 対応作業に着手する前に、必ず対象 Issue を見直し、作業の妥当性を確認します。

#### 1.1 見直しのタイミング

- **Issue 対応作業開始前**: ブランチ作成前に必ず実施
- **Issue 内容変更後**: Issue の本文やコメントが更新された場合
- **長期放置後の再開**: 2週間以上放置した後で作業を再開する場合

#### 1.2 見直しチェックリスト

以下の項目をすべて確認し、問題がないことを検証します。

| チェック項目 | 確認内容 | 判定基準 |
|:---|:---|:---|
| **Issue の有効性** | Issue がまだ有効か、既に解決されていないか | 重複 Issue がないか、既にマージされていないか |
| **タイトルの明確さ** | タイトルから内容が一目でわかるか | 前置き (feat/fix/docs など) が付いているか |
| **本文の充実度** | 概要・詳細・環境・再現方法が記載されているか | 本文が空でないか、必要な情報が揃っているか |
| **要件の明確さ** | 何を実装すればよいか明確か | 受け入れ基準が定義されているか |
| **ラベルの適切さ** | 適切なラベルが付与されているか | 変更タイプ (feat/fix/docs など) が反映されているか |
| **優先度の確認** | 優先度が適切に設定されているか | 緊急度と重要度が合致しているか |
| **関連 Issue の確認** | 関連する Issue や PR が存在するか | 依存関係や重複がないか |
| **Assignee の確認** | 担当者が適切に設定されているか | 自分が担当者か、または作業を始めてよいか |
| **Milestone の確認** | 適切なマイルストーンが設定されているか | 目標期間と合致しているか |
| **日本語として読めるか** | issueの内容が日本語として自然に読めるか | タイトル・概要・詳細が日本語で記載され、機械翻訳のような不自然な表現がないか |

#### 1.3 見直し時のアクション

| 状況 | アクション |
|:---|:---|
| **Issue が無効** | 担当者に確認し、必要に応じて Issue をクローズ |
| **重複 Issue 発見** | 重複している Issue を統合し、片方をクローズ |
| **要件が不明確** | Issue のコメントで不明点を質問し、回答を待つ |
| **ラベルが不適切** | 適切なラベルに変更する |
| **優先度が不適切** | 優先度を調整する |
| **関連 Issue 未发现** | 関連する Issue を見つけてリンクする |
| **日本語として読めない** | issueの内容を自然な日本語に修正する |
| **すべて正常** | 作業继续进行 |

#### 1.4 見直し後の進め方

1. **問題発見の場合**: Issue を修正または担当者に確認してから作業を開始
2. **すべて正常の場合**: ブランチ作成に進み、実装を開始
3. **記録の残し方**: 見直しで発見した事項を Issue のコメントに記載

### 2. ブランチ戦略 (Branch Strategy)

#### 2.1 ブランチ命名規則

| ブランチタイプ | 命名規則 | 例 |
|:---|:---|:---|
| メインブランチ | `main` | `main` |
| 開発ブランチ | `develop` | `develop` |
| 機能ブランチ | `feature/issue-<番号>-<短い説明>` | `feature/issue-378-add-issue-workflow-skill` |
| バグ修正ブランチ | `fix/issue-<番号>-<短い説明>` | `fix/issue-123-fix-login-error` |
| ドキュメントブランチ | `docs/issue-<番号>-<短い説明>` | `docs/issue-456-update-readme` |
| リファクタブランチ | `refactor/issue-<番号>-<短い説明>` | `refactor/issue-789-refactor-auth-module` |

#### 2.2 ブランチ作成ルール

- **必ず最新のメインブランチから分岐**: 作業開始前に `main` ブランチを最新に更新してから feature ブランチを作成
- **1 Issue につき 1 ブランチ**: 1つのブランチで複数の Issue をまたいで作業しない
- **ブランチの説明**: ブランチ名から Issue 番号と内容が一目でわかるように命名
- **短い期間での作業**: ブランチは長期間放置せず、早めに PR を作成してマージする

#### 2.3 ブランチ分岐元

| Issue タイプ | 分岐元ブランチ | PR 先ブランチ |
|:---|:---|:---|
| 機能追加 (feat) | `main` | `develop` |
| バグ修正 (fix) | `main` | `main` |
| ドキュメント (docs) | `main` | `main` |
| リファクタ (refactor) | `main` | `develop` |
| その他 | `main` | `develop` |

### 3. コミットルール (Commit Rules)

#### 3.1 コミットメッセージの形式

```
<type>(<scope>): <subject>

<body>

Refs #<issue_number>
```

#### 3.2 コミットタイプ (type)

| タイプ | 説明 | 使用例 |
|:---|:---|:---|
| `feat` | 新規機能追加 | `feat(account): ユーザー登録機能を追加` |
| `fix` | バグ修正 | `fix(login): ログインエラーを修正` |
| `docs` | ドキュメント変更 | `docs(readme): インストール手順を更新` |
| `style` | コードスタイル修正 (フォーマット等) | `style(account): コードフォーマットを適用` |
| `refactor` | リファクタリング (仕様変更なし) | `refactor(auth): 認証ロジックを整理` |
| `perf` | パフォーマンス改善 | `perf(query): クエリパフォーマンスを最適化` |
| `test` | テストコードの変更 | `test(account): ユーザー登録のテストを追加` |
| `chore` | 雑務 (ビルド設定等) | `chore(gradle): 依存関係を更新` |

#### 3.3 コミットのタイミング

- **機能単位でコミット**: 1つのコミットで1つの論理的な変更を完了
- **テストを通してからコミット**: コミット前にテストを実行し、全件パスすることを確認
- **中途半端な状態をコミットしない**: 動作しないコードや未完成の機能をコミットしない
- **小刻みにコミット**: 大きな変更を複数の小さなコミットに分割

#### 3.4 Issue 番号の紐付け

- コミットメッセージの最後に `Refs #<issue_number>` を記載
- 複数の Issue をまたぐ場合は `Refs #<number1>, #<number2>` と記載
- Issue を解決する場合は `Closes #<issue_number>` または `Fixes #<issue_number>` を使用

---

### 4. プッシュルール (Push Rules)

#### 4.1 プッシュのタイミング

- **コミット後、即座にプッシュ**: ローカルでテストが通ったら、早めにリモートブランチにプッシュ
- **頻繁なプッシュ**: 作業途中でも定期的にプッシュしてバックアップを取る
- **PR 作成前にもプッシュ**: PR 作成前に最新のコードをプッシュすること

#### 4.2 プッシュ前の確認事項

- [ ] テストが全件パスしているか
- [ ] コミットメッセージが適切に記載されているか
- [ ] 不要なファイルや機密情報が含まれていないか
- [ ] ブランチが最新のメインブランチと統合されているか

---

### 5. PR 作成ルール (Pull Request Rules)

#### 5.1 PR 作成のタイミング

- **機能単位で PR を作成**: 1つの Issue や機能単位で PR を作成
- **早めに PR を作成**: 実装が完了したら早めに PR を作成してレビューを開始
- **Draft PR の活用**: 未完成だが早期にレビューを開始したい場合は Draft PR を使用

#### 5.2 PR の構成要素

| 要素 | 説明 |
|:---|:---|
| タイトル | `<type>: <短い説明>` の形式 (例: `feat: ユーザー登録機能を追加`) |
| 概要 | 変更内容の概要を7行程度で記載 |
| 変更差分表 | 変更ファイルのリストと状態 (created/updated/deleted/renamed) |
| 動作確認方法 | テスト実行方法や確認手順 |
| 関連 Issue | 関連する Issue のリンク (`closes: #XX`) |
| Label | 変更タイプに応じたラベルを付与 |
| Assignees | レビュアーを指定 |

#### 5.3 PR レビューフロー

1. **PR 作成**: `pull-request` スキルを使用して PR を作成
2. **自動テスト実行**: CI/CD による自動テストの実行を確認
3. **pr-review スキルによるレビュー**: `pr-review` スキルを使用して3回の反復レビューを実施
4. **指摘事項の修正**: レビューで指摘された事項を修正し、PR を更新
5. **マージ**: レビュー完了後に PR をマージ

#### 5.4 PR マージ後の処理

- **Issue のクローズ**: PR マージ後に Issue をクローズ (`closes: #XX` が設定されていれば自動クローズ)
- **ブランチの削除**: マージ後に feature ブランチを削除
- **変更の確認**: マージ後の動作を確認

---

### 6. Issue 対応の全体フロー (Complete Workflow)

```
Issue の見直し
    ↓
Issue 確認
    ↓
ブランチ作成 (feature/issue-<番号>-<説明>)
    ↓
実装とテスト
    ↓
コミット (Refs #<番号>)
    ↓
プッシュ
    ↓
PR 作成 (pull-request スキル)
    ↓
PR レビュー (pr-review スキル、3回の反復)
    ↓
マージ
    ↓
Issue クローズ
    ↓
ブランチ削除
```

---

### 7. 注意事項 (Important Notes)

- **Issue の優先度**: Issue のラベルや優先度に応じて対応の順序を決定
- **コミュニケーション**: 不明点や変更が必要な場合は、Issue のコメントで連携
- **ドキュメントの更新**: 機能追加や変更時には関連ドキュメントも更新
- **テストの網羅性**: 境界値や異常系を含む網羅的なテストを作成
- **コードレビューの重要性**: 自己レビューだけでなく、他者によるレビューを必ず実施
