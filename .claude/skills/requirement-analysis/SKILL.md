# Requirement Analysis（modulith-learning）

要求（ステークホルダーが欲しいもの）を、実装・テストで検証できる要件（システムが満たすべきこと）に変換する。
プロジェクトの手順書が正であり、このスキルはそれを実作業に落とすための手引き:

- `src/doc/02 Request analysis/02 システム要求のまとめ方.md` — 要求の収集・分類
- `src/doc/03 Requirement definition/02 システム要求からシステム要件定義にまとめる手順.md` —
  要件化・優先度・トレーサビリティ
- `src/doc/01 Current system analysis/` — 現行システム分析（既存機能の改修時）
- `src/doc/99 Dictionary/template/index.md` — 用語辞書の形式
- `src/doc/95 Architecture decision record (ADR)/template/template.md` — 設計判断の記録

着手時にこれらを読み、内容が食い違う場合はドキュメント側に従う。

## 0. 進め方の原則

- **推測で埋めない。** 不明点は「未決事項」として明示し、ユーザーに質問する。質問は一度にまとめ、選択肢と推奨案を添える。
- **価値から始める。** 機能の前に「誰の・どんな問題を・どう解決し・達成をどう判定するか」を確認する（
  `src/doc/20 question/index.md` の問いを参照）。
- **既存コードと用語を確認してから書く。** 同じ概念が既にモジュールとして存在しないか、
  `backend/src/main/java/undecided/**` と用語辞書を先に調べる。
- 成果物は日本語で書く。識別子（クラス名・API パス）は英語。

## 1. スコープと目的

次を 3〜6 行で書き、ユーザーと合意してから先へ進む:

- 背景 / 解決したい問題
- 対象ユーザー（ロール: 一般ユーザー / 管理者 など）と主な仕事
- スコープ内 / スコープ外（スコープ外を明記することが重要）
- 成功の判定方法（測れる指標または観察できる状態）

## 2. 要求の収集

情報源と、そこから得た要求を記録する。要求は原文に近い形で残し、まだ解釈しない。

| ID    | 情報源                                  | 要求（原文に近い形） |
|-------|-----------------------------------------|----------------------|
| RQ-01 | Issue #xx / ユーザー発言 / 現行システム | ...                  |

既存機能の改修なら、現行の振る舞いを実コード・テストから確認して「現状」として併記する。

## 3. 要件への変換と分類

要求ごとに、検証可能な要件文にする。1 要件 = 1 つの検証可能な事柄。

- 書式: 「〈主体〉は〈条件〉のとき、〈対象〉を〈振る舞い〉できる / しなければならない」
- 「適切に」「迅速に」「柔軟に」などの曖昧語は数値か具体的条件に置き換える。

分類（手順書 §3 に準拠）:

| 種別             | 例                                                     |
|------------------|--------------------------------------------------------|
| 機能要件 (FR)    | 管理者はプロジェクトをアーカイブできる                 |
| 非機能要件 (NFR) | 一覧 API は 1,000 件で p95 500ms 以内に応答する        |
| 業務要件 (BR)    | アーカイブ済みプロジェクトにはスプリントを追加できない |
| 技術要件 (TR)    | Flyway でスキーマ `xxx_reg` に追加する                 |
| 法規制要件 (LR)  | 個人情報は〇〇法に従い保持期間を設ける                 |

非機能要件は少なくとも次の観点を確認する（該当なしなら「該当なし」と書く）:
性能 / 可用性 / セキュリティ・認可（ロール別の可否） / 監査・ログ / データ保持・移行 / 国際化・日付と祝日（
`calendarReg` 等の既存モジュールとの関係）。

## 4. ドメインとモジュール境界

- 登場する用語を洗い出し、用語辞書の形式（用語名 / 読み方 / 英語表記 / 定義 / 関連用語 /
  カテゴリ）で定義する。新しい用語や既存と意味がずれる用語は辞書の更新候補として挙げる。
- 要件を、担当する Spring Modulith モジュール（`generic.*` / `supporting.*` / 業務モジュール）に割り当てる。
    - 既存モジュールに入るか、新しいモジュールが必要か。
    - モジュール間で必要な連携（公開 API / ドメインイベント）。`internal` への依存が必要に見えたら境界の見直しを提案する。
- 不変条件（常に成り立つべきルール）と状態遷移を列挙する。状態がある場合は簡単な状態遷移表を書く。
- 方針の分かれる設計判断があれば ADR の候補として記録する（このスキルでは決めきらず、選択肢とトレードオフを示す）。

## 5. ユースケースと受け入れ基準

主要なユースケースごとに:

- アクター / 事前条件 / 基本フロー / 代替・例外フロー / 事後条件
- 受け入れ基準を Given / When / Then で書く。正常系だけでなく、境界値・異常系・権限なしを必ず含める。

```
AC-FR-03-1
Given 管理者でログインしており、ステータスが ACTIVE のプロジェクトがある
When  そのプロジェクトをアーカイブする
Then  ステータスが ARCHIVED になり、一覧で「Archived」と表示される

AC-FR-03-2
Given 一般ユーザーでログインしている
When  プロジェクトのアーカイブ API を呼ぶ
Then  403 が返り、ステータスは変わらない
```

受け入れ基準は後工程でそのままテストになる粒度にする
（バックエンドは `should...` 命名 + 日本語 `@DisplayName` のテスト、フロントエンドは Storybook
のストーリー / `play` 関数）。

## 6. 優先順位と実現可能性

- MoSCoW（Must / Should / Could / Won't）で分類する。Won't も明記する。
- 各要件に概算の影響範囲（モジュール、DB マイグレーション有無、フロント画面）と主なリスクを添える。
- Must だけで最初に価値を届けられる最小の単位（MVP）を提案する。

## 7. トレーサビリティ

要求 → 要件 → 受け入れ基準 → 実装先 → テストを 1 つの表で追えるようにする:

| 要求  | 要件  | 優先度 | 受け入れ基準   | モジュール / 層                    | テスト         |
|-------|-------|--------|----------------|------------------------------------|----------------|
| RQ-01 | FR-03 | Must   | AC-FR-03-1, -2 | `xxxMgmt` / Business, Presentation | (実装時に記入) |

## 8. 成果物

1. 要件定義ドキュメントを `src/doc/03 Requirement definition/<連番> <テーマ>.md`
   に作成する。構成は以下:
    1. スコープと目的 / 2. 要求一覧 / 3. 要件一覧（分類別） / 4. 用語・モジュール割り当て・不変条件 /
    5. ユースケースと受け入れ基準 / 6. 優先度と MVP / 7. トレーサビリティ表 / 8. 未決事項・ADR 候補
2. 用語辞書の更新候補、ADR 候補は一覧として末尾に残す（辞書・ADR 自体の更新はユーザーの了承後）。
3. 実装単位への分割案（GitHub Issue の候補）を提示する。1 Issue = 1 つのレビュー可能な PR
   になる粒度で、タイトル・概要・受け入れ基準・依存関係を書く。 **Issue の作成（`gh issue create`
   ）は外部への公開になるため、必ずユーザーに確認してから行う。**

## 9. 完了前のセルフチェック

- [ ] スコープ外が明記されている
- [ ] すべての要件が検証可能（曖昧語がない）で、ID が振られている
- [ ] 各 Must 要件に正常系・異常系・権限の受け入れ基準がある
- [ ] 非機能要件の各観点に記述または「該当なし」がある
- [ ] 用語が辞書と矛盾していない、モジュール割り当てが境界ルールに沿っている
- [ ] 未決事項が質問としてユーザーに提示されている
- [ ] トレーサビリティ表で要求から受け入れ基準まで漏れなく辿れる
